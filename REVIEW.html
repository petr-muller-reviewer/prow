Verdict: Approve

Clean, well-tested, additive change. Adds trigger comment provenance (ID and URL) to ProwJobSpec and surfaces it as env vars for comment-triggered presubmits. No correctness bugs found. The implementation correctly keeps the boundary at provenance metadata (who triggered this) rather than behavioral parameters (what to do differently). All three independent reviewer perspectives converge on approval. Two suggestions and one architectural question below.

What this PR does

  • Adds a TriggerComment struct (ID + HTML URL) to ProwJobSpec to capture which GitHub comment triggered a job.
  • Populates it in handleGenericComment for /test, /retest, /ok-to-test commands; leaves it nil for automatic triggers (PR open/sync, Tide, periodics).
  • Surfaces as TRIGGER_COMMENT_ID and TRIGGER_COMMENT_URL env vars and in the JOB_SPEC JSON under trigger_comment.
  • Handles the review-body edge case (URL present but no dedicated comment ID) by omitting TRIGGER_COMMENT_ID when ID is zero.
  • Updates both CRD manifests, generated deepcopy, tests (two new cases), and documentation.

Findings

Should Fix RunRequestedWithLabels has 7 positional parameters

pkg/plugins/trigger/trigger.go:335-336

func RunRequestedWithLabels(c Client, pr *github.PullRequest, baseSHA string,
    requestedJobs []config.Presubmit, eventGUID string,
    labels map[string]string, triggerComment *prowapi.TriggerComment) error {

This exported function now takes 7 positional args. It's at the edge of readability and each new feature adds another parameter. Not blocking for this PR, but the next addition should refactor to an options struct. Consider noting this as a known debt item.

Nit Reserved env var names deserve a release note

pkg/pod-utils/downwardapi/jobspec.go:209

pullEnv := []string{PullNumberEnv, PullPullShaEnv, PullHeadRefEnv, PullTitleEnv,
    TriggerCommentIDEnv, TriggerCommentURLEnv}

TRIGGER_COMMENT_ID and TRIGGER_COMMENT_URL are now reserved for all presubmits via EnvForType. Any existing job config defining these names will fail config validation on upgrade. The names are distinctive enough that collision is very unlikely, but a release note would help operators who hit this.

Question Abstraction boundary: provenance vs. behavioral coupling

pkg/apis/prowjobs/v1/types.go:240-259

// TriggerComment, when set, references the GitHub comment whose command
// triggered this job (e.g. /test, /retest, /ok-to-test). It is nil for jobs
// that were triggered automatically ...
TriggerComment *TriggerComment `json:"trigger_comment,omitempty"`

TriggerComment introduces "how a job was triggered" into ProwJobSpec, which otherwise describes "what to run against what code". This PR keeps the right boundary — exposing provenance (ID and URL) rather than content (the comment body). But if future extensions start exposing the comment body or parsed arguments, that would cross into coupling job behavior to the trigger mechanism. Worth adding an explicit note in the struct doc comment that this is provenance metadata, not a channel for trigger-time arguments.

Things I checked and was fine with

  • All callers of RunRequestedWithLabels and RunRequested updated for the new parameter.
  • TriggerComment.ID uses int, matching prow's existing GitHub types (IssueComment.ID, Review.ID, ReviewComment.ID).
  • Shared triggerComment pointer in runRequested loop is safe: value-only fields, never mutated after construction, DeepCopy generated correctly (**out = **in).
  • Zero-value handling: ID == 0 suppresses TRIGGER_COMMENT_ID; empty HTMLURL suppresses TRIGGER_COMMENT_URL.
  • EnvForType/EnvForSpec asymmetry (unconditional listing vs conditional setting) matches existing pattern for PULL_TITLE and other optional vars.
  • CRD schema (type: integer / type: string) matches Go types. Both production and integration CRDs updated consistently.
  • Tests cover full-comment case (ID + URL) and URL-only case (review body, ID=0) with explicit absent-key assertion.
  • gc.CommentID nil-check in generic-comment.go correctly handles events without a dedicated comment ID.
  • Rollback is clean: old binaries ignore the trigger_comment field.
  • CRD update ordering is flexible (field is optional with zero-value defaults).

Open questions for the author

  • Should the TriggerComment doc comment explicitly state this is provenance metadata and not intended as a channel for passing trigger-time arguments to jobs? This would help future contributors maintain the right abstraction boundary.
  • Would you consider adding a release note about the two new reserved env var names (TRIGGER_COMMENT_ID, TRIGGER_COMMENT_URL) for presubmits?
