Verdict: Approve

A correct, focused, low-risk operational improvement. The change adds diagnostic reason strings to webhook HMAC validation failures, helping operators identify which org/repo has a misconfigured webhook secret. No critical issues. Two should-fix suggestions: acknowledge the exported API signature change, and add test assertions for the new message strings.

Gate: Merge

All CI checks pass. The exported ValidatePayload signature change is the only material merge risk, but the blast radius is small (common entry point ValidateWebhook is unchanged) and it's a compile-time break, not a runtime surprise. Missing approved label is a process gate (needs /approve from a pkg/OWNERS approver).

What this PR does

  • Changes ValidatePayload return type from bool to (bool, string), adding a human-readable reason for each failure path (invalid payload, invalid signature, missing HMAC config, wrong secret).
  • Surfaces the reason in the HTTP 403 response via ValidateWebhook, e.g. "403 Forbidden: Invalid X-Hub-Signature-256 - misconfigured webhook secret from organization/repo: foobar/foobar".
  • Updates a stale GitHub docs URL in types.go (old URL redirected to the new one).
  • Updates tests to destructure the new return value (but does not assert on the message content).

Findings

should-fix Exported API signature change not acknowledged

pkg/github/hmac.go:42

ValidatePayload is an exported function. Changing the return type from bool to (bool, string) is a compile-time breaking change for any external importer of sigs.k8s.io/prow/pkg/github that calls this function directly. The blast radius is small — ValidateWebhook is the common entry point and its signature is unchanged — but the PR description should acknowledge the API change for downstream consumers.

should-fix No test assertions on message return values

pkg/github/hmac_test.go:97-102

Tests correctly destructure (valid, msg) but only assert on valid. The diagnostic strings — the entire purpose of this PR — are untested. Adding an expectedMsg field to the table-driven test cases would prevent silent regressions. Additionally, no test case exercises the final "misconfigured webhook secret" path (valid JSON payload, valid-format signature, wrong HMAC key).

valid, msg := ValidatePayload([]byte(tc.payload), tc.sig, tc.tokenGenerator)
if valid != tc.valid {
    t.Errorf("Wrong validation for the test %q: expected %t but got %t, message: %s", tc.name, tc.valid, valid, msg)
}

nit Error message wording slightly misleading

pkg/github/hmac.go:78

"misconfigured webhook secret from organization/repo: " implies the webhook secret is misconfigured on the sender side, but the HMAC mismatch could also mean the webhook points at the wrong Prow instance or the HMAC config on the Prow side is stale. "webhook signature mismatch for organization/repo: " would be more neutral and accurate.

return false, "misconfigured webhook secret from organization/repo: " + orgRepo

nit Diagnostic detail in HTTP body vs server-side logging

pkg/github/webhooks.go:67

The detailed message (including the attacker-controlled orgRepo parsed from the unauthenticated payload) is returned in the HTTP response body. responseHTTPError logs at Debug level, which is often disabled in production. Logging at Warning/Info and keeping the HTTP body generic would be slightly cleaner. Not unsafe as-is: http.Error sets text/plain, no injection vector, and the reflected data is what the sender provided.

responseHTTPError(w, http.StatusForbidden, "403 Forbidden: Invalid X-Hub-Signature-256 - "+message)
