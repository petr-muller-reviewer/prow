Fix double linking bug when key is a substring of another link
github.com/kubernetes-sigs/prow/pull/776 · base: main · head: b566b97b9568557e32ab5c0eaea74423d5528981
Reviewed: 2026-07-01T11:57:54Z

Verdict

Approve with suggestions

All three review perspectives (code quality, maintainability, deployment risk) independently reach APPROVE with LOW risk and no breaking changes. The fix is correct, surgical, and well-documented. The one gap — no test for the suffix boundary case — was independently flagged by two reviewers and is worth a follow-up, but does not block merge.

What this PR does

  • Fixes a link-corruption bug where a shorter Jira key (e.g. BC-1) that is a substring of a longer one (ABC-123) was being matched and linked inside the already-generated [ABC-123](...) markdown, producing [A[BC-1](url1)23](url2).
  • Adds a prefix alphanumeric guard to replaceStringIfNeeded: skips replacement when the character immediately before the match is a letter or digit.
  • Adds a suffix alphanumeric guard: skips replacement when the character immediately after the match is a letter or digit (e.g. prevents AC-1 from matching inside AC-1234).
  • Extracts an isAlphanumeric(byte) bool helper used by both guards.
  • Extends the test table with an optional issueNames field (nil-safe fallback) and adds a multi-issue scenario reproducing the reported bug.

Findings

nit Suffix boundary case is untested 2 reviewers

📄 pkg/plugins/jira/jira_test.go:472

The updated code comment explicitly names two cases — prefix boundary (BC-1 inside ABC-123) and suffix boundary (AC-1 inside AC-1234) — but the new test only exercises the prefix. Every skipped replacement in the test is decided by prefixOk=false (the preceding 'A' short-circuits &&); suffixOk is never the decisive gate. A bug in the suffix path would leave all tests green.

// The blocked match in line 1:
//   "BC-1" inside "[ABC-123](url)" — text[idx-1]='A' → prefixOk=false → short-circuit
//   suffixOk (text[endIdx]='2') never evaluated as decisive

// Missing: a case where prefixOk=true but suffixOk=false, e.g.:
issueNames: []string{"AC-1", "AC-1234"},
body:        "AC-1234 references AC-1",
expected:    "AC-1234 references [AC-1](url)",  // AC-1 NOT linked inside AC-1234

nit Prefix condition mixes two idioms

📄 pkg/plugins/jira/jira.go:264

The combined prefix check places the pre-existing strings.Contains("[/\`-", string(text[idx-1])) (byte-to-string set membership) next to the new isAlphanumeric(text[idx-1]) (clean predicate). A isSafePrefixChar(c byte) bool helper that wraps both would unify them, name the concept, and make the condition a one-liner — useful if the guard character set ever expands again.

// Current (line 264):
prefixOk := idx == 0 || (!strings.Contains("[/`-", string(text[idx-1])) && !isAlphanumeric(text[idx-1]))

// Suggested follow-up:
prefixOk := idx == 0 || isSafePrefixChar(text[idx-1])

Things I checked and was fine with

  • startingIdx = endIdx is semantically identical to the removed startingIdx = idx + len(old) — pure DRY refactor, no behavior change.
  • isAlphanumeric on byte is correct: UTF-8 continuation bytes (0x80–0xBF) are outside the ASCII alphanumeric range, so multibyte characters adjacent to a match cannot false-positive.
  • strings.Contains("[/\`-", ...) is NOT made redundant by !isAlphanumeric: [, /, \`, - are non-alphanumeric and would pass the alphanumeric check, allowing replacement without the explicit guard. Both conditions are necessary and correct.
  • End-of-string safety: endIdx >= len(text) short-circuits before text[endIdx] is read — no out-of-bounds.
  • Issue-ordering independence: when BC-1 is processed before ABC-123, the preceding 'A' in the raw text still triggers prefixOk=false. Non-determinism from referencedIssues.UnsortedList() is safe.
  • Test helper refactor (optional issueNames []string field, nil fallback to the issueName constant) does not change semantics of any existing test case.
  • No config schema, API surface, CLI flags, or external dependencies changed — zero operator action needed on upgrade; rollback is safe.

Open questions for the author

  • Would you add a follow-up test for the suffix boundary? The case issueNames: []string{"AC-1", "AC-1234"}, body "AC-1234 references AC-1", expected "AC-1234 references [AC-1](url)" would close the gap and make the intent self-documenting — both halves of the fix would then have independent coverage.
  • Non-blocking: consider extracting isSafePrefixChar(c byte) bool to wrap the strings.Contains and isAlphanumeric checks together? Would make line 264 a one-liner and give the concept a name for future extension.
