  • API surface: No exported Go API changes beyond the new additive config field and accessor. No CRD/proto changes.

What this PR does

  • Adds a new config option abort_superseded_batch_jobs (per-org/repo map with * global key, defaulting to true) that tells Tide to abort stale in-flight batch ProwJobs before triggering a new batch.
  • New method abortSupersededBatchJobs(sp subpool) lists all Tide-created batch ProwJobs for the same org/repo/branch via label selector, then patches any with a baseSHA different from the current subpool SHA to AbortedState. Skips completed jobs and jobs matching the current SHA.
  • Called in takeAction right before pickBatch, only when batchPending == 0 and the config is enabled. Abort failures are non-fatal (logged, new batch proceeds).
  • Refactors pre-existing job filtering in the test from reflect.DeepEqual to name-based sets.Set — necessary because aborted jobs no longer match their original objects, and also cleaner.
  • Addresses the waste described in issue #650: when baseSHA advances, old batches become invisible to Tide (filtered by dividePool) but keep running to completion, producing results that can never be used.

Findings

Should fix No logging on successful abort

pkg/tide/tide.go:1561-1571

The patch loop logs errors but is completely silent on success. All three review perspectives flagged this independently. An info-level log per aborted job (with job name and old baseSHA) would match the codebase’s instrumentation standard and make production debugging significantly easier.

if err := c.prowJobClient.Patch(c.ctx, &pj, ctrlruntimeclient.MergeFrom(prev)); err != nil {
    errs = append(errs, fmt.Errorf("failed to abort superseded batch prowjob %s: %w", pj.Name, err))
}

Suggested addition after the patch succeeds:

sp.log.WithField("prowjob", pj.Name).WithField("old_base_sha", pj.Spec.Refs.BaseSHA).Info("Aborted superseded batch job")

Should fix No Prometheus counter for aborted jobs

pkg/tide/tide.go:1541-1573

The codebase already has tideMetrics.retests for batch triggers. An analogous tide_superseded_batch_aborts_total counter (with org/repo/branch labels) would let operators quantify compute savings and detect misconfiguration (e.g., unexpectedly high abort rates). Could reasonably be a follow-up PR.

Nit List-to-Patch race can mark a just-completed job as aborted

pkg/tide/tide.go:1562

Between the List call and the Patch loop, a job could complete naturally. The pj.Complete() guard only checks the snapshot from list time. A patch would then set a completed job back to AbortedState. The window is narrow and the consequence is cosmetic (the work already ran), but worth documenting as a known limitation.

if pj.Spec.Refs == nil || pj.Spec.Refs.BaseSHA == sp.sha || pj.Complete() {
    continue
}

Nit Test uses branch name as BaseSHA for “current” job

pkg/tide/tide_test.go:2110

The “current-batch” fixture sets BaseSHA: defaultBranch (a branch name like “master”), which happens to equal sp.sha. Using a distinct fake value like "current-sha" with a matching sp.sha would make the test intent clearer.

Question Interaction with prioritize_existing_batches

pkg/tide/tide.go:1602-1607

Both features affect batch lifecycle but are complementary: prioritize_existing_batches tries to reuse existing batch results, while abort_superseded_batch_jobs cleans up when a new batch is triggered. The interaction may not be obvious to operators. A brief note in the config documentation would help.
