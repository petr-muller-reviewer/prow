Verdict

Approve.

Clean, well-structured addition that follows existing codebase patterns closely. No correctness issues found. All three review perspectives (code quality, maintainability, deployment risk) converge on approve. The strongest suggestion — documenting the ref format convention — was raised independently by two reviewers but is not blocking.

What this PR does

  • Adds CreateRef/CreateRefWithContext and UpdateRef/UpdateRefWithContext to the GitHub client for creating and updating Git references via the API.
  • Refactors the existing GetRef to delegate to a new GetRefWithContext, enabling context-aware ref reads.
  • Introduces IsUnprocessableEntity for classifying 422 errors (e.g. non-fast-forward ref updates) and NewUnprocessableEntity for test construction.
  • Extends FakeClient with RefsCreated/RefsUpdated tracking slices so downstream tests can assert on ref mutations.
  • Adds unit tests verifying HTTP methods, paths, request body payloads, and error classification.

Should fix

Should fix Ref format convention undocumented on UpdateRef

pkg/github/client.go:3476-3497

// UpdateRef updates a ref to the given SHA.
func (c *client) UpdateRef(org, repo, ref, sha string, force bool) error {

// UpdateRefWithContext updates a ref to the given SHA.
func (c *client) UpdateRefWithContext(ctx context.Context, org, repo, ref, sha string, force bool) error {

CreateRef requires a fully-qualified ref (refs/heads/my-branch) while UpdateRef/GetRef take an unqualified ref (heads/my-feature). The difference is encoded in the URL path construction (/repos/.../git/refs for POST vs /repos/.../git/refs/%s for PATCH) but not in the doc comments. Two independent reviewers flagged this as an easy source of caller mistakes. Adding a note like // ref does not include the "refs/" prefix, e.g. "heads/my-feature" would prevent misuse.

Nit TestUpdateRef only tests force: false

The test only exercises the force: false path. A table-driven case with force: true would verify the boolean serializes correctly rather than always being the zero value.

Nit CreateRefWithContext doc omits namespace requirement

pkg/github/client.go:3458

// CreateRefWithContext creates a ref at the given SHA.

CreateRef’s doc says the ref must include its namespace (refs/heads/my-branch), but the WithContext variant omits this. Since WithContext is where the implementation lives, it should carry the full contract.

Things I checked and was fine with

  • GetRef refactor to delegate to GetRefWithContext is semantically equivalent — c.request() already calls requestWithContext(context.Background(), ...) internally.
  • Adding methods to the CommitClient interface does not break other implementors: downstream code uses narrow per-plugin interfaces (e.g. override.githubClient, tide.githubClient), not CommitClient directly.
  • map[string]string in CreateRef vs map[string]interface{} in UpdateRef is correct: the force field must serialize as a JSON boolean, not a string.
  • IsUnprocessableEntity follows the same errors.As + status-code check pattern as the existing IsNotFound. Intentionally lacks the ErrorMessages() fallback (that fallback is legacy).
  • FakeClient implementations properly acquire the mutex before appending to the tracking slices.
  • Tests verify HTTP method, URL path, request body contents (via cmp.Diff), and error classification (wrapped 422 recognized, 400 rejected).
  • New mutating methods are dry-run safe (POST/PATCH short-circuited by requestRawWithContext).
  • No new API token scopes required.
  • DeleteRef lacking a WithContext variant is a pre-existing asymmetry, not a blocker for this PR.
