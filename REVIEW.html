Verdict

Approve (with suggestions) — correct, well-scoped fix; add regression tests for the new guard when convenient, but nothing here should block merge.

The fix correctly addresses the panic from #800 both defensively (nil guard in publisher.Commit) and at the root cause (populating GitUser in GitClientFactory). A follow-up multi-perspective maintainer review (code quality, maintainability, deployment risk) independently converged on the same conclusion: small, low-risk, idiomatic change with no config/API surface impact and LOW deployment risk. The main remaining gap is test coverage — neither new code path has an accompanying test case — which is worth asking for but doesn't warrant blocking a change this size and risk.

What this PR does

  • Fixes #800: publisher.Commit panicked with a nil pointer dereference when p.info (a GitUserGetter) was never set.
  • pkg/git/v2/publisher.go: adds an if p.info == nil guard in Commit, returning a wrapped error instead of panicking.
  • pkg/flagutil/github.go: GitClientFactory now sets opts.GitUser in the token/app-auth branch, using the same user login as opts.Username and an empty email — this is the actual root-cause fix for real-world callers.
  • No test changes included.

should-fixNo test asserting GitClientFactory sets GitUser

pkg/flagutil/github.go:340-366

The actual root-cause fix (populating opts.GitUser from the token/app-auth branch) has no accompanying test. A unit test asserting opts.GitUser is non-nil / returns the expected user after this branch runs would cover the real bug, not just the defensive guard in publisher.go.

opts.Username = func() (string, error) { return user, nil }
opts.GitUser = func() (string, string, error) { return user, "", nil } // pass empty email, git allows this
opts.Token = generator

questionEmpty email acceptable for all downstream consumers?

pkg/flagutil/github.go:359

Using an empty email is valid git (--author "name <>"), but worth confirming GitHub / downstream tooling handles commits with an empty-email author as expected (attribution, verification, etc.) across every caller of GitClientFactory (tide, hook, moonraker, deck, cherrypicker, gerrit, generic-autobumper, sub, gangway).

nitConsider a noreply-style email instead of empty string

pkg/flagutil/github.go:359

A synthesized email like <login>@users.noreply.github.com (GitHub's own convention for bot commit authorship) would maximize compatibility with any external tooling that assumes a non-empty author email, versus the current empty string. Non-blocking follow-up.

Things I checked and was fine with

  • Nil guard error format matches the existing wrapping style in the same function (fmt.Errorf("error committing %q: ...", title)).
  • GitUser is only set inside the cookieFilePath == "" && (TokenPath != "" || AppPrivateKeyPath != "") branch, consistent with where Username/Token are set — the Gerrit path is correctly unaffected/out of scope. It still leaves GitUser nil after this PR and relies solely on the new guard in publisher.go to fail cleanly instead of panicking — confirmed intentional defense-in-depth, not an oversight.
  • All current callers of GitClientFactory (moonraker, tide, deck, hook, gangway, sub, cherrypicker, generic-autobumper, gerrit) route through this fixed path and benefit.
  • Change is minimal and additive; low blast radius, no behavior change for already-correctly-configured callers. No config/CLI/API surface changes; safe, low-risk upgrade with clean rollback.
  • Multi-perspective maintainer review (code quality, maintainability, deployment risk) independently converged on the same two should-fix findings above; deployment risk assessed LOW, maintenance burden assessed LOW.
