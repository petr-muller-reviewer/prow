Verdict

Request changes.

The contextCheckerGetterFactory fix (append instead of replace) is correct and addresses the core issue. However, the requirementDiff change introduces double-counting of missing required contexts because unsuccessfulContexts already calls MissingRequiredContexts internally. This was independently identified by all three review perspectives (code quality, maintainability, deployment risk). The inflated diff value affects PR-to-query ranking, and the duplicated call site creates a maintenance hazard. The factory fix alone may be the complete solution.

What this PR does

  • Fixes contextCheckerGetterFactory to append additional required contexts to the base policy instead of replacing them, preserving contexts from Tide configuration.
  • Adds an explicit MissingRequiredContexts check in requirementDiff to detect contexts that are completely absent from the PR (not just present-but-failed).
  • Adds slices.Compact() to deduplicate context names in the status description message.
  • Adds 12 new test cases for the missing-context scenarios and a dedicated test for the factory append behavior.
  • Includes minor whitespace alignment fixes in unrelated constant/map declarations.

Findings

Blocking Double-counting of missing required contexts in requirementDiff

Converging concern: independently flagged by all three reviewers (code quality, maintainability, deployment risk).

pkg/tide/status.go:235-242

unsuccessfulContexts at tide.go:878 already calls cc.MissingRequiredContexts() and returns missing contexts as synthetic failed entries. The new code at status.go:242 calls cc.MissingRequiredContexts() again and appends to the same contexts slice. Every missing required context ends up in contexts twice.

The slices.Compact at line 248 fixes the user-visible description, but it runs after diff += len(contexts) at line 245. The diff value is inflated. Since diff is used at status.go:322 to rank PR-to-query matches (minDiffCount), this affects which query Tide considers closest for a PR. 

// tide.go:878 — already inside unsuccessfulContexts:
for _, c := range cc.MissingRequiredContexts(contextsToStrings(contexts)) {
    failed = append(failed, newExpectedContext(c))
}

// status.go:235-242 — new code adds them again:
for _, ctx := range unsuccessfulContexts(headContexts, cc, log) {
    contexts = append(contexts, string(ctx.Context))
}
// ...
contexts = append(contexts, cc.MissingRequiredContexts(presentContexts.UnsortedList())...)

Recommendation: Investigate whether the contextCheckerGetterFactory append fix alone resolves the bug. If unsuccessfulContexts now correctly detects missing required contexts (which it should, since the factory properly populates them), remove the redundant MissingRequiredContexts call from requirementDiff. If both calls are genuinely needed, document why with a comment and ensure diff is computed after deduplication.

Blocking Test expectedDiff values encode the double-counting bug

Converging concern: independently flagged by code quality and maintainability reviewers.

pkg/tide/status_test.go:1324-1435

The test comments misattribute the expectedDiff values. For example, "Missing required context not present in PR" claims expectedDiff: 2 is "1 for ci/test being present + 1 for missing ci/required-check". But ci/test is successful and not counted by unsuccessfulContexts. The 2 comes from ci/required-check being counted twice. The tests pass but validate incorrect behavior.

Once the double-counting is fixed, these expectedDiff values and comments will need updating.

Blocking Duplicated responsibility creates maintenance hazard

pkg/tide/status.go:235-242 and pkg/tide/tide.go:878

MissingRequiredContexts is now called in two places for the same data flow — inside unsuccessfulContexts and again explicitly in requirementDiff. A future maintainer modifying context-checking logic must trace both call sites and understand their interaction, with Compact acting as a silent safety net. The contextCheckerGetterFactory append fix alone may be the complete root cause fix: once the factory correctly populates RequiredContexts, unsuccessfulContexts naturally detects missing ones without needing the second call.

Should fix Unnecessary len guard on append

pkg/tide/status.go:793-795

append(slice, empty...) is a no-op in Go. The if len(requiredContexts) > 0 guard adds no value and slightly obscures the intent. 

if len(requiredContexts) > 0 {
    contextPolicy.RequiredContexts = append(contextPolicy.RequiredContexts, requiredContexts...)
}

Could be simplified to just the append line.

Should fix TestContextCheckerGetterFactoryAppend uses type assertion on internal type

pkg/tide/status_test.go:1612-1616

The test type-asserts to *config.TideContextPolicy and inspects the RequiredContexts slice directly. If the return type ever becomes a wrapper, this breaks for unrelated reasons. Testing through the contextChecker interface (calling MissingRequiredContexts and IsOptional) would be more robust and better document the expected behavior. 

policy, ok := cc.(*config.TideContextPolicy)
if !ok {
    t.Fatalf("Expected *config.TideContextPolicy, got %T", cc)
}

Nit Whitespace-only changes in unrelated code

pkg/tide/status.go:48-50, pkg/tide/status_test.go:1751,1764

Alignment fixes for constant declarations and map literals that aren't related to this PR. Minor diff noise.

Nit Nil git.ClientFactory in TestContextCheckerGetterFactoryAppend

pkg/tide/status_test.go:1601

var gc git.ClientFactory is nil. Works because the tested code path doesn't invoke git methods, but will panic if factory internals change. A no-op or fake implementation would be safer.

Things I checked and was fine with

  • contextCheckerGetterFactory append-vs-replace fix is correct and addresses the core issue of base required contexts being dropped.
  • slices and sets imports are already present and used elsewhere in the file — no new dependencies.
  • MissingRequiredContexts method correctly computes set difference of RequiredContexts minus present contexts.
  • slices.Compact correctly deduplicates sorted slices (called after sort.Strings).
  • No security concerns.
  • Deployment risk is low: no config schema changes, no new API calls, backward-compatible, safe to roll back.
  • Previously silently dropped contexts from Tide config (overwritten by ProwJob-derived contexts) will now be correctly enforced — this is the desired behavior.

Open questions for the author

  • Was the double-counting in requirementDiff intentional as a stronger penalty for missing required contexts, or an oversight from not noticing that unsuccessfulContexts already handles this?
  • Would removing the new MissingRequiredContexts call from requirementDiff entirely (relying on unsuccessfulContexts) be acceptable, since that function already covers the missing-context case?
  • If both calls are genuinely needed (e.g., requirementDiff is sometimes called with a contextChecker that does not go through contextCheckerGetterFactory), can that reason be documented with a comment?
