Verdict: Approve with suggestions

Reviewed via direct code review plus a 3-perspective maintainer review (code quality, maintainability, deployment risk) and advisor synthesis — all four assessments converge. This is a small, well-scoped change with no config or API surface impact, and it incidentally fixes a latent bug in the pre-existing "single release note block" validation. The one recurring concern — best-effort line-ending handling in the new append path — is cosmetic, not a functional break, and doesn't block merge.

What this PR does

  • Makes /release-note-edit append a new release-note block to the PR body when one doesn't already exist, instead of erroring out.
  • Detects the body's line-ending style (\n vs \r\n) and avoids introducing extra blank lines when appending.
  • Moves the "must be used with a single release note block" validation from checking ic.Issue.Body to checking ic.Comment.Body — this incidentally fixes a bug where the old check could never actually detect multiple blocks.
  • Adds two new test cases: appending to a non-empty body without a block, and appending to an empty body.

Findings

should-fixMixed line-ending handling in the append path is unsound

pkg/plugins/releasenote/releasenote.go:511-524

lineEnding := "\n"
if strings.Contains(ic.Issue.Body, "\r\n") {
    lineEnding = "\r\n"
}
separator := lineEnding + lineEnding
if ic.Issue.Body == "" {
    separator = ""
} else if strings.HasSuffix(ic.Issue.Body, lineEnding+lineEnding) {
    separator = ""
} else if strings.HasSuffix(ic.Issue.Body, lineEnding) {
    separator = lineEnding
}

lineEnding is inferred from whether \r\n appears anywhere in the body, but the suffix checks assume that global guess matches the body's trailing line ending. A body with inconsistent line endings (plausible after manual GitHub edits) falls through all suffix branches to the double-separator default, producing a mixed-style seam right before the new block. Flagged independently by all three specialist reviewers (code quality, maintainability, deployment risk) in the maintainer review pass. Not a functional break — GitHub renders either way — but a real gap in the new logic worth tightening.

should-fixAppend-branch test coverage is narrow

pkg/plugins/releasenote/releasenote_test.go:767-800

expectedNote: "Top\nBelow\n\n```release-note\nThe new note\n```\n",
...
expectedNote: "```release-note\nThe new note\n```\n",

Only "body without a block, no trailing newline" and "empty body" are tested. Untested: body already ending in a blank line, body ending in exactly one line ending, and a body using \r\n line endings (the CRLF-detection branch is never exercised by any test). A future refactor of this logic has no test to catch a regression in those branches.

Things I checked and was fine with

  • Confirmed the old "single release note block" check (len(i) != 4 on FindStringSubmatchIndex(ic.Issue.Body)) could never actually detect multiple blocks — that function returns a fixed-length slice or nil, so the check was equivalent to "no match in issue body." The pre-existing "multiple release note blocks" test only passed incidentally because its fixture left Issue.Body empty. The new check is a genuine correctness fix, independently confirmed by all three specialist reviewers in the maintainer review pass.
  • Hand-traced both new test cases ("append to body without release note block", "append to empty body") against the separator logic — both produce the expected output.
  • newNote is already validated non-empty before the append branch runs (early return above for an empty note).
  • The appended block (fenced with ```release-note and a trailing line ending) matches noteMatcherRE, so subsequent plugin runs/label determination will pick it up correctly.
  • No config structs, YAML/JSON tags, CLI flags, or plugin registration are touched — change is isolated to one command handler. Rollback is a plain binary revert with no persisted-state migration.
  • The pre-existing "one release-note block" splice path (else branch) is functionally unchanged from before this PR, only re-indented.

Open questions for the author

  • Is the pluginHelp description meant to be updated in a follow-up, or is it intentionally left generic?
  • Does the new "exactly one block in the comment" check reject any previously-accepted /release-note-edit comment shape? If so, worth a one-line callout in the PR description/release notes.
