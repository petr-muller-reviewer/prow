Verdict: Needs discussion

The implementation itself is small, well-scoped, and low-risk — it plugs a real gap (kubelet-initiated terminations, e.g. spot-node reclaims, were previously misreported as test failures) into an existing, already-bounded revival mechanism, with solid unit test coverage for the new predicate, and was independently approved by a three-perspective maintainer panel (code quality, maintainability, deployment risk). However, two maintainer disagreements are now unresolved: scope (kubelet-termination-only vs. any DisruptionTarget reason, and whether that's safe on non-Kubernetes-only deployments like OpenShift), and — as of 2026-07-27 — a correctness objection that led to lgtm being canceled, disputing whether kubelet-initiated terminations are generally safe to retry. mimowo's documentation-backed rebuttal to the latter looks strong, but is unconfirmed by the objecting maintainer as of this refresh.

What this PR does

  • Adds a new PodUnexpectedStopCause value, termination-by-kubelet, detected via a new podWasTerminatedByKubelet helper.
  • The helper matches pods with status.reason == "Terminated" plus a DisruptionTarget condition whose status is True and reason is TerminationByKubelet (both upstream corev1 constants).
  • These pods now flow through the same delete-and-recreate branch in syncPendingJob already used for evicted/OOM-killed/unreachable-node pods, subject to the pre-existing MaxRevivals cap.
  • Renames an existing test case for clarity and adds new cases: a dedicated TestGetPodUnexpectedStopCause table (5 sub-cases) and a new TestSyncPendingJob case verifying revival behavior.
  • Fixes kubernetes-sigs/kueue#12856.

Findings

questionlgtm canceled: dispute over whether kubelet terminations are generally retriable

PR-level discussion (issue comments, 2026-07-27)

Prucek canceled lgtm, arguing the kubelet terminates pods for multiple legitimate, non-retriable reasons (resource-pressure eviction, graceful node shutdown, node-level preemption, node-level OOM), and objects to treating all kubelet-initiated terminations as retriable infrastructure glitches. mimowo responded citing upstream Kubernetes documentation: the DisruptionTarget pod condition is specifically and only attached for retriable disruption scenarios; pod-caused disruptions that would recur on retry (e.g. exceeding container resource limits) deliberately do NOT receive this condition. This directly addresses Prucek's concern if accurate — the PR doesn't match on "any kubelet termination," only ones additionally flagged via DisruptionTarget/TerminationByKubelet, which per docs excludes the non-retriable cases Prucek lists. As of this refresh, Prucek has not replied to the rebuttal and lgtm remains removed.

Prucek: "Kubelet terminates pods for many legitimate reasons: Resource
pressure ... Graceful node shutdown ... Priority-based preemption at the
node level ... Node-level OOM ... I don't think we should be going in this
direction. /lgtm cancel"

mimowo: "...DisruptionTarget condition ... was designed specifically to
mark retriable terminations ... In all other disruption scenarios, ...
Pods don't receive the DisruptionTarget condition because the disruptions
were probably caused by the Pod and would reoccur on retry."

questionNarrowed objection: does TerminationByKubelet over-include node-pressure eviction?

PR-level discussion (issue comments, 2026-07-27)

Prucek conceded the DisruptionTarget design intent (retriable-by-design for spot reclamation/graceful shutdown) but points out TerminationByKubelet specifically also fires for node-pressure eviction (memory/disk/PID pressure) — a case where retrying reproduces the same resource contention rather than escaping a transient infra event, and could compound cluster pressure. mimowo counters that MaxRevivals=3 bounds the downside, and that expecting contributors to manually distinguish "safe to retry now" from "will hit the same pressure again" before clicking retry is unrealistic. Author yuluo-yx reframed this as a broader open design question: should Prow auto-recover from infra disruption by default, and is there a need for granular per-cause/per-cluster opt-in/opt-out (which would also address the earlier "no opt-out for this revival cause, unlike eviction" finding below). Unresolved as of this refresh.

Prucek: "...TerminationByKubelet covers both spot/graceful-node-shutdown
and node-pressure eviction (memory, disk, PID pressure). For node-pressure
eviction, the pod was terminated because the node ran out of resources —
retrying is likely to hit the same problem again, and auto-reviving could
make things worse by adding load to an already-pressured cluster."

mimowo: "...the mechanism is anyway capped by max_revivals=3 ...
contributors don't check if a PR failed maybe due to PID pressure on node
... most of them just randomly do "retry". Relying on humans being slow is
not a good strategy."

yuluo-yx: "...key questions are: Should Prow automatically recover from
such infrastructure disruptions by default? And how can we provide
sufficiently granular control for expensive tasks, different clusters, and
various causes of disruption?"

questionScope disagreement: TerminationByKubelet-only vs. any DisruptionTarget

pkg/plank/reconciler.go:714-728 (podWasTerminatedByKubelet)

Maintainer mimowo proposed generalizing this to match any DisruptionTarget condition reason (covering preemption/eviction/kubelet-termination uniformly), citing upstream k8s docs that DisruptionTarget broadly signals k8s-initiated disruption, and asked the author to broaden the PR per a Slack discussion with testing leads. Maintainer droslean objects: Prow is not Kubernetes-only, and defaulting this behavior needs prior investigation of how OpenShift represents equivalent node/pod disruption. This is an open, unresolved design question that could change the shape of the fix (new type name PodUnexpectedStopCauseDisruption, broader condition match) before merge. The author has not yet responded substantively.

// mimowo's proposed generalization:
if podWasDisrupted(pod) {
    // DisruptionTarget identifies a retriable disruption affecting the Pod,
    // such as preemption, eviction, or termination by the kubelet. Treat it as
    // unexpected so Plank can revive the Pod. This also covers spot node
    // reclamation observed in Kueue CI.
    return PodUnexpectedStopCauseDisruption
}

questionNo opt-out for this revival cause, unlike eviction

pkg/plank/reconciler.go:487 (ErrorOnEviction) vs the new branch

Eviction has a per-job opt-out (pj.Spec.ErrorOnEviction) for teams wanting fail-fast instead of retry. The new kubelet-termination cause has no equivalent — any matching pod is always revived (subject to MaxRevivals). Raised by the deployment-risk reviewer as worth discussing with the author, not a merge blocker.

Things I checked and was fine with

  • podWasTerminatedByKubelet uses upstream corev1.DisruptionTarget / corev1.PodReasonTerminationByKubelet constants; confirmed present in vendored k8s.io/api (v0.29.6+).
  • Check ordering in getPodUnexpectedStopCause (evicted → kubelet-terminated → node-unreachable) has no overlap risk — the underlying pod.Status.Reason values are mutually exclusive across these branches.
  • The condition loop correctly returns on the first DisruptionTarget match (Kubernetes only ever sets one condition per type).
  • go build ./pkg/plank/..., go vet, and go test ./pkg/plank/... -run 'TestGetPodUnexpectedStopCause|TestSyncPendingJob' all pass locally at the head SHA.
  • New TestGetPodUnexpectedStopCause table covers the happy path plus 4 negative cases (inactive condition, wrong reason, missing condition, condition present but pod not Terminated).
  • No config/CRD/struct-tag changes; behavior is unconditional post-upgrade, inert on pre-1.26 clusters lacking PodDisruptionConditions; rollback is a plain binary revert.
  • No RBAC, dependency, or resource-consumption changes; reuses the existing delete/recreate pod flow.

Open questions for the author

  • Was a max-revivals test case for the new cause intentionally left out, or just missed alongside the existing eviction one?
  • Any interest in squashing the two commits before merge, given the second only adds a comment?
  • Is an ErrorOnEviction-style opt-out warranted for teams with strict-SLA jobs that prefer fail-fast over retry on kubelet-initiated termination?
  • Should this behavior change (retry instead of immediate failure for kubelet-terminated pods) be called out explicitly in release notes, given it silently affects fail-fast signals for operators on spot/preemptible infrastructure?
