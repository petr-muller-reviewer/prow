3/3 Reviewers

ListDeploys has no pagination — may miss deploys on busy repos

netlify/client.go:65

The Netlify GET /api/v1/sites/{site_id}/deploys endpoint returns paginated results (default 20 per page). For active repos like kubernetes/website, the latest deploy preview for a given PR may not appear in the first page if many production or branch deploys have occurred since.

Without a per_page query parameter or pagination loop, the plugin may falsely report "No Netlify deploy preview was found" for PRs that do have one.

Highest-confidence issue across all three reviews. The maintainer advisor recommends this be addressed either before merge or as an immediate follow-up.

Suggestion: At minimum, pass ?per_page=100 as a query parameter to widen the window. Ideally, also filter by branch=deploy-preview-{number} if the Netlify API supports it, so the relevant deploy is always in the result set. Consider paginating if the first page yields no match.
3/3 Reviewers

/retest overlaps with built-in trigger plugin

plugin/plugin.go:37,69 · server.go:131

Prow's built-in trigger plugin already handles /retest to re-run failed presubmit jobs (pkg/plugins/trigger/trigger.go:140). On repos where this external plugin is enabled, both plugins fire on every /retest comment. This is a deliberate design choice (per #693), but creates implicit coupling: any future change to /retest semantics in trigger must consider this plugin and vice versa.

Consequences:

  • Every /retest hits the Netlify API to list deploys, even when the user only wants to re-run Prow CI.
  • The plugin posts a comment on every /retest where Netlify has nothing useful to do (preview is ready, no preview exists, etc.). This is the common case and will be noisy.
  • On kubernetes/website with frequent /retest usage, this means an extra bot comment on most retests.
Suggestion: Either (a) only post a comment when a retry is actually performed — stay silent on no-ops for /retest specifically, or (b) use a distinct command like /retest-preview instead of overloading /retest. At minimum, add a code comment on commandRe explaining the intentional overlap with the trigger plugin, and document the dual-processing behavior.
2/3 Reviewers

Silent failure when Netlify API calls fail

server.go:165

When RetryDeploy (or ListDeploys) fails, the error is returned and logged by the goroutine, but no comment is posted to the PR. The user gets complete silence — they don't know whether the retry was attempted, succeeded, or failed.

Suggestion: Post a comment like "Failed to communicate with Netlify API" before returning the error, so users have feedback when something goes wrong.

Goroutine error logging at Info level + wrong logger

server.go:86-90

Two issues in the goroutine error path:

  • Wrong logger: Error is logged via s.log instead of the request-scoped l, losing the event-type and event-GUID structured fields.
  • Wrong level: Operational failures (Netlify API errors, GitHub API errors) are logged at Info level. These should be Warn or Error for monitoring visibility.

}()
Suggestion: Use l.WithError(err).Error("Failed to handle issue comment.") to preserve structured fields and use an appropriate log level.

Suggestion: Use io.LimitReader(resp.Body, 4096) or similar to cap the read.

Minor

Canceled/skipped Netlify build states not distinguished

plugin/plugin.go (Evaluate)

Source: apullo777 (Kueue), 2026-07-27, PR comment.

Kueue uses a Netlify build.ignore rule to skip previews for certain PRs, producing canceled/skipped deploy states. These currently fall into Evaluate()'s generic unsupported-state path rather than being handled explicitly, so a user retrying a deliberately-skipped preview gets the same response as any other unsupported state, with no indication the skip was intentional.

Not blocking for the current single-consumer (kubernetes/website) scope, but relevant if this plugin is adopted more broadly.

Minor

Single Netlify token assumed for all configured repos

config/config.go · main.go (--netlify-token-file)

Source: apullo777 (Kueue), 2026-07-27, PR comment.

The plugin takes one Netlify API token for the whole process; the per-repo config only maps site_id. Fine for the current single-consumer scope, but would need to become per-repository credentials if a second consumer (e.g. Kueue, using a separate Netlify project) can't share the same token. Caesarsage has explicitly deferred this until credential sharing is confirmed one way or the other.

Positive

What's done well

  • Clean separation of concerns: config, Netlify client, command parsing/decision logic, and server handler are in distinct packages with clear interfaces.
  • Interfaces at consumer: githubClient, netlifyClient, pluginConfigAgent are defined at the consumer site (server.go), following the Go idiom of "accept interfaces, return structs." Narrow and specific to what this plugin needs.
  • Pure decision logic: The Evaluate function is a pure function with no side effects, making it trivially testable. The decision/action pattern cleanly separates "what to do" from "doing it."
  • Trust gating reuses existing Prow infrastructure: trigger.TrustedUser and trigger.TrustedPullRequest are correctly reused rather than reimplemented, reducing drift risk.
  • Code block stripping: markdown.DropCodeBlock is correctly used before parsing commands, preventing commands in code examples from triggering actions.
  • Good test coverage: All layers are tested — config loading, Netlify client with mock HTTP transport, command parsing edge cases, decision logic for all state/command combinations, and server-level integration tests for trust gating and happy path. Tests are behavior-oriented, not implementation-detail-oriented.
  • Follows existing plugin conventions: Project structure, flag handling, health endpoint, and webhook validation all match the patterns in needs-rebase and other external plugins.
  • Safe defaults: Dry-run defaults to true, url.PathEscape for URL construction, context.WithTimeout for external API calls, strict YAML unmarshalling.
