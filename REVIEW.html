#577 updateconfig: Add ACL support for ConfigMap updates

Author: midnightconman Base: main Head: 63cbfe64 Reviewed: 2026-06-22T16:51:14Z Merged size/XL

Verdict

Request Changes (post-merge)

The core ACL feature is well-designed and well-tested. The blocking issue is a silent operational trap: config-bootstrapper will be unable to update any ConfigMap that has allowed_repos configured, with no warning. This warrants a follow-up fix since the PR is already merged.

What this PR does

  • Adds allowed_repos and denied_repos fields to ConfigMapSpec, letting admins control which orgs/repos can trigger ConfigMap updates via the config_updater plugin.
  • Implements deny-before-allow precedence: deny list is checked first, then allow list if present, then default-allow if no allow list exists.
  • Supports both org-level ("kubernetes") and repo-level ("kubernetes/test-infra") entries in both lists.
  • Adds checkconfig validation for the new fields (registered as a default warning) and updates generated config documentation.
  • Updates config-bootstrapper to pass an empty repo string, intended to bypass ACL checks for local-file bootstrapping.

Findings

Blocking

Blocking Config-bootstrapper silently blocked by allowed_repos

cmd/config-bootstrapper/main.go:149 + pkg/plugins/config.go:603-631

The config-bootstrapper passes "" as the repo argument to FilterChanges. When a ConfigMapSpec has allowed_repos configured, IsAllowed("") returns false because the empty string doesn't match any entry in the allow list. The bootstrapper silently skips that ConfigMap with only a Debug-level log.

The comment on line 148 says "ACL restrictions won't apply in this mode unless explicitly configured" — this is misleading. The natural reading is that the bootstrapper bypasses ACLs, but in fact adding allowed_repos to any ConfigMapSpec will break the bootstrapper for that entry.

This is an operational trap: an admin adds ACLs and the bootstrapper silently stops updating those ConfigMaps. There's no warning, no error — just stale data.

// Fix: add early return in IsAllowed
func (cm ConfigMapSpec) IsAllowed(repo string) bool {
    if repo == "" {
        return true
    }
    // ... rest of ACL logic
}

Should fix

Should fix Trailing-slash entries pass validation but silently never match

cmd/checkconfig/main.go:1552-1566

validateRepoName("kubernetes/") passes: SplitN yields ["kubernetes", ""], which satisfies all checks (len <= 2, s[0] != ""). At runtime, NewOrgRepo("kubernetes/") sets Org: "kubernetes", Repo: "", and the ACL check treats it as org-level. So "kubernetes/" silently behaves as "kubernetes" in deny lists, but in allow lists it could cause subtle mismatch if someone expects repo-level semantics.

// Add after the len(s) > 2 check:
if len(s) == 2 && s[1] == "" {
    return errors.New("repo name cannot be empty after org")
}
Should fix Non-deterministic test due to map iteration order

cmd/checkconfig/main_test.go — "multiple maps with errors" test case

The test asserts an exact error string containing errors from two map keys ("config.yaml" and "plugins.yaml"). Go map iteration is non-deterministic, so the error order can vary between runs. This test will flake.

Fix: assert each error substring independently, or sort the aggregated error list before comparing.

Nits

Nit ACL denials logged at Debug level only

pkg/plugins/updateconfig/updateconfig.go:314-320

ACL-denied updates are logged at Debug. Operators won't see these unless debug logging is enabled. During initial ACL rollout or when diagnosing "why did my ConfigMap stop updating", an Info or Warn-level message would surface the issue faster.

Nit Whitespace in ACL entries not validated

cmd/checkconfig/main.go:1552-1566

Entries like " kubernetes" or "kubernetes/ test-infra" pass validation but will never match at runtime. A strings.TrimSpace or explicit check would catch accidental whitespace from YAML copy-paste errors.

Nit Value receiver copies full struct on each call

pkg/plugins/config.go:603

IsAllowed uses a value receiver, copying the entire ConfigMapSpec on each call. The slice/map fields are reference types so data isn't deep-copied, but a pointer receiver would be cleaner and consistent with methods on larger structs.

Nit FilterChanges now has 6 positional parameters

pkg/plugins/updateconfig/updateconfig.go:284

Adding repo string as the 6th positional argument makes call sites harder to read. Not worth changing now, but if another parameter is added, an options struct would help.

Nit No test for trailing-slash entry behavior

Neither TestConfigMapSpecIsAllowed nor TestValidateConfigUpdaterACLs includes an entry like "kubernetes/". Adding a case would document the intended behavior (or catch the proposed validation fix).

Questions

Question Are there external consumers of FilterChanges?

pkg/plugins/updateconfig/updateconfig.go:284

Adding the repo parameter is a breaking change to an exported function. Both in-tree call sites are updated. External consumers (if any) will get a compile error. This is the right failure mode, but worth confirming whether any known downstream tools import this package directly.

Things I checked and was fine with

  • Deny-before-allow precedence order is the correct default-safe approach for a security control.
  • Thorough test coverage: 29 test cases across IsAllowed (14), FilterChangesWithACLs (7), and validateConfigUpdaterACLs (8).
  • Fully backwards-compatible: new fields use omitempty, zero-value defaults preserve existing "allow all" behavior. No config migration required.
  • Clean integration with existing infrastructure: reuses config.NewOrgRepo for org extraction, registers checkconfig validation as a default warning, updates generated config docs.
  • IsAllowed as a method on ConfigMapSpec is idiomatic Go and well-placed.
  • Rollback is safe: removing ACL fields from YAML and deploying the prior binary works without issues.

Open questions for the author

  • Was the config-bootstrapper behavior with allowed_repos intentional? If so, should there be a warning in the docs that the bootstrapper won't update ACL-protected ConfigMaps?
  • Are there known external consumers of FilterChanges that would be affected by the signature change?

Should tests Fix non-deterministic checkconfig ACL validation test

cmd/checkconfig/main_test.go — "multiple maps with errors" test case

In kubernetes-sigs/prow, following the merge of PR #577 ("updateconfig: Add ACL support
for ConfigMap updates", merge commit e821f0db6d3151be5dc9bf950cfc63446043e72f), there is
a flaky test in cmd/checkconfig/main_test.go.

The test case "multiple maps with errors" in TestValidateConfigUpdaterACLs asserts an
exact error string that contains errors from iterating a Go map (pcfg.ConfigUpdater.Maps
with keys "config.yaml" and "plugins.yaml"). Go map iteration order is non-deterministic,
so the two error substrings can appear in either order, making the test flake.

Fix this by changing the assertion approach. Instead of comparing the full aggregated
error string, assert that each expected error substring is present independently. For
example, check that the error string contains both
`config_updater.maps["config.yaml"].allowed_repos: org/repo cannot be empty` and
`config_updater.maps["plugins.yaml"].denied_repos: you cannot set a repo without an org`
as substrings, regardless of order. Alternatively, split the error string and sort before
comparing.

Keep the test's coverage intent intact — it should still verify that errors from multiple
map entries are all reported.

Acceptance criteria: go test ./cmd/checkconfig/... passes reliably (run it multiple times
to confirm no flake). The test still catches the same validation errors.

Out of scope: changing the validation logic itself, modifying other test cases, or any
functional changes.
Should validation Reject trailing-slash and whitespace entries in validateRepoName

cmd/checkconfig/main.go:1552-1566, cmd/checkconfig/main_test.go, pkg/plugins/config_test.go

In kubernetes-sigs/prow, following the merge of PR #577 ("updateconfig: Add ACL support
for ConfigMap updates", merge commit e821f0db6d3151be5dc9bf950cfc63446043e72f), the
validateRepoName function in cmd/checkconfig/main.go accepts entries that will silently
misbehave at runtime.

Two gaps:
1. Trailing-slash entries like "kubernetes/" pass validation (SplitN yields
   ["kubernetes", ""], which satisfies all current checks). At runtime, this silently
   behaves as an org-level entry, which is confusing.
2. Entries with leading/trailing whitespace like " kubernetes" or "kubernetes/ test-infra"
   pass validation but will never match anything at runtime, because IsAllowed does exact
   string comparison.

Fix this in validateRepoName (cmd/checkconfig/main.go):
1. After the existing `len(s) > 2` check, add: if len(s) == 2 && s[1] == "" {
   return errors.New("repo name cannot be empty after org") } — this catches
   trailing-slash entries.
2. Add a whitespace check: if strings.TrimSpace(repo) != repo {
   return errors.New("org/repo must not contain leading or trailing whitespace") } — put
   this near the top, before the split.

Then add test cases:
- In TestValidateConfigUpdaterACLs (cmd/checkconfig/main_test.go): add cases for
  "kubernetes/" in allowed_repos (expect error about empty repo after org) and
  " kubernetes" in denied_repos (expect error about whitespace).
- In TestConfigMapSpecIsAllowed (pkg/plugins/config_test.go): add a case for
  "kubernetes/" in AllowedRepos with repo "kubernetes/test-infra" to document runtime
  behavior (it would match via org, but the point is that checkconfig now rejects it
  before it gets to runtime).

Acceptance criteria: go test ./cmd/checkconfig/... and go test ./pkg/plugins/... pass.
validateRepoName rejects "kubernetes/", " kubernetes", and "kubernetes " with clear
error messages.

Out of scope: changing IsAllowed logic, normalizing inputs at runtime (e.g., trimming
whitespace in IsAllowed), or modifying any other validation functions.
