Verdict: request changes (recommend closing in favor of #656 + a fresh config-surface PR). A multi-perspective review (code quality, maintainability, deployment risk) converges: the fixup/amend detection is enabled by default and applies a Tide-blocking do-not-merge/* label with only an opt-out, which is too risky to ship as-is; the new config-surface change also reuses validateRepoDupes with a hardcoded, misleading "welcome" plugin error message. The maintainer already asked for this PR to be split into a behavior-only PR (gated, disabled by default — now #656) and a separate config-surface PR; the author agreed. The advisor synthesis recommends closing #641 outright rather than continuing to iterate on it.

What this PR does

  • Detects fixup!/amend! commits in a PR's history via a new subject-line regex, separate from the existing issue-closing-keyword check.
  • Applies a new do-not-merge/fixup-commits label and a dedicated comment when such commits are present; removes/prunes them when the commits disappear. Enabled by default for every repo running the plugin.
  • Introduces a new plugin configuration surface, plugins.InvalidCommitMsg (repos, disable_fixup_check), with org/repo-priority resolution via InvalidCommitMsgFor.
  • Adds config validation (validateInvalidCommitMsg) and plugs into the existing validateRepoDupes generic helper.
  • Leaves the existing issue-closing-keyword check's full-message matching behavior unchanged (an earlier revision had accidentally narrowed it to subject-only; that regression is fixed in this diff).

Findings

blockingvalidateRepoDupes emits misleading "welcome" plugin error

pkg/plugins/config.go:1598-1600, 1614-1621

if err := validateRepoDupes(c.InvalidCommitMsg); err != nil {
    return err
}
// validateRepoDupes error text: "The repo %q is duplicated in the 'welcome' plugin configuration."

Configuration.Validate() calls the shared validateRepoDupes, but that helper hardcodes plugin-name text in its error strings. A duplicate repos entry under invalid_commit_msg produces an error pointing at the wrong plugin (welcome) — actively misleading for anyone debugging a config validation failure. Untested for this new call site.

blockingFixup check ships enabled-by-default with no pre-rollout opt-out window

pkg/plugins/invalidcommitmsg/invalidcommitmsg.go:128-131

invalidCommitCfg := cfg.InvalidCommitMsgFor(org, repo)
checkFixup := !invalidCommitCfg.DisableFixupCheck

do-not-merge/fixup-commits uses the standard Prow/Tide merge-blocking label prefix. Because the check defaults to enabled (opt-out only), every repo already running this plugin starts auto-labeling and blocking in-flight PRs with fixup/amend commits the moment this ships, with no way to pre-stage the opt-out beforehand. This is the core reason the maintainer requested a split and gating (see #656, which makes it opt-in/disabled-by-default).

should-fixBehavior and config surface bundled in one PR

The org/repo config-resolution machinery (InvalidCommitMsg, InvalidCommitMsgFor, validateInvalidCommitMsg) is independently reviewable/testable/bisectable from the fixup-detection logic. Maintainer asked for a split; author agreed and opened #656 for the behavior-only half.

should-fixLabel/comment sync logic duplicated instead of shared

pkg/plugins/invalidcommitmsg/invalidcommitmsg.go:177-183, 213-227

if hasFixupCommitMsgLabel && len(fixupCommits) == 0 {
    ...
    cp.PruneComments(func(comment github.IssueComment) bool {
        return strings.Contains(comment.Body, fixupCommitMsgCommentPruneBody)
    })
}
...
if len(fixupCommits) != 0 {
    cp.PruneComments(func(comment github.IssueComment) bool {
        return strings.Contains(comment.Body, fixupCommitMsgCommentPruneBody)
    })

The fixup label add/remove/prune logic is a close copy of the existing invalid-commit-message logic, including pruning fixup comments in two separate branches. Not new dead weight, but doubles the surface area of an already-hard-to-reason-about idiom rather than factoring out a shared helper.

should-fixNo pre-creation path for the new label; silent AddLabel failures

pkg/plugins/invalidcommitmsg/invalidcommitmsg.go:194-198

if !hasFixupCommitMsgLabel && len(fixupCommits) != 0 {
    if err := gc.AddLabel(org, repo, number, fixupCommitMsgLabel); err != nil {
        log.WithError(err).Errorf("GitHub failed to add the following label: %s", fixupCommitMsgLabel)
    }
}

If a repo's label set is managed by a labels-sync tool that doesn't yet include do-not-merge/fixup-commits, AddLabel fails silently (logged only) — failures go unnoticed at scale.

pkg/plugins/config.go:1459-1477

"org/" or "/repo" pass validation despite being malformed, then silently never match at runtime.

Likely to trip golangci-lint's whitespace linter.

nitCopy-pasted "triggers" comment on InvalidCommitMsgFor

nitThree near-identical org/repo resolution functions, no shared generic helper

pkg/plugins/config.go (TriggerFor, DcoFor, InvalidCommitMsgFor)

InvalidCommitMsgFor is essentially a verbatim copy with only the receiver type changed, even though generic ListableRepos machinery already exists for the dupe-check side. Not this PR's debt to fix, but it adds a third copy.

nitstrings.Split allocates full line slice for first-line-only use

pkg/plugins/invalidcommitmsg/invalidcommitmsg.go:150

strings.Split(msg, "\n")[0] allocates a slice of all lines in a loop over allCommits; strings.SplitN(msg, "\n", 2)[0] avoids the extra work. Negligible in practice.

nitFixupCommitRegex doesn't require the space after "!"

pkg/plugins/invalidcommitmsg/invalidcommitmsg.go:82

^(fixup!|amend!) matches even without the trailing space git's --autosquash convention always produces. Low impact.

nitTest doesn't assert both labels added for a combined fixup+close-keyword commit

pkg/plugins/invalidcommitmsg/invalidcommitmsg_test.go:230-247

The "commit with fixup and close keyword" test case only asserts invalidCommitMsgLabel membership, not fixupCommitMsgLabel too, even though both should be added. A regression dropping the fixup label on combined commits wouldn't be caught.

Things I checked and was fine with

  • CloseIssueRegex still matches the full commit message (not subject-only); only the new FixupCommitRegex is subject-line-scoped. An earlier revision's regression here is fixed.
  • InvalidCommitMsgFor's two-pass repo-then-org priority resolution matches the existing TriggerFor/DcoFor convention.
  • &cfg taken from a for _, cfg := range loop is safe: go.mod requires Go 1.25 (Go 1.22+ per-iteration loop variable semantics).
  • getRepos() on InvalidCommitMsg correctly implements the ListableRepos interface used by validateRepoDupes, matching Approve/Welcome.
  • Config schema change is additive/backward-compatible (omitempty, new struct) — no parsing breakage for existing deployments.
  • checkFixup being false still allows stale fixup labels to be cleaned up (removal isn't gated by checkFixup) — correct when disable_fixup_check is turned on after the fact.
  • disable_fixup_check wired through and tested end-to-end (config → handle).
  • Test coverage of fixup-only, amend-only, disabled-check, and label-removal-on-resolution cases is solid.
