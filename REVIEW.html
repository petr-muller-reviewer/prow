Full-source re-review at af38ab180, re-deriving every claim from the code rather than from the earlier summary. No blocking findings. The fork logic is careful — the parentResult caching correctly avoids double-reporting a failed GetRepo, and the unvalidated parts[1] index is safe because the validation loop hard-returns first. Build and the cmd/peribolos + pkg/config/org suites pass, and YAML backward compatibility was confirmed empirically rather than argued. The substantive gap the earlier pass missed is the --dump path: it auto-populates fork:, so "opt-in via a new config key" holds only until an operator re-dumps, after which --fix-repos quietly starts reconciling forks. That is release-note material, not a merge blocker.

This review supersedes an earlier summary-derived pass that contained four factual errors; they are listed under Corrections.

What this PR does

  • Adds a fork: block to the peribolos org-config repos: surface (ForkConfig{From, DefaultBranchOnly}), reconciled by a new configureForks that runs before configureRepos.
  • Adds CreateForkInOrg to the GitHub client, passing the config key as GitHub's fork name parameter so fork naming is explicit rather than GitHub-selected.
  • Adds --fix-forks, defaulting to whatever --fix-repos is unless explicitly passed.
  • Extracts the GitHub-API-shaped fields of org.Repo into an embedded RepoMetadata struct — serialization-transparent, Go-source breaking.
  • Teaches --dump to emit fork: for any repo whose GitHub parent is set.

Findings

No blocking findings.

should fix--dump auto-populates fork:, silently widening what --fix-repos reconciles

cmd/peribolos/main.go:402-406

This is the mechanism by which fork reconciliation reaches operators who never opted in. Combined with --fix-forks inheriting from --fix-repos, a config regenerated by --dump after upgrading starts reconciling every fork in the org — one extra GetRepos plus one GetRepo per fork, and the hard-failure paths below become reachable. Behaviourally a no-op for a faithful dump, but "opt-in via the new config key" holds only until the next re-dump. Worth a release note.

// If repo is a fork, record the upstream
if full.Fork && full.Parent.FullName != "" {
    repoConfig.Fork = &org.ForkConfig{From: full.Parent.FullName}

should fixUpstream rename or transfer turns a previously-working config into a non-zero exit

cmd/peribolos/main.go:1342, :1465-1468

A dumped from: pins the upstream's FullName at dump time. If that upstream is later renamed or transferred, expectedUpstream stops matching Parent.FullName, checkExistingRepoConflict produces a conflict error, and the whole run exits non-zero. Pre-PR there was no fork tracking to disagree with reality. The error is accurate and actionable, so this is acceptable — but it is a new way for an untouched config to start failing.

return fmt.Errorf("repo %s exists as fork of %s, but config specifies %s",
    repoName, cachedResult.fullName, expectedUpstream)

should fixDuplicate-upstream validation hard-returns, making dump→apply non-idempotent

cmd/peribolos/main.go:1369-1371

Unlike the format errors just below it (which accumulate into an aggregate), this is a bare return nil, err that aborts all fork handling. An org holding two repos with the same GitHub parent — reachable by transferring a fork in, even if the fork API refuses a second fork — dumps to a config that peribolos then rejects outright. It fails loudly rather than corrupting anything, but peribolos --dump | peribolos --fix-repos should not be able to produce a config peribolos won't accept.

if existing, ok := upstreamToConfig[upstream]; ok {
    return nil, fmt.Errorf("multiple config entries (%s, %s) fork from the same upstream %s, only one fork per upstream is allowed per org", existing, repoName, repoCfg.Fork.From)
}

should fixFork error is dropped from the message when another subsystem fails first

cmd/peribolos/main.go:1009-1013, :1054-1056

forkErr is deliberately deferred so other subsystems still run, then returned at the end. But configureRepos, configureCollaborators and configureTeams all return directly on failure, discarding forkErr. Exit status is still non-zero so the stated guarantee holds, but the fork failure becomes invisible — the operator sees only the repos/teams error. Wrapping into an aggregate at each return would preserve both.

} else if err := configureRepos(opt, client, orgName, orgConfig, forkNames); err != nil {
    return fmt.Errorf("failed to configure %s repos: %w", orgName, err)
}

should fixNew user-facing config surface and flag ship with no documentation

site/content/en/docs/components/cli-tools/peribolos.md

The PR touches zero docs. --fix-forks's inheritance from --fix-repos is non-obvious behaviour documented only in the flag help string and the PR body. Mitigating: that page does not document the repos: surface at all today, so this matches an existing gap rather than creating a regression — but the inheritance semantics in particular will surprise operators.

nitEmpty-string return conflates dry-run with a nameless 202

cmd/peribolos/main.go:1480-1486, pkg/github/client.go:4598-4600

createdName == "" is the sentinel for "dry run, nothing created". A real non-dry 202 whose body lacks name would take the same branch, log dry-run: fork creation skipped, record a fork name that does not exist, and skip waitForFork. GitHub does return the repo object, so this is theoretical — but a bool return or an explicit dry check in the caller would remove the ambiguity.

if createdName == "" {
    repoLogger.Info("dry-run: fork creation skipped")
    forkNames[repoName] = repoName
    continue
}

Things I checked and was fine with

  • RepoMetadata embedding is serialization-transparent. Verified empirically, not by reasoning: a pre-PR config with flat description/private/default_branch/previously/on_create/collaborators parses through sigs.k8s.io/yaml, all fields promote, and re-marshals flat with no repometadata nesting key.
  • cmd/peribolos is the only in-tree importer of pkg/config/org.
  • parts[1] indexing in the second configureForks loop (main.go:1408-1410) is safe — the validation loop hard-returns on any malformed from before it is reached.
  • parentResult caching correctly avoids double-reporting: a failed GetRepo on the config-named repo is recorded once in the candidate loop, and checkExistingRepoConflict returns nil for that case (main.go:1338-1341).
  • append([]string{wantName}, wantRepo.Previously...) at main.go:1207 and :1209 allocate fresh backing arrays — no slice aliasing into config state.
  • Fork/rename mapping is threaded correctly: configureRepos uses actualName for the update to avoid spurious renames (main.go:1266-1269), and configureCollaborators remaps via forkNames (main.go:1522).
  • --fix-repos --fix-forks=false leaves fork-configured repos unmanaged rather than creating them as empty repos (main.go:1238-1241). Consistent with opting out.
  • waitForFork distinguishes 404 from other errors and surfaces the latter immediately (main.go:1320-1322) — ivankatliarchuk's March point, confirmed fixed.
  • Fork detection is not O(repos): one GetRepos plus at most two GetRepo per configured fork (main.go:1421-1424) — ivankatliarchuk's other point, confirmed fixed.
  • go build ./... succeeds; cmd/peribolos and pkg/config/org suites pass.

Corrections to the earlier pass

  1. "New fields fork_from, default_branch_only are omitempty pointers" — describes the pre-2479e7c74 shape. Current surface is nested fork: {from, default_branch_only}; ForkConfig.From is a plain string, not a pointer and not omitempty.
  2. "Config key as fork name … not visible in the current PR diff — may be in unpushed commits" — it is in the diff: main.go:1473 passes repoName to CreateForkInOrg, serialized as name at client.go:4602-4610.
  3. Release-note framing was presented as a missed repo convention; no such convention exists here.
  4. The independent risk scan did not examine the --dump path, which is where this feature actually reaches existing operators.
