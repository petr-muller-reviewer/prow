Verdict

Request changes

CI is currently red: pull-prow-verify-lint fails because this bump deprecates a method (model.LabelName.IsValid) that pkg/metrics/push.go:52 still calls, and staticcheck blocks on it. All other jobs (build, integration, unit tests, race detector) pass. On content alone both version bumps look safe — no CVEs, no breaking behavior hitting how Prow actually uses either library — but the PR cannot merge as-is and needs a follow-up commit fixing the deprecated call before this can be approved.

What this PR does

  • Dependabot-grouped bump of the "prometheus" dependency group: github.com/prometheus/client_golang v1.22.0 → v1.24.1 and github.com/prometheus/common v0.62.0 → v0.70.1, in both the main module and hack/tools.
  • Dep-only change — only go.mod/go.sum in . and hack/tools are touched; no project source code changed.
  • Pulls along a long tail of indirect version bumps via go mod tidy (golang.org/x/net, x/sync, x/text, x/crypto, x/mod, x/sys, x/term, x/tools, google.golang.org/protobuf, prometheus/procfs, klauspost/compress, go.yaml.in/yaml/v2) — all remain marked // indirect and none are imported directly by project code.

Findings

Blocking

pull-prow-verify-lint fails: staticcheck flags deprecated model.LabelName.IsValid

pkg/metrics/push.go:52

if !model.LabelName(ln).IsValid() {

prometheus/common v0.70.1 deprecates model.LabelName.IsValid() in favor of ValidationScheme.IsValidLabelName(). This is the only prometheus/common call site in the project, and staticcheck (SA1019) fails the pull-prow-verify-lint job on it — confirmed in the CI log, not a hypothetical from the changelog. Needs a follow-up commit switching to ValidationScheme.IsValidLabelName before this can merge.

Nit

Unrelated modernize lint findings bundled in the same failing check

cmd/checkconfig/main.go:1008, cmd/checkconfig/main.go:1545, cmd/deck/configured_jobs.go:83, cmd/deck/tide.go:193

org := strings.SplitN(repo, "/", 2)[0]

Four modernize (stringscut) findings suggesting strings.Split(...)[0] become strings.Cut(...) also show up in the same lint run, in files this PR doesn't touch — likely surfaced by a golangci-lint/Go toolchain version shift rather than the prometheus bump itself. They're bundled into the same failing check regardless and will need addressing (or suppressing) to get CI green.

Question

client_golang v1.24.1 is only 5 days old, with a 40-file blast radius

go.mod:50

Released 2026-07-24 (v1.24.0, the substantive release, is 2026-07-20 — 9 days old; v1.24.1 is a 1-commit bugfix on top fixing a promhttp nil-URL panic). Both are proper tags, not pseudo-versions. This is the standard metrics client imported in 40 files across nearly every component (deck, hook, tide, crier, ghproxy, gerrit, github client/ghmetrics, moonraker, sinker, plugins/updateconfig, bugzilla, jenkins, jira, pubsub). Nothing in the changelog looks risky — min Go bumped to 1.25 (already satisfied, repo is on 1.25.8), a name-validation default change that doesn't affect prow (no use of NameValidationScheme/LegacyValidation), new opt-in promhttp features, and defensive bugfixes — but the combination of "very fresh" + "touches everything" is worth a deliberate call rather than default merge.

Question

go.mod:52

Released 2026-07-22. Usage is light — single call site in pkg/metrics/push.go using only expfmt.NewEncoder/expfmt.NewFormat and model. The v0.66.0 breaking change (zero-value TextParser now panics, must use NewTextParser) doesn't apply since prow never constructs a TextParser. Lower-stakes than the client_golang bump, but same soak-time question applies.
