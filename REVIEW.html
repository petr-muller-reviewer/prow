Verdict

Request Changes

Same verdict, substantially different reasons. The relocation is a real improvement and I want to credit it: the check now sits behind a live client.Create instead of an informer-cache read, which is what my previous "this branch is dead code" blocker was asking for, and it targets a path that genuinely wedges. What remains is the timeout basis. At this new call site, gating on pj.Status.PendingTime is not merely imprecise — it is a behavioural regression. The !podExists branch exists to recreate a pod that a rescheduler deleted mid-flight; today a transient failure there retries under backoff, and after this change, for any job older than the pending timeout (10 minutes by default), the very first failure kills the job outright. That condition is trivially true for essentially every real CI job, so "enforce a timeout" becomes "never retry". Fix the clock reference and this is close.

What this PR does

  • Identifies a real stuck-forever path: isRequestError (reconciler.go:1138-1144) only matches 4xx APIStatus errors and defaults to code 500 for everything else, so a connection error from pod creation never takes the "Unprocessable pod" completion path — it is returned for requeue, forever, under controller-runtime backoff.
  • Adds a timeout check inside the !isRequestError(err) arm of the startPod failure handling: if PendingTime is set and r.clock.Since(PendingTime) >= r.maxPodPendingTimeout(pj), mark the job ErrorState/complete instead of returning the error.
  • Completed jobs fall through to the shared tail of syncPendingJob (JobURL, transition log, patch, cache barrier), so no completion logic is duplicated.
  • Keeps the maxPodPendingTimeout helper from the previous revision; drops the updateProwJobStatus helper, restoring that code inline.
  • Two new table-driven cases in TestSyncPendingJob, driven through clientWrapper.createError; the now-unused getError/GetErr plumbing is removed.

Findings

blockingTimeout gated on job age, not on how long pod creation has been failing

pkg/plank/reconciler.go:468

if !isRequestError(err) {
    if pj.Status.PendingTime != nil && r.clock.Since(pj.Status.PendingTime.Time) >= r.maxPodPendingTimeout(pj) {
        pj.SetComplete()
        pj.Status.State = prowv1.ErrorState

pj.Status.PendingTime is set exactly once, in syncTriggeredJob at reconciler.go:750-753, on the Triggered→Pending transition, and is never reset — those two sites (:468 and :753) are the only references in the file. It is the job's start time. Prow has no Running state distinct from PendingState (pkg/apis/prowjobs/v1/types.go:61-62), so Since(PendingTime) is total job age, not time spent failing to create a pod. For any job alive longer than PodPendingTimeout — 10 minutes by default (pkg/config/config.go:2513) — the condition is unconditionally true.

Consequence: this is a regression, not just an imprecision. The !podExists branch exists for a pod deleted manually or by a rescheduler mid-flight. Today a transient non-4xx failure on the recreate — an apiserver 500, a webhook timeout, or a getBuildID/tot failure (reconciler.go:867, also a non-request error) — returns an error and retries under backoff. After this change, for any job past the pending timeout, that single failure completes the job as ErrorState with zero retries. A three-hour job's pod gets rescheduled, one blip on the recreate, job dead.

Fix: gate on a duration that measures the failure, not the job. Either record a "pod creation first failed at" timestamp on the ProwJob status (set on failure, cleared on success), or require N consecutive failures. If neither is palatable, at minimum stop reusing pod_pending_timeout, whose name and existing use at reconciler.go:559 both mean "the pod never started". Please add a regression test: long-running job (PendingTime 3h ago) plus a single Create error must not error the job.

should fixJob can be errored while its pod is actually running, and the pod is not deleted

pkg/plank/reconciler.go:467-476, pkg/plank/reconciler.go:893-905

}); err != nil {
    return "", "", fmt.Errorf("failed waiting for new pod %s in cluster %s  appear in cache: %w", podName.String(), pj.ClusterAlias(), err)
}

startPod can return a non-request error after a successful Create: the post-create cache barrier times out if the informer lags more than 10 seconds. Previously that error was returned and the next reconcile found the pod via podExists and continued normally. Now, for any job past the pending timeout, the ProwJob is completed as ErrorState while the pod is live in the build cluster.

The pod then runs to completion with no reporting, and unlike every other completion path in this function (the PodRunning timeout calls deletePod at :622) nothing deletes it. Sinker eventually GCs pods whose ProwJob is complete, so it is not a permanent leak — but the job result is wrong and the cluster does the work anyway. Distinguishing "Create failed" from "Create succeeded, barrier timed out" inside startPod, or calling deletePod before completing, would close this.

should fixsyncTriggeredJob has the identical failure path and was left unchanged

pkg/plank/reconciler.go:737-741

id, pn, err = r.startPod(ctx, pj)
if err != nil {
    if !isRequestError(err) {
        return nil, fmt.Errorf("error starting pod: %w", err)
    }

syncTriggeredJob calls startPod and handles failure with the same shape, untouched by this PR. A job that has never reached PendingState has PendingTime == nil, so no timeout could apply there anyway — an unreachable build cluster still wedges triggered jobs indefinitely.

This is arguably the more common manifestation of the reported symptom: a job submitted while the cluster is down never leaves TriggeredState. The PR only rescues jobs that were already pending when the cluster went away. Either extend the fix (which needs a clock reference other than PendingTime — the same mechanism the blocking finding asks for would supply one) or say explicitly in the PR description that triggered jobs are out of scope, and why.

should fixUncovered stuck-forever paths remain from the previous review

pkg/plank/reconciler.go:604-615, pkg/plank/reconciler.go:820-822

if pod.Status.StartTime.IsZero() || time.Since(pod.Status.StartTime.Time) < maxPodRunning {
    // Pod is still running. Do nothing.
    return nil, nil
}

The previous pass traced three paths that wedge when a build cluster stops responding mid-flight. This push covers one (pod absent from cache → Create fails). Two remain:

  • Pending, pod last seen Running: Since(pod.Status.StartTime) < maxPodRunning (48h default, config.go:2517) → return nil, nil. No state change, no requeue, no error, no log — the job goes silent. This is the closest match to the PR body's five-day periodic-build-farm-canary-build06 example.
  • Aborted: syncAbortedJob's deletePod fails and the error returns before SetComplete, so it requeues forever.
  • Related: once PodRunningTimeout does elapse, deletePod at :622 fails and returns before the patch, so the computed AbortedState transition is discarded on every attempt.

Out of scope for this PR if that is deliberate — but the PR body claims to fix the canary incident, and the path it covers may not be the one that produced it. The logs settle it (see open questions).

should fixExpectError test case still asserts almost nothing

pkg/plank/controller_test.go:1814-1823

if (err != nil) != tc.ExpectError {
    ...
}
if err != nil {
    return
}

The assertion mismatch from the previous review is genuinely fixed — (err != nil) != tc.ExpectError now fails correctly when an expected error is missing. But the immediately following early return skips every subsequent assertion. For the "build cluster unreachable, pending timeout not yet exceeded" case, the declared ExpectedState: prowapi.PendingState and ExpectedNumPods: 0 are dead configuration — only "some error occurred" is verified, and an error from any unrelated path would pass.

For the error case, still assert tc.PJ.Status.State and tc.PJ.Complete() on the in-memory object (no patch happened) before returning — or drop the unused expectations, so the test does not imply coverage it lacks.

nitTerminalError from an unknown cluster alias is now absorbed by the timeout branch

pkg/plank/reconciler.go:467-476 vs pkg/plank/reconciler.go:885

startPod returns TerminalError(fmt.Errorf("unknown cluster alias %q", ...)) at :885. That is not an APIStatus error, so isRequestError is false and it now lands in the new branch. Open questions for the author

  • Still my highest priority, and still unanswered from the last pass: what do plank's logs actually say for the stuck canary (periodic-build-farm-canary-build06, the five-day example in the PR body)? If they show error starting pod for PJ ..., this PR now targets the right path and the review reduces to the findings above. If they show silence, or Reconciliation failed with terminal error, the covered path is not the incident's path. Nothing else can be settled without this.
  • Was the job-age reading of PendingTime deliberate? It cannot distinguish "pod never started" from "job has been running for hours", and at the new call site the latter is the common case.
  • Is losing retry on the pod-recreate path acceptable? Before this change a transient Create failure retried under backoff; after it, for any job past the pending timeout, the first failure is fatal. If that is not intended, the blocking finding's fix restores it.
  • Should triggered-but-not-yet-pending jobs be covered too, or is the TriggeredState wedge deliberately left for a follow-up?
  • Worth a distinct metric or log for "errored because pod creation failed against an unreachable cluster", to separate it from other ErrorState causes? It can fire across many jobs at once.
  • Should mid-flight unreachability get explicit handling at all — re-probing clusters that were healthy at startup, extending the existing interrupts.Terminate() recovery in kubernetes_cluster_clients.go:427-462 — rather than relying on each job's own timeout?
