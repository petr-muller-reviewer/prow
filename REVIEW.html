Verdict

Approve — good to merge as-is or with the two suggested improvements below.

Clean, well-tested change that adds a generic fallback from sparse checkout to full clone when the sparse clone fails. The runClone extraction is the right structural move, the retry orchestration in Run() is straightforward, and the tests cover both fallback and happy paths using real git repos. No critical issues, no deployment risk, no configuration or API surface changes. Two "should-fix" items are worth considering but neither is blocking. An open design question from droslean about permanent sparse checkout degradation visibility is noted but not blocking merge.

What this PR does

  • Extracts the inner clone logic from Run() into a new runClone() function returning a Record.
  • When a clone fails and sparse checkout was enabled, wipes the clone directory and retries with a full clone (no sparse checkout, no blobless filter).
  • Merges command history from both the failed sparse attempt and the successful full clone into a single Record for debugging.
  • Adds two integration tests (table-driven) covering the fallback path and the happy path, each using real git repos.

Findings

Should fix

record.Refs reflects fallback refs, not original request
pkg/pod-utils/clone/clone.go:75-88

After fallback, record = runClone(fullRefs, ...) overwrites record.Refs with fullRefs, which has SparseCheckoutFiles: nil. Any downstream consumer inspecting Record.Refs.SparseCheckoutFiles will not know sparse checkout was originally requested. The PR description explicitly calls out debugging visibility as a goal.

Fix: add record.Refs = refs after the fallback runClone call.

record = runClone(fullRefs, dir, gitUserName, gitUserEmail, cookiePath, env, user, token)
record.Commands = append(failedCommands, record.Commands...)
// add: record.Refs = refs
os.RemoveAll failure proceeds into doomed retry
pkg/pod-utils/clone/clone.go:81-83

If os.RemoveAll(cloneDir) fails (e.g. permission denied), the code logs a warning but proceeds to runClone into a dirty directory. The second attempt will almost certainly fail with a confusing, unrelated error that obscures the real problem. Consider returning the original failed record when cleanup fails. 

if err := os.RemoveAll(cloneDir); err != nil {
    logrus.WithError(err).Warn("Failed to clean up clone directory for fallback")
}
// proceeds unconditionally — consider returning original failed record here

Open design question

Silent permanent sparse checkout degradation
pkg/pod-utils/clone/clone.go:77-88

Raised by droslean (2026-05-25): If sparse checkout is permanently broken for a repo (e.g. an always-present submodule conflict), every clone attempt silently falls back to full clone. The fallback is now logged at Warn level (improved from Info), and logs are preserved in clone-log.txt in PJ artifacts (Prucek's response).

droslean's position: this makes the sparse checkout feature pointless in degraded cases with no operator signal. Prucek's position: failures are rare edge cases; Warn-level logging is sufficient. Open for assigned reviewers (cjwagner, stevekuznetsov): is Warn-in-clone-log adequate, or should permanent failures surface via a metric or ProwJob annotation?

Things I checked and was fine with

  • runClone extraction is clean; startTime in runClone does not shadow startTime in Run() (separate functions); duration accounting correctly moved to Run() caller
  • fullRefs := refs is a safe struct copy; nil-ing SparseCheckoutFiles correctly makes isSparseCheckoutSet return false
  • append(failedCommands, record.Commands...) is safe — failedCommands is a separate slice reference
  • Fallback only triggers when isSparseCheckoutSet(refs) is true AND record.Failed is true — no impact on non-sparse clones
  • Tests use real git repos and assert on behavioral outcomes; table-driven refactor is clean and addresses droslean's feedback
  • No configuration, API, CLI flag, or ProwJob spec changes — purely internal resilience improvement
  • No breaking changes, safe to roll back, zero upgrade friction for operators
  • Deployment risk is LOW: only observable change is previously-failing sparse jobs now succeed via full clone

Open questions for the author

  • Should record.Refs after a successful fallback reflect the original request (with SparseCheckoutFiles) or what was actually executed (without)? Debugging visibility argues for the original request.
  • Is warn-and-continue the right behavior when os.RemoveAll fails, or should the fallback be skipped entirely?
  • Is Warn-level logging in clone-log.txt sufficient operator visibility for silent permanent sparse checkout degradation, or does this need a metric or explicit ProwJob status annotation? (droslean's concern, 2026-05-25, unresolved)
