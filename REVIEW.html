Verdict

Request changes

The core feature (configurable exclusive label prefixes) is a reasonable, mostly-clean addition, but it ships with hardcoded default prefixes (priority/, lifecycle/, tracked/) that are applied unconditionally to every repo using the label plugin — a silent behavior change with no opt-in, no test coverage, and no mention in the PR description. That needs to be resolved before merge; the remaining issues (stale-snapshot conflict detection, a case-sensitivity mismatch, overlap with the existing lifecycle plugin) are smaller correctness/design gaps worth fixing but not independent blockers.

Confirmed by independent multi-perspective review (three parallel reviewers — code quality, maintainability, deployment risk — plus a synthesizing advisor pass): all three converged independently on the hardcoded-defaults issue as the primary blocker, and the deployment-risk reviewer separately rated it HIGH risk since priority/* is one of the plugin's always-active label categories, meaning ordinary /priority usage on any repo would trigger silent removals immediately upon upgrade with no rollback path for already-removed labels.

What this PR does

  • Adds ExclusiveLabelPrefixes []string to the plugins.Label config struct, merged in Label.mergeFrom.
  • In handleComment, after a label is successfully added, computes which existing issue labels share its prefix (from a configured list plus three hardcoded defaults) and queues them for removal.
  • Adds helper functions conflictingExclusiveLabels, uniqueExclusiveLabelPrefixes, exclusiveLabelPrefix, hasExclusiveLabelPrefix.
  • Adds a continue after a failed AddLabel call so conflict-removal isn't computed for labels that didn't actually get added.
  • Regenerates plugin-config-documented.yaml and adds one new table-driven test case.

Findings

BlockingHardcoded default prefixes change behavior for all existing installations

pkg/plugins/label/label.go:41 and pkg/plugins/label/label.go:206

defaultExclusiveLabelPrefixes = []string{"priority/", "lifecycle/", "tracked/"}
...
exclusiveLabelPrefixes := uniqueExclusiveLabelPrefixes(append(defaultExclusiveLabelPrefixes, config.ExclusiveLabelPrefixes...))

This unconditionally merges priority/, lifecycle/, and tracked/ into the exclusive set for every repo running the label plugin, even with exclusive_label_prefixes unset. That silently changes behavior for every existing upstream user, with no opt-in and no mention in the PR description. lifecycle/* labels are already managed by the separate lifecycle plugin with its own exclusivity handling, so this could conflict or double-remove. No test exercises this default path at all — the added test explicitly passes its own prefix list.

BlockingSilent fleet-wide behavior change: /priority now auto-removes existing labels with zero config change

pkg/plugins/label/label.go:41,206

defaultExclusiveLabelPrefixes = []string{"priority/", "lifecycle/", "tracked/"}

Since priority is one of the label plugin's always-active regex categories, any /priority X command on any repo running the label plugin starts silently removing that issue/PR's existing priority/* label the moment this ships — no operator opts in, no restart-time signal, and it's not documented as a default anywhere. This is a one-way change: rollback reverts the binary but does not restore labels already removed while the new logic was live. Independently rated HIGH risk by the deployment-risk reviewer.

Should fixDuplicates existing lifecycle plugin's own exclusivity logic for lifecycle/*

pkg/plugins/label/label.go:41 vs pkg/plugins/lifecycle/lifecycle.go

The separate lifecycle plugin already implements exclusivity for lifecycle/{active,frozen,stale,rotten} via its own /lifecycle command and exact-enum matching. This PR's default lifecycle/ prefix creates a second, divergent implementation of the same invariant (prefix-match vs exact-enum, different case-handling) — a likely source of future incident-debugging confusion.

QuestionWhere does the tracked/ default prefix come from?

pkg/plugins/label/label.go:41

tracked/ appears nowhere else in the codebase — no constant, no plugin, no docs, no mention in the PR description. It looks like it encodes one org's private labeling convention rather than a general-purpose default.

Should fixStale label snapshot misses conflicts within a single comment

pkg/plugins/label/label.go:378-394, 262

for _, labelToAdd := range labelsToAdd {
    ...
    if err := gc.AddLabel(org, repo, e.Number, labelToAdd); err != nil {
        ...
        continue
    }
    labelsToRemove = append(labelsToRemove, conflictingExclusiveLabels(issueLabels, labelToAdd, exclusiveLabelPrefixes)...)
}

conflictingExclusiveLabels is evaluated against issueLabels, fetched once before the add-loop runs and never updated as labels are added. If one comment adds two labels sharing an exclusive prefix, neither is flagged as conflicting with the other — both survive, breaking the "mutually exclusive" guarantee for that edge case.

Should fixCase-sensitive equality check inconsistent with rest of file

pkg/plugins/label/label.go:388

if existingLabel == labelToAdd || !hasExclusiveLabelPrefix(existingLabel, []string{matchingPrefix}) {
    continue
}

This uses a plain ==, while the rest of the codebase uses strings.EqualFold for label comparisons (see github.HasLabel). labelToAdd is already lowercased by the regex-extraction helpers, but issueLabels come straight from the GitHub API with arbitrary casing — a differently-cased duplicate of the just-added label would fail this equality check and could be queued for its own removal.

NitSingle-element slice allocation to reuse multi-prefix helper

pkg/plugins/label/label.go:388

!hasExclusiveLabelPrefix(existingLabel, []string{matchingPrefix})

Wraps one string in a slice per existing label just to call the multi-prefix helper. A direct prefix check would avoid the per-call allocation and read more directly.

NitAppend onto package-level slice is fragile

pkg/plugins/label/label.go:206

append(defaultExclusiveLabelPrefixes, config.ExclusiveLabelPrefixes...) appends onto a shared package var. Safe today only because len == cap forces reallocation; a future change that pre-allocates capacity on that var would introduce a data race across concurrent handleComment calls.

NitmergeFrom doesn't dedup ExclusiveLabelPrefixes

pkg/plugins/config.go:2385-2389

l.ExclusiveLabelPrefixes = append(l.ExclusiveLabelPrefixes, other.ExclusiveLabelPrefixes...)

Appends without dedup, unlike the runtime uniqueExclusiveLabelPrefixes dedup in label.go. Harmless since runtime dedup happens later, but inconsistent with other merge fields nearby.

NitNo validation that configured prefixes end in a separator

pkg/plugins/config.go:458-461, exclusiveLabelPrefix/hasExclusiveLabelPrefix

Prefixes are matched with plain strings.HasPrefix. A configured prefix missing the trailing / (e.g. track instead of tracked/) would also match unrelated labels like trackless/foo.

NitNo log line distinguishes exclusivity-triggered removal from explicit /remove-*

pkg/plugins/label/label.go:262-290

Labels queued via conflictingExclusiveLabels are merged into the same generic labelsToRemove path as explicit /remove-* commands, with no distinguishing log field — hurts incident debuggability ("why was this label removed?").

QuestionWas the added continue after failed AddLabel intentional?

pkg/plugins/label/label.go:258-262

if err := gc.AddLabel(org, repo, e.Number, labelToAdd); err != nil {
    log.WithError(err).WithField("label", labelToAdd).Error("GitHub failed to add the label")
    continue
}

Correct, welcome fix — skips computing conflict-removal when the add itself failed — but not called out in the PR description as an intentional behavior change alongside the new feature.

Things I checked and was fine with

  • Label.mergeFrom correctly appends ExclusiveLabelPrefixes (aside from the dedup nit above).
  • plugin-config-documented.yaml regenerated correctly for the new field.
  • Permission/restricted-label gating (canUserSetLabel) is unaffected — the new removal path goes through the same remove-loop with the same checks.
  • The added positive-path test correctly exercises configured-prefix removal end-to-end.
  • No security concerns — no new bypass of existing label permission checks; independently confirmed by deployment-risk review — removals still go through canUserSetLabel, so risk is purely behavioral/data-loss, not a permission bypass.
  • Config schema change is additive/omitempty-tagged; existing YAML/JSON configs continue to parse without error.

Open questions for the author

  • Why hardcode priority/, lifecycle/, tracked/ as always-on defaults rather than making this purely opt-in via exclusive_label_prefixes? This changes behavior for every existing repo using the label plugin without any config change on their part.
  • Have you considered the interaction with the separate lifecycle plugin's own exclusivity handling for lifecycle/* labels? Could the two conflict or double-remove?
  • Should conflictingExclusiveLabels use the running set of labels-added-so-far rather than the pre-comment snapshot, to catch conflicts between two labels added within the same comment?
  • Where does the tracked/ prefix convention come from — is it specific to one downstream user's setup rather than a general-purpose default?
  • If the hardcoded defaults are kept in some form, will there be a release note or migration announcement so operators can audit exposure before upgrading?
