Verdict

Approve with suggestions.

A small, well-scoped fix for a real Jira API quirk (incremental field rejection on 400 responses). The retry loop is clean and preserves all error paths correctly. Deployment risk is low — purely internal, no config/API changes, no callers outside the jira package. The main gaps are missing retry logging (flagged by all three review perspectives) and absent test coverage for CloneIssue. Neither blocks merge, but logging in particular would save real debugging time in production.

What this PR does

  • Wraps the CreateIssue call in CloneIssue with a for range 5 retry loop, replacing the old "try once, fix fields, retry once" pattern.
  • On each iteration, if CreateIssue returns a 400, calls unsetProblematicFields to remove the reported fields and loops again.
  • Non-400 errors and unsetProblematicFields failures still return immediately inside the loop.
  • After the loop, if err != nil catches exhaustion of all retries.
  • Net: +11 / -8 lines in a single file (pkg/jira/jira.go).

Findings

should-fix No retry logging (all 3 reviewers)

pkg/jira/jira.go:533-549

The retry loop silently removes fields and retries up to 5 times. No log trail shows which fields were removed or how many retries occurred. Each retry mutates the issue by deleting fields — a side effect that should leave a trace. A logrus line per iteration with the attempt number and removed field names would significantly improve production debuggability.

for range 5 {
    createdIssue, err = jc.CreateIssue(childIssue)
    if err == nil {
        break
    }
    ...
    childIssue, newErr = unsetProblematicFields(childIssue, JiraErrorBody(err))

should-fix No test coverage for CloneIssue (2 reviewers)

pkg/jira/jira.go:513-574

Zero tests for CloneIssue exist in jira_test.go. Pre-existing debt, but the new retry loop introduces a non-trivial state machine (success on first try, success after N retries, exhaustion of retries, non-400 error, unsetProblematicFields failure) that warrants at least one table-driven test with a fake Client returning different 400 errors on successive calls.

nit Wasted work on final iteration

pkg/jira/jira.go:533-549

On the 5th (final) iteration, if CreateIssue returns a 400 and unsetProblematicFields succeeds, the corrected issue is never retried — the loop ends and the error is returned. The last unsetProblematicFields call does JSON marshal/unmarshal work that is thrown away. Not a correctness bug (the function correctly returns the error), but wasteful. Could guard the unset call with a check that it's not the last iteration, or use range 6.

question No-progress retry scenario

pkg/jira/jira.go:533-549

If Jira returns a 400 with an empty Errors map or fields not present in the issue, unsetProblematicFields succeeds but changes nothing. The loop resubmits the identical payload up to 5 times. Pre-existing issue (single retry also failed the same way), but the loop amplifies it from 2 to 5 wasted API calls. A check that processedResponse.Errors is non-empty before retrying would guard against this.

Things I checked and was fine with

  • for range 5 is idiomatic Go 1.22+ — Prow targets recent Go.
  • err variable scoping: declared on line 516 via data, err := ..., reused via assignment (not :=) in the loop — correct.
  • Early-return paths preserved inside the loop: non-400 errors and unsetProblematicFields failures return immediately.
  • Post-loop if err != nil correctly catches retry exhaustion.
  • unsetProblematicFields correctly deletes reported fields from the issue map and strips null customfields.
  • No configuration, API, or interface changes — purely internal implementation.
  • No callers of CloneIssue outside the jira package — minimal blast radius.
  • Deployment risk is LOW: no config migration, no ordering dependencies, safe to roll back, fully backwards-compatible.

Open questions for the author

  • Should we add a log line when retrying, including the attempt number and which fields were unset? Would save significant debugging time for Jira field configuration issues.
  • Is there a known upper bound on how many distinct problematic fields Jira reports across successive attempts? Is the choice of 5 retries based on observed behavior?
  • Should the loop guard against the no-progress case where unsetProblematicFields removes zero fields?
