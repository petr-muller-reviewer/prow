Verdict: Approve

Combines a direct code review with a three-perspective maintainer review (code quality, maintainability, deployment risk) plus a synthesized advisor recommendation of APPROVE_WITH_SUGGESTIONS. The exclusion mechanism is correctly wired to the actual error-wrapping chain used by tryMerge/mergePRs, is properly synchronized against the real concurrent sync-loop pattern, and is covered by genuine end-to-end regression tests. Two gaps — the unfiltered batch-merge path and unbounded-but-slow exclusion-map growth — were independently flagged by multiple reviewers and are worth tracking as explicit follow-ups, but neither is a correctness or safety defect that should block merge.

What this PR does

  • Fixes #673: takeAction() deterministically re-picks the lowest-numbered PR from successes every cycle; if it fails with UnmergablePRError (e.g. branch protection needs more approvals), it blocked the whole merge queue forever.
  • Adds syncController.mergeExclusions map[string]int keyed by org/repo#number@sha, with mutex-guarded excludeFromMerge/isExcludedFromMerge.
  • isUnmergableError() unwraps *mergeFailure → mergeErr.err → fmt.Errorf-wrapped github.UnmergablePRError via errors.As.
  • takeAction() filters successes through isExcludedFromMerge before pickHighestPriorityPR, and records an exclusion when mergePRs returns an unmergeable error.
  • SHA-scoped key means a new push (new head SHA) auto-clears the exclusion without waiting for it to age out.
Since previous review: the author pushed a second commit (d6d08d0b2) addressing both should-fix findings below.
  • Extracted the exclusion filter into filterExcludedFromMerge() and applied it to the batch path too (pickBatch, before candidates are considered), plus added excludeUnmergablePRsFromBatch() which inspects a failed batch merge's per-PR errors and excludes only the individual PR(s) that came back UnmergablePRError, leaving batch-mates alone.
  • Replaced the wall-clock TTL (map[string]time.Time, 5-minute mergeExclusionTTL) with a sync-cycle counter (map[string]int, mergeExclusionSyncs = 3) aged by a new ageMergeExclusions(), called unconditionally once per Sync(). Since every entry is decremented (and deleted at zero) every cycle regardless of lookup, this also closes the unbounded-growth gap for abandoned/closed PRs.
  • Added TestExcludeFromMergeReplacesPriorSHA, TestTakeActionExcludesPRThatFailsInBatch, TestPickBatchExcludesMergeExcludedPR; renamed TestMergeExclusionExpiry → TestMergeExclusionAging.

Findings

nitpkg/tide/tide.go:99-105, 536-550

excludeFromMerge will panic on a nil mergeExclusions map. The field is only initialized in newSyncController. Several existing tests build &syncController{...} literals directly without setting it; none currently trigger the write path, so there's no live bug today, but this is a latent footgun for future test additions. isExcludedFromMerge's read is nil-safe already.

mergeExclusions   map[string]int
mergeExclusionsMu sync.Mutex

nitpkg/tide/tide.go:1649 vs 1663

Per-cycle skip is logged at Debug while the original exclusion is Warning. An operator investigating a stuck PR days after the original Warning scrolled out of retention has no way to see why it's still being skipped, since Debug logging is usually off in production. Promoting the skip log to Info would help incident debugging without much added volume.

sp.log.WithFields(pr.logFields()).Debug("Skipping PR temporarily excluded from merging due to recent merge failure.")

nitpkg/tide/tide.go:570-586

isUnmergableError duplicates knowledge of mergeFailure's internal shape. It iterates mf.errs and recurses — structural knowledge that also lives in mergeFailure.historyMessage()/operatorError(). A mergeFailure.underlyingErrors() []error helper would reduce duplication. Not urgent.

question

Should mergeExclusionSyncs (3 cycles, hardcoded) be configurable? Raised by the deployment-risk pass, originally against the 5-minute TTL — the concern carries over to the new sync-cycle counter. For large multi-tenant installations, a branch-protection misconfiguration can take a human longer than a few sync cycles to notice/fix, causing the PR to flap in and out of the queue with repeated Warning logs. A Tide config knob and/or a tide_merge_exclusions_active metric would give operators visibility without a code change to tune. The switch from wall-clock to cycle-count makes the exclusion window's real-world duration depend on the configured sync period, worth calling out in docs if not made configurable.

Resolved

Fixed in d6d08d0b2: takeAction's batch-merge branch now calls the new excludeUnmergablePRsFromBatch() on failure, excluding only the PR(s) that failed with UnmergablePRError — batch-mates that merged fine are untouched. pickBatch also now runs candidates through filterExcludedFromMerge() before batch selection. Covered by TestTakeActionExcludesPRThatFailsInBatch and TestPickBatchExcludesMergeExcludedPR.

was should-fix

Exclusion map entries for abandoned PRs were never cleaned up. Fixed in d6d08d0b2, as a side effect of switching to a sync-cycle counter: ageMergeExclusions() is now called unconditionally once per Sync(), decrementing (and deleting at zero) every entry regardless of whether it's looked up again. Covered by TestMergeExclusionAging (renamed from TestMergeExclusionExpiry).

Things I checked and was fine with

  • Traced the full error-unwrap chain end-to-end: tryMerge() wraps github.UnmergablePRError as fmt.Errorf("PR is unmergable...: %w", err) → GitHubProvider.mergePRs() wraps into &mergeFailure{errs: []mergeErr{...}} → isUnmergableError() type-asserts *mergeFailure, recurses into me.err, falls back to errors.As. Matches the real runtime error shape.
  • takeAction only calls mergePRs with a single-element slice on the non-batch path, so mergeFailure.errs always has exactly one entry there — no ambiguity about which PR triggered the exclusion.
  • Exclusion set/check both key off pr.HeadRefOID consistently.
  • mergeExclusionsMu is the correct primitive: syncSubpool runs concurrently across org/repo/branch subpools via goroutines, so the shared map genuinely needs locking; both accessors take/release it around the full read-modify-write sequence.
  • New tests (TestTakeActionSkipsExcludedPRs, TestIsUnmergableError, TestMergeExclusionAging, TestExcludeFromMergeReplacesPriorSHA, TestTakeActionExcludesPRThatFailsInBatch, TestPickBatchExcludesMergeExcludedPR) are structurally consistent with existing test helpers; argument counts/types match current signatures. TestTakeActionSkipsExcludedPRs and TestTakeActionExcludesPRThatFailsInBatch are genuine end-to-end regression tests (single-PR and batch paths respectively), not unit tests of map internals.
  • isUnmergableError correctly returns false for UnauthorizedToPushError and generic errors — not overly broad.
  • Feature is GitHub-only (Gerrit provider untouched); consistent with the PR's stated scope.
  • No config/API/schema changes; drop-in, safely revertible (all state is in-memory, lost on restart).
  • Could not run go test ./pkg/tide/... in this environment (no go binary available) — relied on static tracing of signatures/control flow instead of executing the suite.
