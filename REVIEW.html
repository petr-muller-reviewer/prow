REQUEST CHANGES

The core resolution logic is well-designed and well-tested, and the previous round's biggest issue (silent global activation via empty repos) is fixed. But a 3-perspective maintainer review converged, independently, on the same conclusion: the generated plugin-config-documented.yaml now documents disproven semantics, and this redesign introduces new silent, security-relevant trust-widening behavior on upgrade — repo-level configs merging instead of shadowing, previously-inert Repos: ["*"] entries becoming live global grants, and no scope validation preventing a supplemental config from self-escalating to instance-wide trust. Deployment risk is rated HIGH.

What this PR does

  • Replaces TrustedApps []string on Trigger with a structured TrustedApp type (name, untrusted, locked); custom UnmarshalJSON keeps legacy string lists parsing, including mixed arrays.
  • Rewrites TriggerFor as a single pass that both picks the most specific trigger (repo > org > defaults, first match wins) and accumulates trusted apps at global (Repos: ["*"]), org, and repo levels.
  • Adds resolveTrustedApps: lower levels override upper ones per app unless the upper level set locked, and same-level duplicates can no longer clobber an already-locked entry. Repo level can never lock. The flat resolved list is stored in unexported resolvedTrustedApps and read via GetTrustedApps().
  • Migrates all five call sites (generic-comment.go, pull-request.go, verify-owners.go, welcome.go, retitle.go) to the accessor.
  • Adds ValidateLockedTrustedApps() wired into checkconfig as the optional validate-locked-trusted-apps warning, flagging lower-level entries that mention apps locked above them.

blocking Repo-level trigger still silently merges with org/global trust instead of shadowing

pkg/plugins/config.go:1134-1174 — TriggerFor

Unaddressed from previous review. A repo-level trigger that previously fully shadowed its org's trusted_apps (old code returned the first matching trigger outright) now has its trust list merged with org/global apps instead. An existing repo config that deliberately scoped a narrow trusted-apps list now silently inherits every org/global app too, with no operator-facing signal. The deployment-risk perspective rates this HIGH severity — it silently widens automatic-CI-trust on upgrade. Needs a migration callout, a checkconfig signal, or an explicit way to opt out of inheritance.

deployment risk: HIGH
blocking Repos: ["*"] flips previously-inert entries into live global grants

pkg/plugins/config.go:1140-1163 — TriggerFor switch

Pre-PR, no Repos value — including a literal "*" string — ever matched the old lookup (sets.NewString(trigger.Repos...).Has(fullName)/.Has(org)), so any existing config with "*" in a Repos list (copy-paste, template placeholder, accidental leftover) was a harmless no-op. Post-PR, repos.Has("*") makes that same entry an active global rule merged into every org and repo instance-wide — activating purely as a side effect of upgrading the binary, no config change, no warning, no error.

deployment risk: HIGH (primary concern)
blocking Supplemental/per-repo config aggregation has no scope validation

pkg/plugins/config.go:2459 — mergeFrom

mergeFrom appends a supplemental config's Triggers directly onto c.Triggers with no validation that Repos values stay scoped to the org/repo that owns that supplemental file. This aggregation mechanism predates the PR, but pre-PR the worst a careless supplemental entry could do was claim trust for the specific org/repo string it listed. Post-PR, the same mechanism lets any supplemental config (e.g. a per-org self-service plugin-config file, a common decentralized-config pattern) declare Repos: ["*"] and grant its chosen app global, instance-wide trust — a materially larger escalation surface introduced by this PR.

should fix Global/org/repo classification logic reimplemented independently in three places

pkg/plugins/config.go — TriggerFor (~1143-1160), validateTrigger (~1646), ValidateLockedTrustedApps (~1697-1758)

The rule for what counts as global (Repos contains "*") vs. org (no slash) vs. repo (has slash) is implemented independently three times, with slightly different mechanics each time (a sets.Set lookup, a raw sets.New[string](...).Has("*") call, and manual r == "*"/strings.Contains(r, "/")/strings.SplitN string logic). If the classification rule ever changes, all three sites need to be kept in sync by hand with no shared helper enforcing it.

code qualitymaintainability
should fix Same-level conflicting unlocked entries resolve by iteration order, not content

pkg/plugins/config.go:1185-1226 — resolveTrustedApps

When two triggers match the same level (e.g. two global Repos: ["*"] blocks, or two org-level blocks for the same org) with conflicting untrusted values for the same app and neither is locked, the last one encountered in c.Triggers iteration order wins via plain map overwrite. Reordering the triggers: list (config generator, alphabetical re-sort, supplemental-dir concatenation order) can silently flip which value takes effect with zero change to the actual trust values.

should fix resolvedTrustedApps is hidden derived state requiring a cmpopts workaround

pkg/plugins/config.go:599-603 (GetTrustedApps), pkg/plugins/config.go:2464 (mergeFrom)

Trigger gained an unexported field populated only as a side effect of TriggerFor; any Trigger value constructed another way silently returns "no apps trusted" via GetTrustedApps(), indistinguishable from a real empty-trust config. This forced cmpopts.IgnoreUnexported(Trigger{}) into both production mergeFrom code and TestMergeFrom — the hidden state leaked into diffing/merging logic project-wide. A plain value-returning resolution function (or a distinct ResolvedTrigger type) would avoid derived state living inside the config struct.

question Repos: ["*", "someorg"] collapses entirely to global

pkg/plugins/config.go:1143-1160 — TriggerFor switch

The switch checks repos.Has("*") first, so a trigger mixing "*" with a specific org/repo name is classified purely as global for bucket selection; the org/repo-specific name never picks the org/repo match. Compounds the mixed-repos question below. Likely a non-issue in practice, but worth a doc note or a validateTrigger warning.

question Mixed repos lists get level-classified per lookup

pkg/plugins/config.go:1145-1163 — TriggerFor switch

A trigger with Repos: ["myorg", "myorg/myrepo"] counts as repo-level for myorg/myrepo (the repo case wins in the switch, so its locked is dropped there) but org-level for sibling repos. Surprising classification; consider documenting it or warning on mixed org+repo lists.

question GetTrustedApps() returns nil without TriggerFor

pkg/plugins/config.go:599-603

resolvedTrustedApps is only populated by TriggerFor; a directly constructed Trigger returns nil even with TrustedApps set. It fails closed (no apps trusted) — the correct security default, so low risk — but a doc comment on the TrustedApps field warning against reading it directly would help future callers. See also the should-fix finding above on the hidden-state design itself.

question DCO plugin's TrustedApps []string may confuse readers

pkg/plugins/config.go:897, pkg/plugins/dco/dco.go:301

DCO has its own flat TrustedApps []string, unrelated to the trigger type; config.TrustedApps in dco.go:301 looks like a missed migration at a glance. A clarifying comment on the DCO field would help. Whether DCO should adopt the hierarchical type is separate-PR scope.

question Adopting object-form trusted_apps is a one-way street for binary rollback

pkg/plugins/config.go — TrustedApps.UnmarshalJSON

Once a config is edited to use the new {name, untrusted, locked} object form (even for a single entry), it can no longer be loaded by a pre-PR Prow binary — only the reverse (legacy strings loaded by the new binary) is supported. Worth calling out explicitly in the PR description/changelog as an operational rollback caveat.
