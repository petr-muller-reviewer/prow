Verdict

Request changes. This PR was reviewed twice — a direct code review, and a three-perspective maintainer review (code quality, maintainability, deployment risk) with advisor synthesis. All four independent passes converge on the same primary defect: the channel-fanout loop in notifyOnCLAIfMerged returns on the first Slack post error, silently dropping delivery to remaining configured channels. A second should-fix item (message misattributes the merge to the PR author rather than the merger) was raised by the code-quality pass. No reviewer found a correctness bug or a deployment-blocking risk — the rest are duplication/observability/doc-parity nits. The PR is tagged [WIP]/do-not-merge/work-in-progress, so further changes may already be planned.

What this PR does

  • Adds plugins.CLAAlert config: a list of {Repos, Channels} entries supporting both org/repo and bare org scoping.
  • Registers a new PullRequestEvent handler in the slackevents plugin (previously only push and comment events were handled).
  • On PR merge, checks for the cncf-cla: no label directly from the event payload and posts a Slack alert to all channels configured for that repo/org.
  • Updates help provider docs/yaml snippet to document the new config shape.
  • Adds a 9-case table-driven test (TestNotifyOnCLAIfMerged) covering match/no-match, action/merge guards, and repo-vs-org precedence.

Findings

Should fix

should-fixChannel fanout short-circuits on first error

pkg/plugins/slackevents/slackevents.go:270-278 (in notifyOnCLAIfMerged)
for _, ch := range ca.Channels {
    if err := pc.SlackClient.WriteMessage(msg, ch); err != nil {
        return fmt.Errorf("failed to post CLA alert to %s: %w", ch, err)
    }
}

The loop returns immediately when WriteMessage errors on one channel, so later channels never get notified. Flagged independently by all three maintainer-review perspectives (code quality, maintainability, deployment risk) plus the direct review — the highest-confidence finding in this PR. notifyOnSlackIfManualMerge elsewhere in the same file uses utilerrors.NewAggregate to attempt every channel and collect errors; this new code should follow that pattern, especially since CLA-compliance alerts benefit from best-effort delivery.

should-fixAlert message misattributes the merge to the PR author

pkg/plugins/slackevents/slackevents.go:262-269 (in notifyOnCLAIfMerged)
msg := fmt.Sprintf(
    "*Alert:* PR #%d merged with %q label by %s — %s",
    pre.Number,
    labels.ClaNo,
    pre.PullRequest.User.Login,
    pre.PullRequest.HTMLURL,
)

Uses PullRequest.User.Login, which is the PR author, not who merged it. This misleads readers into thinking %s performed the merge. Consider PullRequest.MergedBy.Login if available, or reword to clarify it's the author.

Nits

nitgetCLAAlert duplicates getMergeWarning's matching logic

pkg/plugins/slackevents/slackevents.go:281-291 (getCLAAlert)

Byte-for-byte structural duplicate of the existing getMergeWarning two-pass (exact org/repo match, then org-level fallback) logic, using sets.NewString(...).Has(...) rebuilt per call. Two copies now have to be kept in sync if matching semantics change; consider a shared helper.

nitNo observability for sent/suppressed CLA alerts

pkg/plugins/slackevents/slackevents.go:246-279 (notifyOnCLAIfMerged)

No log line marks "CLA alert sent" or "suppressed (no matching config)". For a compliance-sensitive alert, this makes production debugging of "why didn't we get notified" harder than necessary.

nitPer-repo help text doesn't mention CLA alert config

pkg/plugins/slackevents/slackevents.go:63-77 (helpProvider)

configInfo[repo.String()] documents merge-warning status per repo but says nothing about whether a repo has CLAAlerts configured, unlike the parallel MergeWarning handling. Doc parity gap, not functional.

Questions

questionMissing test for WriteMessage error path

pkg/plugins/slackevents/slackevents_test.go:376-560 (TestNotifyOnCLAIfMerged)

9 cases cover matching/non-matching/precedence logic well, but none exercise a failing WriteMessage call — exactly the path with the short-circuit bug above. Add once fanout error handling is fixed.

questionCase-sensitive org/repo matching in getCLAAlert

pkg/plugins/slackevents/slackevents.go:281-291 (getCLAAlert)

sets.NewString(a.Repos...).Has(repo.String()) is case-sensitive; a misconfigured Repos entry (wrong case) silently never matches and never alerts. Matches existing repo-matching conventions elsewhere in Prow, but easy to get wrong and fails silently.

questionNo validation that CLAAlert.Channels is non-empty

pkg/plugins/config.go:855-862 (CLAAlert struct)

A CLAAlert entry with Repos set but empty Channels would silently match and no-op. Consider config-load-time validation for parity with other Slack config, if such validation exists for MergeWarnings.

Things I checked and was fine with

  • Merge/action guard (Action != Closed || !Merged) is correct and tested.
  • Repo-exact-match-before-org-fallback precedence in getCLAAlert is correct and tested (exact repo match takes precedence over org-level case).
  • Label matching iterates all labels and matches on labels.ClaNo, tested with the label among others; break after first match prevents a double-send even if a duplicate label were ever present in the payload.
  • Reading labels directly from PullRequestEvent (no extra GitHub API call) is efficient and documented as merge-strategy independent.
  • helpProvider yaml snippet and doc <ol> update render correctly; plugins.RegisterPullRequestHandler registration is new and doesn't conflict with existing push/comment handler registrations.
  • New CLAAlerts field is omitempty and purely additive — no breaking change to existing configs, no new Slack scopes/tokens required, rollback is a plain binary revert.
  • FakeClient used in new tests is a pre-existing test helper, not duplicated.

Open questions for the author

  • Should a failed WriteMessage on one channel still allow other configured channels to receive the CLA alert (aggregate errors) rather than aborting the loop?
  • Should the alert message use MergedBy.Login instead of User.Login, or is the author intentionally the signal wanted here?
  • Is silent no-op on case-mismatched Repos entries or empty Channels in CLAAlert config acceptable, or should config validation catch this?
  • Given this is marked WIP, is there a design decision still pending (e.g., dedup on redelivered webhook events, shared repo-matching helper, or per-repo CLA-alert status in docs) that would change the shape of this review?
