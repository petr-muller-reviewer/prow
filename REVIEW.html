Verdict

Request changes

The Tekton preset-merging design itself is sound and mirrors the existing pod-preset mechanism, but two blocking issues need to be fixed first: a unit-test file that Go silently never runs (confirmed by three independent review passes — code quality, maintainability, and deployment risk all converged on this), and a stale/unrebased branch dragging in ~52k unrelated lines (a controller-gen CRD regeneration) plus scattered unrelated refactors. A handful of smaller correctness and API-clarity nits round out the review.

What this PR does

  • Extends the existing Preset mechanism (currently PodSpec-only) with Tekton PipelineRunSpec fields: tekton_params, tekton_workspaces, tekton_service_account, tekton_timeout, tekton_task_run_template.
  • Adds mergeTektonPreset/ResolveTektonPresets mirroring the existing PodSpec preset logic, with label matching and duplicate-field conflict detection.
  • Wires resolution into defaultPresubmits/defaultPostsubmits/DefaultPeriodic for jobs with a PipelineRunSpec.
  • Adds deepcopy support for the new Preset fields.
  • Adds unit tests and an integration test verifying end-to-end propagation into created PipelineRuns.

Findings

Blocking

BlockingUnit test file is misnamed and never runs

pkg/config/jobs_test_tekton_presets.go

Confirmed independently by all three reviewer perspectives (code quality, maintainability, deployment risk).

File declares package config, imports "testing", and defines TestResolveTektonPresets/TestMergeTektonPreset (287 lines, 15 test cases) — but the filename ends in _presets.go, not _test.go. Go's toolchain only excludes files ending exactly in _test.go from normal builds, so this file compiles into every production binary that imports pkg/config (hook, deck, sinker, prow-controller-manager, etc.), permanently pulling testing into production, and go test ./pkg/config/... never discovers or runs these tests. CI reports green while this unit-test coverage silently never executes.

Fix: rename to jobs_tekton_presets_test.go (or fold into jobs_test.go) and confirm go test ./pkg/config/... picks it up.

Should fixTimeout conflict check misses explicit zero-duration timeouts

pkg/config/jobs.go:151-159 (mergeTektonPreset)

Conflict is only flagged when Timeouts.Pipeline != nil && Duration != 0. A job that explicitly sets Duration: 0 (meaning "no timeout") would have a preset's timeout silently applied instead of erroring, unlike every other field in this function.

if pipelineRunSpec.Timeouts.Pipeline != nil && pipelineRunSpec.Timeouts.Pipeline.Duration != 0 {
    return fmt.Errorf("timeout conflict: both preset and spec define timeout")
}
pipelineRunSpec.Timeouts.Pipeline = preset.TektonTimeout.DeepCopy()

Nits

NitmergeTektonPreset conflict semantics undocumented and asymmetric

pkg/config/jobs.go:112-170

Service-account/timeout/pod-template use "skip if already equal, error only if different" semantics, while params/workspaces always hard-error on any duplicate. Nothing comments on why this split exists — a future contributor adding a new Tekton field has no documented rule to follow.

Things I checked and was fine with

  • mergeTektonPreset label-matching, duplicate-param/workspace/service-account conflict detection — correct, mirrors mergePreset.
  • Deepcopy additions for new Preset fields — correctly generated.
  • Unit test design (label match/mismatch, duplicate detection, multi-preset, default label-less preset) is good in principle — undermined by the file-naming bug above.
  • Integration test (correctly named *_test.go) verifies preset fields propagate into created PipelineRun objects, including merging preset params with job-specific params.
  • Config compatibility: all new Preset fields are omitempty; existing presets.yaml files parse and behave unchanged; new merge path only fires for jobs that already opt into PipelineRunSpec.
  • No security concerns — merges already-trusted Prow config data, same trust boundary as existing PodSpec presets.

Open questions for the author
