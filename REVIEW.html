Findings

Should fixListCheckRuns called unconditionally in buildAll, unlike the override plugin's own gating

pkg/plugins/trigger/pull-request.go:411-420

The (now-removed) override plugin abort logic gated its own ListCheckRuns call behind oc.UsesAppAuth(). buildAll's call remains unconditional, adding an extra GitHub API call to every PR-opened/reopened/LGTM/ok-to-test-label event even for installations that don't use GitHub Apps/Checks (where it always returns empty). Not harmful, but avoidable rate-limit cost at scale. 

checkRunList, err := c.GitHubClient.ListCheckRuns(org, repo, pr.Head.SHA)
if err != nil {
    c.Logger.WithError(err).Warn("Failed to list check runs; some passing checks may be re-triggered")
}

Nitno test exercises buildAll's new skip-on-success wiring directly

pkg/plugins/trigger/pull-request_test.go (unchanged)

TestAllWithExistingStatusFilter is well unit-tested in isolation, but buildAll's wiring — including the fallback-to-TestAllFilter behavior when the GitHub API calls error — has no direct test coverage.
