Dep-only Dependabot bump of the AWS SDK v2 group. Content-wise it's safe — no CVEs, and the one behaviorally relevant change (S3 200-error detection) is a correctness improvement for the code we exercise. The only soft caveat is that the new releases are just 5-6 days old, right at the edge of the usual soak window; nothing in the changelog argues for urgency, so waiting a few more days would be reasonable but isn't required.

What this PR does

  • Bumps four direct AWS SDK v2 Go modules (aws-sdk-go-v2, config, credentials, service/s3) plus their indirect submodules and smithy-go, in both the root go.mod and hack/tools/go.mod.
  • v1.43.0 → v1.43.4 for the core module (and matching config/credentials patch bumps); service/s3 v1.106.0 → v1.107.0.
  • Touches only go.mod/go.sum in both directories — no project source, tests, or docs changed.
  • All four direct deps are used in exactly one file in this repo: pkg/io/providers/aws.go, the S3 blob-storage provider.

Things I checked and was fine with

  • Classified as dep-only: the diff touches only go.mod/go.sum in the root and hack/tools — no project code changed.
  • Import surface for all four direct deps is narrow: only pkg/io/providers/aws.go (credential loading, custom TLS transport, S3 client construction). Sensitive code, but a single, well-contained file.
  • Read the changelog for the v1.43.0..v1.43.4 range (config/credentials share the same tag commit): no CVEs; mostly kitchen-sink test infra, codegen/model regeneration, and smithy-go version bumps.
  • One relevant fix in range: "Expand checks for S3 200 errors to more operations (wave 1)" (#3493) — improves detection of S3's HTTP-200-with-embedded-error quirk. Directly applicable to our s3.NewFromConfig usage via s3blob, and it's a correctness improvement with low regression risk.
  • "Set FIPS-approved TLS curve preferences when FIPS module is active" (#3499) — not exercised; aws.go doesn't opt into FIPS mode.
  • Transfer Manager HeadObject field additions (#3491) — not applicable, this repo doesn't use Transfer Manager.
  • No pseudo-versions; all new tags resolve cleanly via the Go module proxy with proper Origin metadata pointing at real upstream tags.
  • Investigated the pull-prow-integration CI failure (run 2087143800412573696): unrelated to this PR. test/integration/integration-test.sh installs Tekton Pipeline v1.6.0 into a KIND cluster; the tekton-pipelines-webhook pod got stuck in ImagePullBackOff because containerd/kubelet repeatedly hit net/http: TLS handshake timeout pulling ghcr.io/tektoncd/pipeline/webhook-...:v1.6.0 from pkg-containers.githubusercontent.com (8 failures over ~7 minutes, same error for the resolvers image). No code path connects the AWS SDK v2 bump to Tekton image pulls — this is a registry/network flake in CI infra, not caused by the diff. Recommend /retest.
