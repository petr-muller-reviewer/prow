Verdict: Request changes

Two should-fix items are now open: the pre-existing HasConfigFor() gap, and a newly-raised config-shape concern — Assign's OnlyOrgMembers/Action/ExemptLabels fields are coupled restriction knobs living flat on a struct named after the plugin rather than the feature, and since this is the last point before the schema is released (and thus effectively frozen), the shape should be fixed now. Three open questions (PR/issue scope, org-level key coverage, assign-direction semantics) also need author confirmation. The remaining nits (hardcoded label text, double-comment scenario, MissingUsers merging) are minor UX polish and don't block.

What this PR does

  • Adds a new Assign config (map[string]*Assign) with only_org_members, action (warn/block), and exempt_labels fields.
  • In block mode, non-org-member /assign commands are rejected (members in the same command are still assigned).
  • In warn mode (default), the assign goes through but the bot posts a nudge comment.
  • Issues with configured exempt_labels bypass the restriction entirely (case-insensitive match).
  • When unconfigured, behavior is completely unchanged.

Since first review (2 revisions):

  • Config refactored from []Assign to map[string]*Assign keyed by org or org/repo (Dco pattern).
  • AssignAction type introduced with AssignActionWarn/AssignActionBlock constants; validateAssign() wired into Validate().
  • Closure extracted to three named functions: orgMemberAssignFunc, splitByMembership, blockNonMembers.
  • Dead nil check in newAssignHandler removed.

Findings

Should fix

should-fix HasConfigFor() not updated for Assign

pkg/plugins/config.go:2467-2559

HasConfigFor() is consumed only by cmd/checkconfig's supplemental-config-layout validator (cmd/checkconfig/main.go:1374-1420), which enforces that a config file under myorg/ (or myorg/myrepo/) — the standard sharded-plugins.yaml layout large Prow deployments use — contains only config scoped to that org/repo. Assign isn't part of the function's equality baseline or its orgs/repos enumeration, so any file setting assign: forces global = true unconditionally. A file at myorg/plugins.yaml containing only assign: {myorg: {only_org_members: true}} is correctly scoped but would be rejected by checkconfig as "contains global config" — a false positive. Not silent data loss, but a real break of the verification path this feature is meant to be used through. TestHasConfigFor (pkg/plugins/config_test.go:2051) has no case for Assign. Raised again explicitly in petr-muller's 2026-08-12 review.

should-fix Config struct conflates plugin identity with the restriction feature

pkg/plugins/config.go:115-128

OnlyOrgMembers, Action, and ExemptLabels are coupled knobs of one restriction feature but live flat on Assign (named after the plugin, not the feature). Two of the three fields only have meaning when OnlyOrgMembers is true — nothing in validateAssign() enforces that pairing, so action: block with only_org_members unset validates but silently does nothing (confirmed: the gate at assign.go:48/assign.go:216 is if cfg.OnlyOrgMembers; Action is never consulted otherwise). Config schema is a de facto stable API once released — Assign isn't on main yet, so this is the last free opportunity to fix the shape. Proposed by petr-muller (2026-08-12 review): nest the three fields under a Restrict sub-struct (assign.<org/repo>.restrict.{action,exempt_labels}), using the sub-struct's presence as the enablement signal instead of the OnlyOrgMembers bool — also leaves room for a future non-org-membership restriction mechanism.

type Assign struct {
    OnlyOrgMembers bool         `json:"only_org_members,omitempty"`
    ExemptLabels   []string     `json:"exempt_labels,omitempty"`
    Action         AssignAction `json:"action,omitempty"`
}

Questions

question Restriction scope and semantics are unclear

pkg/plugins/assign/assign.go:94-104, assign.go:216-225

(1) PR vs issue: handleGenericComment runs the /assign restriction path unconditionally — there is no e.IsPR gate (only the separate /cc review-request handler is PR-gated). So only_org_members currently applies identically to /assign on PRs and issues; the warn message is also hardcoded to say "issue" even when triggered from a PR comment. (2) Member/non-member direction: the membership check applies to the assignment target, not the commenter — a non-member can freely /assign an org-member approver (per the standard OWNERS approval-request flow), while an org member assigning a non-member is blocked/warned identically to a non-member self-assigning. Docs don't spell this out. Raised by petr-muller's 2026-08-12 review; needs an explicit answer (and doc wording) from the author.

question Org-level (bare org) key not explicitly covered by tests

pkg/plugins/assign/assign_test.go:472-597

AssignFor() (config.go:1111-1122) resolves org/repo → org → "*" → zero-value with no special-casing, so a bare-org key mechanically works the same as an org/repo key. Not verified whether the test suite exercises the org-only key specifically. Raised by petr-muller's 2026-08-12 review; needs confirmation/added coverage rather than a design change.

question Block mode error merging edge case

pkg/plugins/assign/assign.go:282-294 (now in blockNonMembers)

If AssignIssue for members returns a non-MissingUsers error and there are also non-members, the real error is returned and non-members are silently dropped.
