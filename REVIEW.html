Verdict

Request Changes

The bug this PR describes is real and worth fixing, and the refactor it carries (both extracted helpers) is a genuine improvement that resolves every should-fix finding from the previous pass. The problem is upstream of the timeout semantics: this pass could not identify any production condition under which the modified branch actually executes. A build cluster that is unreachable at startup never enters r.buildClients, so the failure surfaces as a TerminalError that is already handled; a build cluster that dies later keeps serving reads from a frozen informer cache, so Get keeps succeeding. Meanwhile three separate paths genuinely do wedge jobs forever, and the PR touches none of them. Before arguing about when the timeout should fire, it is worth establishing that this branch fires at all — which the plank logs for the PR's own 5-day canary example would settle immediately.

What this PR does

  • In syncPendingJob, when fetching the pod from the build cluster fails, the function used to return the error immediately, skipping the pending-timeout check entirely.
  • Adds a check in that error branch: compare r.clock.Since(pj.Status.PendingTime) against the configured pending timeout, and if exceeded mark the ProwJob ErrorState/complete instead of letting controller-runtime retry forever with backoff.
  • Extracts r.maxPodPendingTimeout(pj), deduplicating the config lookup shared with the existing PodPending case.
  • Extracts r.updateProwJobStatus(ctx, pj, prevPJ) so the new branch reaches the same completion tail (JobURL, transition log, patch, cache-sync wait) as the rest of the function.
  • Adds two table-driven test cases plus a clientWrapper.Get override to simulate build-cluster unreachability.

Findings

BlockingThe new branch is likely unreachable in production

pkg/plank/reconciler.go:499-511 (branch) · reconciler.go:845 (the erroring call) · pkg/flagutil/kubernetes_cluster_clients.go:394-417 (startup probe)

The branch only runs when buildClient.Get returns a non-NotFound error, and no path producing one has been identified. Two sub-cases exhaust the "build cluster unreachable" space:

1. Unreachable at plank startup. BuildClusters probes each cluster (cluster.New plus a live CheckAuthorizations SSAR) and omits failures from the returned map; cmd/prow-controller-manager/main.go:175-177 logs at Error and continues with the survivors. The cluster never enters r.buildClients, so r.pod() returns TerminalError("no build client found for cluster %q") at reconciler.go:835, and defaultReconcile:374-388 already completes the job as ErrorState. Corroborated by syncClusterStatus reporting exactly this state as ClusterStatusNoManager (reconciler.go:319-322).

2. Unreachable after startup. bc.Client = buildCluster.GetClient() (reconciler.go:163) with pods watched via GetCache() (reconciler.go:154-159), controller-runtime v0.21 (go.mod:83), and no DisableFor/CacheOptions overrides anywhere in cmd/ or pkg/flagutil/. Reads are served from the informer indexer with no per-call network I/O, so Get keeps succeeding against frozen data across watch loss. An unsynced informer would block in WaitForCacheSync rather than error, returning only on context cancellation at shutdown.

Consequence for the tests: the injected errors.New("dial tcp: connect: connection refused") (controller_test.go:1417) is a shape this call site cannot produce in production, so the green test does not demonstrate the bug is fixed.

Uncertainty: controller-runtime is not vendored and there is no module cache in this checkout, so the informer / WaitForCacheSync semantics above are from library knowledge, not verified against v0.21 source. Everything cited with a file:line is verified in this tree.

Suggested action: establish the real failure path from plank's logs for the PR's own example (periodic-build-farm-canary-build06, stuck 5 days) before merging, then fix the branch that actually fires. Candidates in the next finding.

BlockingThree stuck-forever paths exist that the PR does not cover

pkg/plank/reconciler.go:656-658 · reconciler.go:514-521 · reconciler.go:822

When a build cluster stops responding mid-flight, reads keep succeeding from the frozen cache, writes (Create/Delete) fail for real, and pod events stop. That produces:

  • Pending, pod last seen Running — Since(pod.Status.StartTime) < maxPodRunning (default 48h, config.go:2517) → return nil, nil. No state change, no requeue, no error, no log. The job goes completely silent. Closest match to the PR's 5-day example.
  • Pending, pod absent from cache — podExists == false → startPod → Create is a direct write and fails; isRequestError (reconciler.go:1146-1152) sees no APIStatus, defaults to code 500, returns false → error starting pod for PJ %s → backoff requeue forever, pod_pending_timeout never consulted.
  • Aborted — syncAbortedJob's Delete fails at :822 and the error returns before SetComplete → requeue forever, never completes.
case corev1.PodRunning:
    ...
    if pod.Status.StartTime.IsZero() || time.Since(pod.Status.StartTime.Time) < maxPodRunning {
        // Pod is still running. Do nothing.
        return nil, nil
    }

Also worth knowing: once PodRunningTimeout finally elapses on a resync-triggered reconcile, deletePod fails and the error returns before updateProwJobStatus, so the AbortedState transition is computed and then discarded on every single attempt.

And plank does not self-restart in this regime: the recovery goroutine in kubernetes_cluster_clients.go:427-462 only launches if aggregatedErr != nil and only probes clusters missing from res, so a cluster that was healthy at startup is never re-probed and interrupts.Terminate() never fires. Only a kubeconfig change (main.go:193-198) restarts it. syncClusterStatus writing ClusterStatusError every minute is the sole operator signal.

Suggested action: pick the path that matches the observed incident. If it is the Running-pod silence, the fix belongs near :656; if it is pod-recreation, near :514.

BlockingTimeout gated on job age, not on cluster-unreachable duration

pkg/plank/reconciler.go:501

if pj.Status.PendingTime != nil && r.clock.Since(pj.Status.PendingTime.Time) >= r.maxPodPendingTimeout(pj) {
    pj.SetComplete()
    pj.Status.State = prowv1.ErrorState

This applies only once the branch can fire at all, but it is independently wrong. Two defects relative to how maxPodPending is used everywhere else:

  • Wrong clock reference. pj.Status.PendingTime is set exactly once at Triggered→Pending (reconciler.go:769) and never updated. Prow has no distinct "Running" ProwJobState — PendingState's own doc comment (types.go:61-62) reads "the job is currently running and we are waiting for it to finish". So this measures total job age, not time-in-pod-pending and not time-since-unreachable.
  • Lost phase guard. The existing check at reconciler.go:626 compares against pod.Status.StartTime and only runs inside case corev1.PodPending. The new branch has no pod, so it applies unconditionally — including to jobs whose pod was last seen Running.

Combined: a job whose pod has run 3h has Since(PendingTime) == 3h >= 30m, so the first observed Get failure marks it errored. The default is 10m (config.go:2513) and the PR's own example uses 30m — both shorter than most CI job runtimes, so this would hit nearly the entire in-flight population of a cluster at once.

Suggested fix: gate on a duration that actually measures unreachability — a "first Get failure at" timestamp (set on failure, cleared on success), or N consecutive failures. Do not reuse pod_pending_timeout, whose name and existing semantics both mean "the pod never started". Add a test: long-running job plus a single Get error must NOT error the job.

The early return skips every subsequent assertion, so ExpectedState: prowapi.PendingState on the "pending timeout not yet exceeded" case is dead configuration — nothing verifies the ProwJob was left untouched, which is the actual behaviour under test. Should fixupdateProwJobStatus name does not describe what it does

pkg/plank/reconciler.go:461-492

The name reads as a setter, but the function (1) mutates pj.Status.URL, (2) logs the transition, (3) patches, and (4) if the state changed, blocks up to 2s polling until the cache reflects it — overwriting pj with the object read back. Neither the pj mutation nor the blocking barrier is inferable from the name, and the barrier is the whole point of the function.

Preferred: hoist the JobURL assignment back to the call sites (two lines) and rename the rest to patchProwJobAndWaitForCache, which then fully describes the body. Alternative: keep it whole under finalizeProwJobStatus / commitProwJobStatus plus a godoc stating that pj is mutated, that the URL error is logged and swallowed, and why the barrier exists (a later reconcile could otherwise observe pre-patch state and recreate a just-deleted pod).

QuestionRetranslate to TerminalError instead of hand-rolling completion?

pkg/plank/reconciler.go:499-511 vs reconciler.go:374-388

return nil, TerminalError(fmt.Errorf("pending timeout exceeded, build cluster unreachable: %w", err))

This would reuse the existing terminal handler and collapse the whole branch to ~4 lines, removing the need for updateProwJobStatus in this PR. It propagates correctly — syncPendingJob → reconcile:326 → serializeIfNeeded:422 → defaultReconcile:374, no wrapping — and IsTerminalError works despite the *nonRetryableError / nonRetryableError{} pointer-value mismatch, since the value-receiver Is is in the pointer's method set.

Tradeoffs: it loses the cache-sync barrier — and unlike existing terminal errors (unknown alias, idempotent), "cluster unreachable" can stop being true, so a stale re-read could hit podExists == false and start a fresh pod for an already-errored job. It also swallows patch failures (:384-386 logs and returns nil, no requeue), reintroducing the stuck-forever symptom. Status.URL loss is moot (already set at :773). Would need if IsTerminalError(err) { return nil, err } first to avoid double nonretryable error: prefixes.

QuestionTerminalError (unknown cluster alias) folded into the same branch

pkg/plank/reconciler.go:499-511 vs reconciler.go:835

If the pending timeout is already exceeded and the fetch failure is actually a TerminalError (unknown/misconfigured cluster alias), this branch marks the job errored directly instead of letting defaultReconcile's IsTerminalError path handle it, and reports "could not get pod from build cluster" rather than "Terminal error: ...". End state is identical; only the diagnostic degrades. Intentional, or worth an IsTerminalError(err) guard?
