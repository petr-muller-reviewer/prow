Verdict

Request changes.

The core design (merge advisory approvers into the approvers map, subtract in LeafApprovers) is sound for the common case and all three maintainer perspectives (code quality, maintainability, deployment risk) are positive. However, two confirmed correctness bugs in the advisory-only-directory edge case need fixing: LeafApprovers returns an empty set when a directory has only advisory approvers, and verify-owners rejects a valid advisory-only root OWNERS file.

What this PR does

  • Adds an advisory_approvers field to the OWNERS file Config struct, supporting both SimpleConfig and FullConfig (filters) formats.
  • At load time (applyConfigToPath), merges advisory approvers into the approvers map so they are recognized by Approvers() for /approve authority.
  • Modifies LeafApprovers to subtract advisory approvers, preventing them from being auto-assigned as reviewers.
  • Adds AdvisoryApprovers(path string) to the RepoOwner interface with stub implementations in all test fakes.
  • Updates verify-owners to collect advisory approvers and include them in org membership validation.

Findings

Blocking

LeafApprovers returns empty set for advisory-only directories

pkg/repoowners/repoowners.go:903-908

func (o *RepoOwners) LeafApprovers(path string) sets.Set[string] {
	all := o.entriesForFile(path, o.approvers, true).Set()
	advisory := o.entriesForFile(path, o.advisoryApprovers, true).Set()
	return all.Difference(advisory)
}

If a directory's OWNERS lists only advisory_approvers: [dan] with no regular approvers, applyConfigToPath merges dan into o.approvers at that path. entriesForFile with leafOnly: true finds {dan} there and stops — never reaching the parent directory's regular approvers. The subtraction yields an empty set: {dan} - {dan} = {}. Auto-assignment silently finds zero candidates even though a parent directory has regular approvers.

verify-owners rejects root OWNERS with only advisory_approvers

pkg/plugins/verify-owners/verify-owners.go:459-464

if filepath.Dir(c.Filename) == "." && len(approvers) == 0 {
	return &messageWithLine{
		lineNumber,
		fmt.Sprintf("No approvers defined in this root directory %s file.", filenames.Owners),
	}, nil
}

The approvers and advisoryApprovers slices are collected separately. The root-level len(approvers) == 0 check on line 459 fires before advisoryApprovers are appended to owners on line 466. A root OWNERS with advisory_approvers: [alice] but no approvers: is rejected as "No approvers defined" even though alice would have /approve power at runtime.

Should fix

Dual-storage invariant is under-documented

pkg/repoowners/repoowners.go:270 (struct field) and :756-769 (applyConfigToPath)

Advisory approvers live in both o.advisoryApprovers and o.approvers. The only documentation of this invariant is the comment inside LeafApprovers. A future contributor adding a new method that reads o.approvers must know advisory approvers are mixed in. Add a doc comment on the advisoryApprovers struct field explaining the dual-storage design. Flagged independently by both the code quality and maintainability reviewers.

TopLevelApprovers/LeafApprovers asymmetry is undocumented

pkg/repoowners/repoowners.go:948-950

TopLevelApprovers() reads o.approvers directly and includes advisory approvers. LeafApprovers() subtracts them. The asymmetry is correct (TopLevelApprovers is used for authorization, not assignment) but a future contributor might "fix" the inconsistency without understanding why. A one-line comment explaining the intentional difference would prevent this.

Nits

Unnecessary set copy and overly complex merge logic

pkg/repoowners/repoowners.go:756-769

if existing, ok := o.approvers[path][re]; ok {
	o.approvers[path][re] = existing.Union(advisorySet)
} else {
	o.approvers[path][re] = advisorySet.Union(sets.New[string]())
}

advisorySet.Union(sets.New[string]()) unions with an empty set, which is just a verbose copy. filterCollaborators never mutates sets in place (it creates new sets via Intersection), so aliasing between the advisoryApprovers and approvers maps would be safe. The entire if/else block could be simplified to match the single-assignment pattern used for every other field. Flagged independently by both code quality and maintainability reviewers.

Questions

Is advisory-only OWNERS a valid use case?

Both blocking findings hinge on whether an OWNERS file with only advisory_approvers (no regular approvers) is a supported configuration. If yes, both bugs need fixing. If no, should there be explicit validation that rejects it with a clear message rather than silently producing empty assignment sets?

Should advisory approvers listed as reviewers appear in LeafReviewers?

TestAdvisoryApproverAlsoReviewer asserts that a user who is both an advisory approver and a reviewer still appears in LeafReviewers. This means they can still be auto-assigned as reviewers, just not as approvers. Is this the intended behavior?

Things I checked and was fine with

  • All RepoOwner interface implementations (6 test fakes) implement AdvisoryApprovers.
  • Callers of LeafApprovers (GetLeafApprovers, GetAllPotentialApprovers, GetCCs, blunderbuss fallback) all use it for auto-assignment where excluding advisory approvers is correct.
  • Callers of Approvers (UnapprovedFiles, GetFilesApprovers, GetCCs reverse map, lgtm, override) all use it for authorization where including advisory approvers is correct.
  • filterCollaborators preserves the superset invariant (approvers ⊇ advisoryApprovers) because set intersection preserves subset relationships.
  • AllApprovers / AllOwners / TopLevelApprovers correctly include advisory approvers via the merged o.approvers map.
  • SimpleConfig.Empty() correctly includes the new field.
  • The add-then-subtract design is safer than the alternative (keep separate, union in Approvers) because new code reading o.approvers automatically includes advisory approvers — the correct default for authorization.
  • Test coverage is thorough (TestAdvisoryApprovers, TestAdvisoryApproverAlsoReviewer, TestApplyConfigWithAdvisoryApprovers, TestSimpleConfigEmptyWithAdvisoryApprovers, TestParseOwnersFileIncludesAdvisoryApprovers).
  • Deployment risk is low: purely additive change, omitempty preserves backward compatibility, rolling upgrades and rollbacks are safe.

Open questions for the author

  • Is an OWNERS file with only advisory_approvers (no regular approvers) a valid use case? If yes, both blocking findings need fixing. If no, should there be validation that rejects it explicitly with a clear message?
  • Should advisory approvers who are also listed as reviewers: still appear in LeafReviewers? The test TestAdvisoryApproverAlsoReviewer asserts yes, but it's worth confirming this is intentional — it means they can still be auto-assigned as reviewers (just not as approvers).
  • The RepoOwner interface gains a new method (AdvisoryApprovers), which is a source-level breaking change for out-of-tree implementations. Should this be noted in release notes?
