Verdict: request changes

The feature is well-built, opt-in, and follows peribolos conventions closely, but it contains a confirmed defect: with --fix-org-roles enabled, peribolos revokes organization roles from teams the operator explicitly excluded via --ignore-secret-teams or --ignore-enterprise-teams, and the config format offers no way to express an exemption. The cause is a filtered set being diffed against an unfiltered one. It is opt-in, so no existing deployment is affected until someone enables the flag — but the first operator who does, in combination with either ignore flag, silently loses permissions. The fix is small and local.

This re-review also supersedes the earlier finding set: two of the three previously "converging" concerns did not survive scrutiny (see the nit on --fix-teams coupling and the note on cleanup logging under Checked).

Gating item (blocks merge)

Ignored teams silently lose their organization roles — cmd/peribolos/main.go:1710-1768 (source: this review, blocking). wantSet (config-declared teams only) is diffed against haveSet (every team GitHub reports holding the role), and the difference is removed. A team excluded via --ignore-secret-teams or --ignore-enterprise-teams therefore has its org role stripped despite the flag's own contract, with no way in the config schema to exempt it. Confirmed empirically against this exact code (see Findings below). Not addressed, not discussed by the author. Blocks merge as-is: this is a live correctness defect in a code path that ships whenever --fix-org-roles is enabled, not a style nit.

  • Embedding OrganizationRolesClient in Client breaks downstream implementers (pkg/github/client.go:79-89,291) — real but consistent with how this project has always grown github.Client; worth a release note, not a blocker.
  • errors variable shadows the errors package (main.go:1750, 1817) — cosmetic, go vet clean.

Merge risk (Area 2)

No new risk beyond what the findings already capture. --fix-org-roles remains opt-in, default false — no existing deployment is affected by merging as-is. The risk is entirely inside the opt-in path: an operator who combines --fix-org-roles with --ignore-secret-teams or --ignore-enterprise-teams (the latter shipped on main in May 2026, daa3c7a62) silently loses role assignments on teams they explicitly asked peribolos not to touch. No CRD/API-server-facing surface — this is a CLI tool operators run themselves — so blast radius is bounded to whoever runs peribolos with that flag combination, but it is a silent permission change with no warning beyond the standard --confirm=false dry-run mechanism. No skill in .claude/skills/ was applicable (no CRD/schema-compat skill present); assessed directly.

Unblocks by

Fixing the ignored-team/role-removal asymmetry (thread ignored-team slugs through to configureRoleTeamAssignments and exclude them from toRemove, or diff against the full team list on both sides). The should-fix items can ride along or follow in a fast-follow; they don't need to gate this hold.

What this PR does

  • Adds a --fix-org-roles flag (default false) and a roles: section to the org config, for declaratively managing who holds GitHub custom organization roles. The roles themselves must already exist in GitHub.
  • configureOrgRoles walks every role GitHub reports, syncing the ones named in config and stripping all assignments from the ones that are not.
  • Adds 7 client methods behind a new OrganizationRolesClient interface, which is embedded into the exported github.Client.
  • --dump gains a roles: section; roles with no team or user assignments are omitted (the most recent commit).
  • Users holding a role indirectly through team membership are preserved, and users with pending org invitations are skipped until they accept.

Findings

Blocking

blockingIgnored teams silently lose their organization roles

cmd/peribolos/main.go:1710-1768

Two sets are compared, and they are drawn from different worlds. wantSet is built from githubTeams, which holds only config-declared teams — configureTeams continues past secret teams (main.go:796) and enterprise teams (main.go:792) before recording them, so an ignored team can never appear. haveSet comes straight from ListTeamsWithRole, which returns every team on GitHub holding the role. The difference is deleted.

normalizedTeams := make(map[string]string)
for name, team := range githubTeams {          // config-declared teams only
    normalizedTeams[strings.ToLower(name)] = team.Slug
}
...
haveSet := sets.New[string]()
for _, team := range currentTeams {          // everything GitHub reports
    haveSet.Insert(team.Slug)
}
...
toRemove := haveSet.Difference(wantSet)
for teamSlug := range toRemove {
    if err := client.RemoveOrganizationRoleFromTeam(orgName, teamSlug, roleID); err != nil {

So --fix-org-roles revokes roles from exactly the teams the operator opted out of managing. That contradicts both flags' own help text at main.go:92-93 — "Do not dump or update secret teams if set" and "Skip enterprise teams and their members during reconciliation" — and partially regresses daa3c7a62 (PR #710, May 2026, same author), which exists specifically to stop peribolos reconciling enterprise-managed teams.

There is no escape hatch. ValidateRoles (pkg/config/org/org.go:98) rejects any role naming a team absent from c.Teams, so the exemption cannot be written down; and declaring the team instead routes it to missing, where peribolos attempts CreateTeam (main.go:855-870).

Confirmed empirically against this head — a throwaway test driving configureOrgRoles with one config-declared team plus one ignored team:

level=info msg="Removed role security-manager from team enterprise-sec"
removed: [test-org/enterprise-sec/1]

Suggested fix: thread the ignored-team slugs through to configureRoleTeamAssignments and exclude them from toRemove, or build haveSet from the full team list so both sides of the diff share a domain.

Should fix

should-fix--dump output is not round-trippable when teams are filtered

cmd/peribolos/main.go:425-433

The same filtered-vs-unfiltered asymmetry, on the dump side.

for _, team := range teamsWithRole {
    // Only include teams that are in slugToName (secret teams are excluded from this map)
    if name, ok := slugToName[team.Slug]; ok {
        teamNames = append(teamNames, name)
    } else if !ignoreSecretTeams {
        teamNames = append(teamNames, team.Slug)   // raw slug leaks into the config
    }
}

A role held by a team missing from slugToName (enterprise teams under --ignore-enterprise-teams) gets the raw slug written into roles.<name>.teams, while the teams: section omits that team. Re-applying the dump fails peribolos' own validation:

role validation failed:
  - role "security-manager" references undefined team "enterprise-sec"

Under --ignore-secret-teams the team is instead dropped silently, which feeds straight into the blocking finding. Dump→apply idempotence is a property operators rely on. Verified by feeding a synthesized dump through ValidateRoles.

should-fixEmbedding OrganizationRolesClient in Client breaks downstream implementers

pkg/github/client.go:79-89,291

type Client interface {
    ...
    OrganizationClient
    OrganizationRolesClient
    TeamClient

Adding 7 methods to the exported github.Client interface is a compile-time break for any out-of-tree type satisfying it — custom fakes, throttling or caching wrappers, decorators. It is safe for callers, not for implementers. In-tree fakegithub.FakeClient is updated so the common case is covered, but this is an upstream library whose consumers we do not control. Worth a release note. (The earlier gate recorded this as unqualifiedly "additive, safe" — that was wrong.)

The dependency is genuine, not arbitrary: configureOrg returns early at main.go:1065-1068 when fixTeams is false, so configureOrgRoles is unreachable without it, and team-name→slug resolution needs configureTeams' output. Questions

questionDoes ListTeamsWithRole return enterprise teams?

The blocking finding assumes GitHub reports enterprise teams among the teams assigned to an org role, which is the documented purpose of enterprise team role grants. The manual testing was against a test org; confirming this specific case would settle the severity.

questionWhat is the intended contract for teams peribolos does not manage?

The author's own test at main_test.go:4734 ("remove team assignment", githubTeams: {}) asserts that a team unknown to the config loses the role. Defensible for unmanaged teams — but nothing in the code distinguishes "not in config" from "explicitly ignored". Which was intended determines whether the fix exempts ignored teams only, or restricts role management to declared teams entirely.
