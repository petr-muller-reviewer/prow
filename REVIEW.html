What this PR does

  • Replaces the empty placeholder page for the hook component at site/content/en/docs/components/core/hook.md with substantive operator documentation.
  • Documents the full webhook dispatch pipeline: receive → HMAC validate → parse → repo check → dispatch to internal plugins → forward to external plugins.
  • Lists all seven GitHub event types with registered internal handlers, and explains that any event type can be forwarded to external plugins.
  • Provides copy-paste-ready YAML for HMAC secret setup, plugins.yaml (org/repo scoping with excluded_repos), and external plugin configuration.
  • Documents CLI flags with defaults, HTTP endpoints, and a troubleshooting section for the two most common failure modes.

Findings

blockingHealth endpoint is misdocumented — will break probe configuration

📍 site/content/en/docs/components/core/hook.md:149-152

⚑ Flagged independently by Code Quality and Deployment Risk reviewers

The Endpoints section lists / on the main port (8888) as "Health check endpoint (returns 200 OK)". That handler is a legacy stub — the source code even has a // TODO remove this health endpoint when the migration to health endpoint is done comment on it. The actual health infrastructure is served by pjutil.NewHealthOnPort on a separate port (default 8081), exposing /healthz (liveness) and /healthz/ready (readiness). Kubernetes operators following this doc will configure probes against the wrong port and endpoint, which silently appears to work (the stub returns 200) while the real health port is unchecked.

- `/hook` - Webhook receiver endpoint (configurable via `--webhook-path`)
- `/plugin-help` - Returns help information about enabled plugins
- `/` - Health check endpoint (returns 200 OK)   ← incorrect

Fix: Replace the / entry with /healthz and /healthz/ready on the health port (default 8081). Optionally note that / on port 8888 exists only for legacy compatibility.

should fixGitHub authentication flags entirely absent

📍 site/content/en/docs/components/core/hook.md:130-143

The CLI flags section does not list --github-token-path (personal access token) or the GitHub App pair --github-app-id / --github-app-private-key-path. Hook cannot call the GitHub API without one of these — plugins will receive events but cannot respond to them. An operator following this doc as their primary reference will produce a deployment that silently accepts webhooks but never comments, labels, or triggers ProwJobs.

Common flags for Hook:

- `--config-path`: Path to [Prow config file](/docs/config/)
- `--plugin-config`: ...
- `--hmac-secret-file`: ...
  [--github-token-path and GitHub App flags absent]

should fixNo mention of ghproxy or --github-endpoint

📍 site/content/en/docs/components/core/hook.md:130-143

The Prow codebase itself warns "It doesn't look like you are using ghproxy to cache API calls to GitHub! This has become a required component of Prow." Despite this, neither --github-endpoint (the flag for pointing Hook at ghproxy) nor ghproxy itself is mentioned anywhere in the doc. Operators will hit GitHub API rate limits without it.

should fix--dry-run footgun is undersold

📍 site/content/en/docs/components/core/hook.md:143

The --dry-run=true default is the single most common footgun for new Prow operators. Hook will silently accept webhooks, produce log output that looks healthy, and take zero real actions (no ProwJob creation, no GitHub comments, no status updates). The current doc mentions this only as a single sentence at the bottom of the flags list — easy to miss. It should be a prominent callout box or bold warning in the Configuration section, not an afterthought.

Production deployments must set `--dry-run=false`.   ← buried at end of flags section
