Verdict: Approve with Suggestions

All three review perspectives (code quality, maintainability, deployment risk) approve this PR. The KAL infrastructure is well-structured, the linter selection is conservative and thoughtful, and deployment risk is low — no struct tags, validation rules, or runtime behavior changed. Two converging concerns (CRD description information loss, missing set -o errexit) are worth addressing but non-blocking.

What this PR does

  • Adds kube-api-linter (KAL) as a custom golangci-lint plugin, built via hack/tools/build-kal and run via hack/make-rules/verify/kube-api-lint.sh against ./pkg/apis/...
  • Enables eight KAL rules: commentstart, conflictingmarkers, duplicatemarkers, nofloats, optionalorrequired, uniquemarkers, nophase, nonullable — with thoughtful TODOs for future rules
  • Fixes every field in pkg/apis/prowjobs/v1/types.go to have lowercase-JSON-tag-prefixed comments and +optional/+required markers
  • Replaces +kubebuilder:validation:Required with +required
  • Regenerates CRD YAML and both documented config files to reflect the comment changes
  • Adds make lint-api target and integrates into make verify; adds cleanup dirs to make clean

Converging Concerns (flagged by 2+ reviewers)

  1. CRD description information loss (Maintainability + Deployment Risk): Spec and Status field comments were reduced to tautologies like “spec is the ProwJob spec”. The commentstart rule only requires the first word to match the JSON tag — the descriptive content should be preserved.
  2. build-kal missing set -o errexit (Code Quality + Maintainability): Every other verify script in the repo includes all three shell options. Without it, the real build error is masked behind “binary not found”.

Findings

Should Fix

CRD descriptions gutted for ProwJobSpec, ProwJobStatus, ResultStoreConfig

pkg/apis/prowjobs/v1/types.go:136-141

To satisfy commentstart, several field-level comments were replaced with tautological stubs. Users reading kubectl explain prowjob.spec now see “spec is the ProwJob spec” instead of the previous description covering podspec, cloning, clusters, child jobs, and concurrency. Similarly, ProwJobStatus lost “provides runtime metadata, such as when it finished, whether it is running, etc.”, and ResultStoreConfig lost “for uploading results to”.

The commentstart rule only requires the comment to start with the JSON tag name in lowercase — it doesn't require removing all content. Rewrite to keep the descriptive text: 

// spec configures the details of the prow job, including the podspec,
// code to clone, the cluster it runs, child jobs, concurrency limitations, etc.
// +optional
Spec ProwJobSpec `json:"spec,omitempty"`
Should Fix

build-kal missing set -o errexit

hack/tools/build-kal:16-17

The script has set -o nounset and set -o pipefail but omits set -o errexit. Every other verify script in the repo includes all three. If the go tool invocation fails, the real error is masked behind the “binary not found” fallback message at line 30. 

set -o nounset
set -o pipefail
Should Fix

Questionable +optional on embedded time.Duration in Duration wrapper

pkg/apis/prowjobs/v1/types.go:464-467

Duration is a wrapper type whose sole purpose is to hold a time.Duration value. Marking the embedded field +optional is semantically wrong — it's the value itself, not an optional sub-field. If KAL flags embedded fields in wrapper types, a nolint directive would be more appropriate than an incorrect marker. 

type Duration struct {
	// +optional
	time.Duration
}
Should Fix

Dubious markers on ProwJobList embedded types

pkg/apis/prowjobs/v1/types.go:1465-1473

TypeMeta is marked +optional, ListMeta and Items are marked +required. These are structural fields on a list type, not user-facing optional/required API fields. Adding markers here to silence the linter misrepresents the API semantics. Consider a nolint directive or excluding the list type from KAL scope. 

type ProwJobList struct {
	// +optional
	metav1.TypeMeta `json:",inline"`
	// +required
	metav1.ListMeta `json:"metadata"`
	// +required
	Items []ProwJob `json:"items"`
}

Open questions for the author

  • Why were descriptive comments stripped rather than reworded to start with the JSON tag? The commentstart rule only requires the first word to match — the rest of the description could have been preserved.
  • Is +optional on embedded time.Duration (in the Duration wrapper) actually required by KAL, or was it added preemptively? If KAL flags it, would a nolint directive be more appropriate?
  • Is kube-api-linter available as a tagged release? The pseudo-version makes it harder to track which version of the rules the codebase conforms to.
  • Should ResultStoreConfig.ProjectID be +required given the prose says it is required for ResultStore functionality?
