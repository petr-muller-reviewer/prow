The production change in pkg/github/client.go is correct and an improvement in every case I could construct — traced and tested. But the headline regression test, TestReadPaginatedResultsWithRedirect, passes against the pre-fix code (verified empirically), so it would not catch a regression of the exact bug this PR fixes. What this PR does

  • In readPaginatedResultsWithValuesWithContext (pkg/github/client.go:1960), the GHE base-path prefix (e.g. /api/v3) was computed as TrimSuffix(resp.Request.URL.RequestURI(), pagedPath). After an HTTP redirect (repo rename/transfer), resp.Request.URL is the final URL, the suffix doesn't match, prefix becomes the entire response URI, and the subsequent TrimPrefix mangles the next-page Link into e.g. &page=2.
  • That mangled path is concatenated as c.bases[hostIndex]+path (client.go:981), producing https://api.github.com&page=2 — a fatal URL-parse/DNS error.
  • Fix: compute the prefix from paths only (resp.Request.URL.Path vs. query-stripped pagedPath), making it immune to query-string differences.
  • Adds a safety fallback: if the trimmed next path doesn't start with /, use the Link header's full RequestURI().
  • Known, documented limitation: GHE plus redirect falls into the fallback and doubles /api/v3 → 404 instead of a crash. Acceptable trade; note the 404 also burns max404Retries with backoff before surfacing.
  • Adds two tests: same-path+query pagination, and pagination across a 301 redirect.

blocking Redirect test passes against pre-fix code — not a regression test

pkg/github/client_test.go:1446-1448

Verified: with git checkout HEAD~1 -- pkg/github/client.go, both new tests pass. The old code only breaks when the next Link is a literal extension of the redirected response's RequestURI (GitHub's real behavior: current URL + &page=N). The test's page-1 response URI ends in ?per_page=100&protected=false but the Link hardcodes ?per_page=100&page=2 — so the old TrimPrefix is a no-op and the old code accidentally works.

w.Header().Set("Link", fmt.Sprintf(
    `<https://%s/repos/new-org/new-repo/branches?per_page=100&page=2>; rel="next"`,
    r.Host))

Suggested (verified: fails on pre-fix code with parse "https://127.0.0.1:<port>&page=2": invalid port, passes with the fix):

w.Header().Set("Link", fmt.Sprintf(
    `<https://%s/repos/new-org/new-repo/branches?%s&page=2>; rel="next"`,
    r.Host, r.URL.RawQuery))

nit t.Fatalf called from HTTP handler goroutine

FailNow is only valid from the test goroutine; from an httptest handler it can hang or fail to stop the test. Use t.Errorf — the redirect test's default: branch (lines 1457–1459) does it right. Pre-existing tests in this file share the flaw, so not a blocker.

Things I checked and was fine with

  • Traced the new prefix logic through: github.com same-path; github.com /repositories/<id>/... next-link shape; GHE with and without query strings; redirect on plain GitHub; GHE+redirect (falls into the documented 404 limitation). All correct.
  • The pagedPath[0] != '/' fallback can't misfire on legitimate GHE links (/api/v3... trims to /...); it fires correctly on redirect-mangled prefixes.
  • URL construction is plain string concat c.bases[hostIndex]+path (client.go:981) — confirms the reported failure mode.
  • Existing pagination tests (including the /api/v3 base-suffix case) pass with the new logic; go test -run TestReadPaginated green.
  • Decoded-vs-raw path mismatch (resp.Request.URL.Path is decoded, pagedPath is raw): checked all readPaginatedResults* call sites — none use percent-encoded path segments (escaping appears only in query params, client.go:3651,5187). Theoretical only; EscapedPath() would harden.
  • values.Encode() sorts keys, so prefix computation stays consistent on later iterations.
