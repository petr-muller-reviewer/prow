Review: kubernetes-sigs/prow#942

feat(deck): add dark mode support for main prow status dashboard
Base: main · Head: d37116e6bc583ddfadff0288b649db55fe91b2af · Reviewed: 2026-09-23T12:15:41Z

Verdict: request changes

The index-only dark-mode behavior is appropriately scoped, but storage-restricted browsers can leave the toggle uninitialized, and !important dark-mode rules override explicitly configured Deck branding colors.

What this PR does

  • Adds early theme selection on the main Deck dashboard from a saved browser preference or the OS color scheme.
  • Adds an index-page header control that persists an explicit light/dark choice.
  • Switches the default logo with the theme while leaving custom logos alone.
  • Adds index-scoped dark styling for the dashboard's navigation, filters, table, histogram, and dialogs.

Findings

Blocking

Theme initialization assumes browser storage is always available

cmd/deck/template/base.html:40-45, 143-160, 166-169

var stored = localStorage.getItem('prow-theme');
...
localStorage.setItem('prow-theme', nextTheme);

localStorage.getItem and setItem may throw when storage is disabled by browser privacy policy or embedding restrictions. An exception at line 144 aborts initialization before the click handler is registered. Wrap access in helpers and fall back to the system preference plus an in-memory choice.

Blocking

Dark mode supersedes operator-configured Deck branding

cmd/deck/static/style.css:1152-1161; cmd/deck/template/base.html:53-56

<body id="{{.PageName}}"{{if branding.BackgroundColor}} style="background-color: {{branding.BackgroundColor}};"{{end}}>
...
background: #121212 !important;
background-color: #212121 !important;

Configured colors are rendered inline but overridden by the new declarations. This can change branding and leave a custom logo with inadequate contrast. Preserve explicit colors or introduce a documented dark-branding policy.

Should fix

Icon-only theme control has no accessible name

cmd/deck/template/base.html:63-65

<button id="theme-toggle" class="mdl-button mdl-js-button mdl-button--icon" title="Toggle dark mode">
  <i id="theme-toggle-icon" class="material-icons">brightness_2</i>
</button>

Add an aria-label and update it with the title so the control has a stable, actionable accessible name.

Should fix

Theme state and palette add avoidable maintenance surface

cmd/deck/static/style.css:1152-1410; cmd/deck/template/base.html:103-185

html.dark-mode body#index,
body#index.dark-mode {
  background: #121212 !important;
}

Selectors are duplicated for two roots, repeated color literals are scattered, and the controller sits in the shared base template. Use one root class, semantic CSS variables, and the existing index frontend bundle for post-DOM behavior.

Things I checked and was fine with

  • The change is limited to the index page; other Deck pages retain their current behavior.
  • The head bootstrap prevents most light-theme flash.
  • A stored preference overrides the system setting, and custom logos are retained.
  • No API, config schema, RBAC, dependency, or server-availability behavior changes.
  • deckVersion cache busting remains in use, so no special upgrade sequencing is needed.

Open questions for the author

  • Should configured background/header colors always win, or should Deck grow explicit dark-branding configuration?
  • Should storage-unavailable browsers support non-persistent switching as a documented fallback?
