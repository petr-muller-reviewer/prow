Verdict: Needs discussion

The change does exactly what issue #789 asked for, is small, and its tests pass — but a second pass through Tide says the preserved base SHA defeats both of Tide's gates for an override result, so in the moved-base case (the only case this PR changes behavior in) /override stops unblocking merges. That is a design question for a maintainer rather than a mechanical fix, hence "needs discussion" rather than "request changes": the intent is clearly endorsed, but the mechanism appears to undo the user-visible effect of the command. Secondary: the lazy per-status lookup can now leave a half-applied override plus two contradictory bot comments, and the new caching test does not actually exercise the new caching.

What this PR does

  • When /override recreates a synthetic successful status/ProwJob for a failed presubmit, it now prefers the base SHA already embedded in the failed status's description (BaseSHA: marker) over re-fetching the PR's current base branch SHA.
  • Adds baseSHAForStatus(status, fallback): returns the embedded SHA if present, else calls fallback().
  • Adds cachedRefGetter(getter): memoizes the fallback RefGetter (value and error) so multiple statuses needing the fallback in one invocation trigger only one GetRef call.
  • Removes the previous unconditional baseSHAGetter() call (and its early-return-on-error) at the top of handle; the getter is now invoked lazily, per status, only when needed.
  • Implements item 2 of issue #789 (follow-up from the #778 review).

Findings

BlockingStale BaseSHA makes Tide ignore the override entirely, in exactly the scenario this PR targets

pkg/plugins/override/override.go:536 (effect at :564) → pkg/tide/tide.go:1055 and pkg/tide/tide.go:1974/2171

Both Tide gates for an override result are keyed on the current pool base SHA. (1) prowJobsFromContexts accepts a green context only when the embedded SHA equals the pool base SHA. (2) The synthetic ProwJob is only visible to the pool through cacheIndexKey(sp.org, sp.repo, sp.branch, sp.sha), which indexes on pj.Spec.Refs.BaseSHA. Stamping the old SHA into both means neither matches once the base branch has moved — precisely the divergence the PR exists to handle.

Concrete scenario: job fails at base B0; base advances to B1; user runs /override prow-job. Pre-PR, status and ProwJob were stamped B1, Tide counted the context as passing, PR merged. Post-PR both carry B0, Tide matches neither, retriggers the job, it fails again — the override never sticks and the user must keep re-overriding.

Note that /override-sticky is unaffected: stickyDescription (override.go:332) embeds config.SkipRetestSentinel, which short-circuits the base-SHA comparison. That asymmetry is itself evidence that plain /override deliberately depends on the current base SHA. A fix probably means either keeping the current base SHA in the status description while using the original only for the ProwJob refs, or giving plain override an equivalent sentinel-style escape hatch.

Should fixGetRef failure mid-loop leaves a partial override and posts two contradictory comments

pkg/plugins/override/override.go:517-541

Previously baseSHAGetter() ran once before any mutation, so a failure produced a single "Cannot get base ref of PR" comment with nothing changed. Now the fallback runs inside the per-status loop. With statuses [A (has marker), B (no marker)] and GetRef failing: A is fully overridden (ProwJob created, status flipped to success, done.Insert(A)), then B returns the failure comment — and the defer at override.go:523 immediately posts the success message listing A. Half-applied override, two comments that contradict each other. Resolving the fallback once up front whenever any targeted status lacks a marker would restore the old atomicity.

baseSHA, err := baseSHAForStatus(status, baseSHAGetter)
if err != nil {
    resp := "Cannot get base ref of PR"
    log.WithError(err).Warn(resp)
    return oc.CreateComment(org, repo, number, plugins.FormatResponseRaw(e.Body, e.HTMLURL, user, resp))
}

NitcachedRefGetter duplicates shaGetterFactory's memoization

pkg/plugins/override/override.go:520, :609-620, :701-712

shaGetterFactory's own comment says it is "a closure to retrieve a sha once". cachedRefGetter adds a second layer whose only new effect is caching failures — immaterial, since the first error aborts handle. Either consolidate, or add a comment stating the wrapper exists so handle does not depend on the caching behavior of whatever RefGetter it is handed.

func cachedRefGetter(getter config.RefGetter) config.RefGetter {
    var baseSHA string
    var err error
    var called bool
    return func() (string, error) {
        if !called {
            baseSHA, err = getter()
            called = true
        }
        return baseSHA, err
    }
}

NitNo comment on why a status's base SHA can diverge from the PR's current base ref

pkg/plugins/override/override.go:602-607

The rationale — a job's original base SHA differs from today's base-branch tip when the branch moved — lives only in the PR description. One line of comment on baseSHAForStatus would stop a future maintainer from reading the marker preference as a bug.

Things I checked and was fine with

  • baseSHAForStatus falls through correctly on an empty description — branch-protection-injected synthetic statuses (github.Status{Context: context}, override.go:499) have a zero-value Description, and BaseSHAFromContextDescription("") returns "".
  • ContextDescriptionWithBaseSha receives only descFn(user) as the human-readable part, so re-encoding an already-marked description cannot double the BaseSHA: suffix or blow the 140-char limit.
  • cachedRefGetter memoizes value and error on first call; no re-entrancy or goroutine concern (handle is single-threaded, matching shaGetterFactory's "not threadsafe" note).
  • The checkrun override path is untouched — checkruns carry no base SHA and still key off the head SHA only.
  • go vet and go test ./pkg/plugins/override/ pass on the PR head.
  • No config/API/CRD/RBAC surface touched; the change is confined to override.go and its test. Drop-in and revertible.
  • No security-relevant surface: base SHA data originates from Prow's own status descriptions, not user-controlled input.
  • Net API-call effect is positive: GetRef is skipped entirely when every targeted status carries a marker.

Open questions for the author

  • Was the Tide coupling considered? Tide only counts an override when the embedded SHA equals the current pool base (tide.go:1055) and only sees the synthetic ProwJob through an index keyed on that same SHA (tide.go:1974). With the original SHA preserved, an override on a stale failing status satisfies neither — so /override would stop unblocking merges in exactly the moved-base case. Is a follow-up planned (sentinel for plain override, or splitting the status SHA from the ProwJob refs SHA)?
  • Should a GetRef failure still guarantee all-or-nothing across the contexts of a single /override invocation, as it did before this change? Right now the user can get a failure comment and a success comment for the same command.
  • Could TestHandleCachesFallbackBaseSHA be reworked to test cachedRefGetter directly (specifically error caching)? As written it passes even with the wrapper removed, because shaGetterFactory already caches successes.
  • Is this PR complementary to or overlapping with #778 (/override-sticky)? Prucek raised this on 2026-08-10; worth an explicit reply distinguishing base-SHA preservation from sticky-override persistence.
