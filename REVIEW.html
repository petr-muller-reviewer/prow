Verdict

Request changes — the PR does not close the bypass on one of its three entry points. handleReview seeds changedFiles from the pull_request_review payload, which carries no changed_files field — confirmed against this repo's own fixture. The guard short-circuits and an APPROVE review on a 5000-file PR still applies the label. Secondarily, the shortfall comparison treats any count mismatch as truncation, so a force-push race can post an "exceeds 3000 files" comment on a small PR and strip its approved label. The earlier blocking finding (unsound commit-based fallback) remains resolved; the core approach is sound and the remaining work is contained.

What this PR does

  • Closes a real, observed approval bypass (openshift/hypershift#8355): GitHub's "list PR files" API silently caps at 3000 files, so the approve plugin never evaluated files past the cap against OWNERS.
  • Adds ChangedFiles to the PullRequest struct so the (always accurate) count on the PR object can be compared with what the files endpoint actually returned.
  • New getFilenames helper: calls GetPullRequestChanges; if the returned count is less than ChangedFiles, returns (nil, true, nil) to signal truncation. No recovery attempt.
  • On truncation: posts an [ApprovalNotifier] "NOT APPROVED" comment (deduplicated), removes a bot-added approved label (human-applied labels preserved), returns nil.
  • PRs ≤3000 files keep byte-identical behavior — single API call, zero overhead.

Findings

BlockingThe pull_request_review path is inert — the bypass stays open there

pkg/plugins/approve/approve.go:284, pkg/plugins/approve/approve.go:378

handleReview seeds changedFiles from re.PullRequest.ChangedFiles, and GitHub's reduced PR object in the pull_request_review payload carries no changed_files. Confirmed against this repo's own fixtures: cmd/phony/examples/review_approve_submitted.json has zero occurrences of changed_files, while opened_pr.json has one. So pr.changedFiles == 0, the expectedFiles > 0 guard short-circuits, and truncated is always false on that path.

changedFiles: re.PullRequest.ChangedFiles,
...
if expectedFiles > 0 && len(filenames) < expectedFiles {
    return nil, true, nil
}

Scenario: repo sets ignore_review_state: false; an approver submits an APPROVE review on a 5000-file PR; handle runs with the truncated file list and applies approved — exactly the bypass this PR exists to close. handleGenericComment (line 210, fed by GetPullRequest) and handlePullRequest (line 343, full PR in payload) are fine. Fix: give handleReview its own ghc.GetPullRequest call, or make the guard treat 0 as unknown rather than as not truncated.

Should fixTruncation detection false-positives on any count shortfall

pkg/plugins/approve/approve.go:378

expectedFiles is a snapshot (webhook payload, or a GetPullRequest issued before the GetPullRequestChanges call), so it can legitimately exceed the live file count. Scenario: author pushes commit A (100 files), force-pushes B (5 files) seconds later; the hook processes the synchronize event for A after B landed → 5 < 100 → truncated == true on a 5-file PR. The plugin then refuses to compute approval, posts the "exceeds the GitHub API limit of 3000 files" comment, and strips approved. Additionally requiring len(filenames) >= 3000 would confine the branch to actual cap hits. (Previously logged under "checked" as a self-healing transient — it does self-heal on the next event, but the wrong comment plus label removal is real user-visible damage.)

Should fixWarning message asserts a fact the code never verified

pkg/plugins/approve/approve.go:384-391

The message hardcodes "changes %d files, which exceeds the GitHub API limit of 3000 files" with pr.changedFiles interpolated, but the branch is reachable at any count (see above). Anyone hitting the force-push race gets a comment claiming their 100-file PR exceeds 3000 files, plus an unexplained label removal. Either gate the branch on the real cap, or word the message so it does not assert a threshold the code did not check.

Should fixWasLabelAddedByHuman error path fails open

pkg/plugins/approve/approve.go:472-476 vs pkg/plugins/approve/approve.go:574-577

On error the truncation path logs and return nil, leaving a bot-applied approved label in place on a PR whose OWNERS coverage is admittedly unknown — the stale approval the commit message says it prevents. A transient GitHub 5xx is enough, and nothing retries, so the label survives until the next event. The normal path's humanAddedApproved treats the same error as "not human-approved" (fails closed).

humanApproved, err := ghc.WasLabelAddedByHuman(pr.org, pr.repo, pr.number, labels.Approved)
if err != nil {
    log.WithError(err).Errorf("Failed to check ... preserving existing label state.")
    return nil
}

Was a question in the previous review; the asymmetry lands on the unsafe side, so raising it. Align the two, or document why preserving the label wins here.

Should fixTest coverage is thin for a security fix

pkg/plugins/approve/approve_test.go:1405-1459

Only one truncation test remains (TestHandleTruncatedFileList), covering the truncated direction only. Every pre-existing TestHandle case constructs state{} without changedFiles, so they all run with expectedFiles == 0 and skip the new check entirely — no case asserts that normal approval still happens with changedFiles: len(files), which is what would catch an off-by-one or inverted comparison. Also missing: the dedup path (second handle run with an identical existing truncation comment must not delete/recreate) and the humanApproved == true label-preserve path. Note the fgc.PullRequests entry added in newFakeGitHubClient (line 80) is never consumed — handle does not call GetPullRequest.

NitNotification churn on large PRs

pkg/plugins/approve/approve.go:456-470

msg embeds pr.changedFiles, so the "is this comment already posted" comparison (!strings.Contains(latestNotification.Body, msg)) is count-sensitive. Every push that changes the file count (5001 → 5002) makes the bodies differ, deleting all prior notifications and posting a fresh one — a new email per push on precisely the giant PRs this targets. Matching on a count-free prefix avoids it. Separately, the delete-then-create ordering means a failed CreateComment leaves the PR with no approval notification at all and only a log line.

NitUnused fetches on the truncation path

pkg/plugins/approve/approve.go:443-450

ListPullRequestComments and ListReviews are fetched before the truncation early-return but unused there. Checking truncated earlier saves two paginated calls on exactly the PRs that are already in an exceptional path.

NitDuplicated notification lifecycle logic

pkg/plugins/approve/approve.go:456-470 vs pkg/plugins/approve/approve.go:536-550

The truncation block re-implements the filter-notifications / compare-latest / delete-all / create-new pattern from the normal flow; two copies in one function will drift. Extract a shared helper.

Nitfakegithub client now reports every PR as truncated

pkg/github/client.go:2502-2504

GetPullRequestChanges returns an empty slice when c.fake is set, so any code path built on github.NewFakeClient() now sees 0 < changed_files and reports truncation. Does not appear reachable from production hook wiring, but it is a new behavioral coupling worth knowing about.

if c.fake {
    return []PullRequestChange{}, nil
}

QuestionDirection vs discussed plan

overall approach; cf. review #4463008939

Review #4463008939 (petr-muller, 2026-06-09, on commit decefa02a) proposed a specific three-part plan. The shipped code diverges on all three points:

  1. "Make GetPullRequestChanges detect the case and return error... any caller will need to handle the case appropriately." Not done — pkg/github/client.go:2499 GetPullRequestChanges is unchanged, no crosscheck, no error. Detection lives privately in the approve plugin's getFilenames instead, so the ~15 other callers (blockade, verify-owners, owners-label, blunderbuss, trigger, ...) remain exposed to the same silent truncation.
  2. "Any caller is advised to do GetPullRequest first... to avoid calling potentially paginated GetPullRequestChanges that's doomed to fail." Not implemented — the plugin always calls GetPullRequestChanges first and compares after the fact; there's no pre-check that skips the paginated call once the count is already known to be over the cap. handleReview doesn't call GetPullRequest at all (see the blocking finding above).
  3. "The approve plugin would fall back to root-level approver instead of handling the actual paths as normal." Not implemented — shipped code fully blocks on truncation (NOT APPROVED comment, strip bot-applied label, require manual admin re-approval). No root-approver fallback logic exists in this PR; that direction only exists in the reviewer's prototype petr-muller/prow:707-explore (commit 3e3c66a3c).

Also moot: the review's ask to handle GetSingleCommit similarly no longer applies, since the entire commit-based fallback that used it was deleted rather than fixed. Net: a materially simpler, more conservative implementation (detect-and-block, plugin-local) than what was requested (detect-and-degrade-to-root-approver, client-level). Confirming whether this is accepted as the final direction or an interim step.

Things I checked and was fine with

  • go test ./pkg/plugins/approve/... passes on f8fb3fd1a.
  • Fast path is byte-identical for ≤3000-file PRs: single GetPullRequestChanges call, zero extra API calls.
  • The truncation comment uses approvers.ApprovalNotificationName and matches notificationRegex — participates in existing notification dedup/replace lifecycle. (Dedup is count-sensitive — see churn nit.)
  • No config/CRD/flag/RBAC/scope changes; ChangedFiles struct field is additive; rollback is a plain image revert. Deployment risk LOW.
  • Detection compares against PR.ChangedFiles, not a hardcoded 3000 — resilient to GitHub changing the cap, though this is also what makes the shortfall check over-trigger.
  • Human-applied approved labels are never removed when WasLabelAddedByHuman succeeds.
  • API cost reduced vs previous revision: no more up-to-11-call fallback; truncation handling adds zero extra API calls beyond GetPullRequestChanges.
  • Returning nil from the truncation path keeps hook error metrics clean.
  • Tests are behavioral (drive handle() through fakegithub; no new mocks).
  • Change cleanly revertible: one struct field plus plugin-local code.
  • handleGenericComment (line 210) and handlePullRequest (line 343) both populate changedFiles from sources that actually carry it — only handleReview is affected.
