REQUEST CHANGES

The resolution mechanics are clean and well-tested, and backward-compatible parsing is handled correctly. But the PR changes the behavior of existing configs in ways that silently expand trust (previously-inert empty-repos triggers become global; repo triggers no longer shadow org-level trusted apps), and the locked guarantee can be silently defeated by an unvalidated duplicate at the same level. These need at minimum explicit migration callouts and validation before merge; the rest is polish.

What this PR does

  • Replaces TrustedApps []string on Trigger with a structured TrustedApp type (name, untrusted, locked); custom UnmarshalJSON keeps legacy string lists parsing, including mixed arrays.
  • Rewrites TriggerFor as a single pass that both picks the most specific trigger (repo > org > defaults, first match wins) and accumulates trusted apps at global (empty repos), org, and repo levels.
  • Adds resolveTrustedApps: lower levels override upper ones per app unless the upper level set locked; repo level can never lock. The flat resolved list is stored in unexported resolvedTrustedApps and read via GetTrustedApps().
  • Migrates all five call sites (generic-comment.go, pull-request.go, verify-owners.go, welcome.go, retitle.go) to the accessor.
  • Adds ValidateLockedTrustedApps() wired into checkconfig as the optional validate-locked-trusted-apps warning, flagging lower-level entries that mention apps locked above them.

Findings

blocking Existing configs silently expand trust on upgrade

pkg/plugins/config.go:1139-1177 — TriggerFor

Two behavior changes hit unmodified existing configs. (a) Triggers with empty repos were previously inert — the old TriggerFor set lookups never matched an empty set, and no validation rejects such entries — but now become the global level and grant trust instance-wide. A forgotten or mistaken entry that was harmless for years activates on upgrade. (b) A repo-level trigger previously shadowed the org trigger entirely; now trusted apps merge across levels, so a repo that deliberately defined a narrow list also inherits every org/global app.

Trusted apps gate automatic CI execution on PRs, so both broaden trust implicitly. Needs at least a prominent release-note/migration callout; ideally the global level requires explicit opt-in (a distinct config key) rather than reinterpreting previously-dead entries.

case len(trigger.Repos) == 0:
    globalApps = append(globalApps, trigger.TrustedApps...)
should fix Same-level duplicates silently drop locks

pkg/plugins/config.go:1188-1204 — resolveTrustedApps

The lock check only protects against lower levels; within a level, entries overwrite unconditionally. Two global triggers both naming app1 — first {locked: true}, second {untrusted: true} (perhaps added later in a different config file) — the second wins and the lock vanishes. validateTrustedApps only dedupes within a single trigger's list; cross-trigger same-level duplicates are unvalidated. Since locked is a security guarantee, it being defeatable by an unflagged duplicate undermines the feature. Either honor locks within a level or validate cross-trigger duplicates per level.

for _, app := range globalApps {
    state[app.Name] = &trustedAppState{  // no lock check — last wins
        trusted: !app.Untrusted,
        locked:  app.Locked,
    }
}
should fix ValidateLockedTrustedApps flags agreement as violation

pkg/plugins/config.go — ValidateLockedTrustedApps

It checks only name membership, not whether the lower level actually conflicts with the locked value. Global locks app1 as trusted; an org also lists app1 as trusted (same value) — flagged anyway. Noisy for a warning users opt into. Also a self-flagging edge: a single trigger with Repos: ["myorg", "myorg/myrepo"] and a locked app populates orgLocked from itself, then its own repo entry is flagged against its own lock. Comparing effective trust values instead of name presence fixes both.

should fix locked: true at repo level is silently ignored without validation

pkg/plugins/config.go:1205-1213 (resolve) and validateTrustedApps

The repo-level arm of resolveTrustedApps drops Locked by design (commented), but validateTrustedApps neither errors nor warns when a repo-level entry sets it. The user gets no feedback that the field is meaningless there.

// locked is not set here: repo is the lowest level, so there is nothing to lock against.
state[app.Name] = &trustedAppState{trusted: !app.Untrusted}

question Mixed repos lists get level-classified per lookup

pkg/plugins/config.go:1145-1163 — TriggerFor switch

A trigger with Repos: ["myorg", "myorg/myrepo"] counts as repo-level for myorg/myrepo (the repo case wins in the switch, so its locked is dropped there) but org-level for sibling repos. Surprising classification; consider documenting it or warning on mixed org+repo lists.

question GetTrustedApps() returns nil without TriggerFor

pkg/plugins/config.go:599-603

resolvedTrustedApps is only populated by TriggerFor; a directly constructed Trigger returns nil even with TrustedApps set. It fails closed (no apps trusted) — the correct security default, so low risk — but a doc comment on the TrustedApps field warning against reading it directly would help future callers.

func (t *Trigger) GetTrustedApps() []string {
    return t.resolvedTrustedApps
}
question DCO plugin's TrustedApps []string may confuse readers

pkg/plugins/config.go:897, pkg/plugins/dco/dco.go:301

DCO has its own flat TrustedApps []string, unrelated to the trigger type; config.TrustedApps in dco.go:301 looks like a missed migration at a glance. A clarifying comment on the DCO field would help. Whether DCO should adopt the hierarchical type is separate-PR scope.

Open questions for the author

  • Should the global level require explicit opt-in (a distinct config key) instead of reinterpreting previously-inert empty-repos triggers?
  • Is merge-across-levels intended to apply to existing repo triggers that previously shadowed org trusted_apps? If so, should release notes call out the trust expansion?
  • Should locks be honored (or duplicates rejected) within the same level, given two same-level triggers can currently drop a lock silently?
  • Should ValidateLockedTrustedApps compare effective trust values rather than flagging any name overlap (which flags agreement and can self-flag mixed-repos triggers)?
  • Should locked: true on a repo-level entry be a validation error?
  • Should DCO's separate TrustedApps []string eventually adopt the hierarchical type? (Separate PR, just flagging.)
