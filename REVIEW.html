Request Changes

The structural direction is correct — replacing the env-var escape hatch with proper plugin config follows established Prow patterns faithfully. Two issues block merge: (1) issueClosingKeywords is accepted and validated in config but the runtime never reads it — a silent no-op that will mislead operators. (2) The default for fixup commit checking has been silently reversed from opt-in to opt-out, which will activate the check for all existing deployments that did not previously set ENABLE_FIXUP_CHECK=true. Both were independently flagged by all three reviewers.

What this PR does

  • Introduces InvalidCommitMsg / InvalidCommitMsgCheck structs in plugins.Configuration, allowing per-check enable/disable control via plugins.yaml.
  • Implements InvalidCommitMsgFor(org, repo) with two-pass repo-then-org precedence lookup, consistent with LgtmFor, ApproveFor, TriggerFor.
  • Replaces os.Getenv("ENABLE_FIXUP_CHECK") with cfg.IsCheckDisabled("fixupPrefix") in handle().
  • Adds validateInvalidCommitMsg() with check-name allowlisting and wires it into Configuration.Validate().
  • Refactors tests from t.Setenv to config struct construction; updates plugin help text.

Maintainer Advisor — Suggested PR Comment

Summary for PR Comment

The structural direction here is correct — replacing the env-var escape hatch with a proper config surface follows established Prow patterns and the implementation mirrors ApproveFor/LgtmFor faithfully. However, two issues need to be resolved before merge. First, the default for fixup commit checking has been silently reversed: the old code was opt-in (env var must be explicitly true), but the new code is opt-out (fixup checking is on unless explicitly disabled in config), which will silently activate the check for all existing deployments that relied on the absence of ENABLE_FIXUP_CHECK. This needs to be either reverted to opt-in semantics or explicitly documented and communicated as a breaking behavior change. Second, issueClosingKeywords is registered as a valid config name and documented as disableable, but IsCheckDisabled("issueClosingKeywords") is never called in handle() — an operator who configures it will see no effect. Please either wire it into the implementation or remove it from the validated set. Happy to approve once those two points are addressed.
