Verdict: request changes

The full-tree htmltest repair and dependency pin are sound, but the new routine verifier calls the networked external-link scan rather than the deterministic internal-only target it introduces. Make that small wiring correction before merging. CI integration is explicitly deferred and should remain a follow-up.

What this PR does

  • Builds the documentation site, then scans the generated tree once with htmltest.
  • Configures htmltest to resolve absolute links from public and removes broad internal-link ignores.
  • Pins htmltest in hack/tools and adds a top-level verify-links target.
  • Adds an internal-only htmltest target and excludes generated site output from unrelated repository checks.

Findings

Blocking — Routine verifier runs the external-link scan

hack/make-rules/verify/links.sh:51; site/Makefile:33-38

make check-broken-links HTMLTEST="${HTMLTEST}"

check-broken-links-internal:
    $(HTMLTEST) -s -c .htmltest.yml

verify-links calls the full checker, not check-broken-links-internal. External failures are warnings, but requests still happen, leaving the normal verifier slow and network-dependent. Its success message also says only internal links were checked. Use the internal target here and keep external checks separately named for manual or periodic use.

Question — What will exercise this target before the planned CI job exists?

Makefile:109-111; hack/make-rules/verify/all.sh:26-70

verify-links:
    hack/make-rules/verify/links.sh

The target is not included in make verify or an existing workflow. The PR deliberately defers CI because the current image lacks Hugo and Node; confirm manual use is intended until a dedicated internal-link presubmit or periodic job lands.

Question — Should the local Hugo requirement match the production build?

hack/make-rules/verify/links.sh:23-27; netlify.toml:7-9

if ! command -v hugo >/dev/null 2>&1; then
  echo "ERROR: hugo is required to build the site before checking links."
fi

The verifier accepts any Hugo on PATH, while Netlify uses Hugo 0.147.8. Validating the extended edition and version, or using a pinned environment, would align local verification with the deployed build.

Things I checked and was fine with

  • The generated site is scanned once with DirectoryPath: public; the obsolete per-file wrapper is removed.
  • The pinned htmltest module builds with go build -mod=readonly github.com/wjdp/htmltest.
  • The internal-only target passes -s to htmltest as intended.
  • git diff --check is clean.
  • Generated site output is excluded from the existing spelling and shell-permission checks.

Open questions for the author

  • Is make verify-links intended to be deterministic and internal-only, with external URLs checked by a distinct manual or periodic target?
  • Until a CI image with Hugo and Node is selected, who or what is expected to run verify-links?
  • Should the verifier enforce the Hugo extended version used by Netlify?
