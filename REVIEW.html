Verdict: Request changes

The exclusion mechanism itself is sound — correctly wired to the actual error-wrapping chain used by tryMerge/mergePRs, properly synchronized against the real concurrent sync-loop pattern, collision-safe in its key scheme, and covered by genuine end-to-end regression tests (suite and go vet both pass). But takeAction applies the new filter in only two of its four decision points. The serial-trigger gate still tests unfiltered successes, so an excluded PR continues to starve other PRs of serial tests — the same head-of-line blocking #673 describes, moved one step downstream. Separately, an already-successful batch is merged without consulting exclusions at all, contradicting the doc comment that claims that case is handled. Both are small, local fixes.

What this PR does

  • Fixes #673: takeAction() deterministically re-picks the lowest-numbered PR from successes every cycle; if it fails with UnmergablePRError (e.g. branch protection needs more approvals), it blocked the whole merge queue forever.
  • Adds syncController.mergeExclusions map[string]int keyed by org/repo#number@sha, with mutex-guarded excludeFromMerge/isExcludedFromMerge/filterExcludedFromMerge.
  • isUnmergableError() unwraps *mergeFailure → mergeErr.err → fmt.Errorf-wrapped github.UnmergablePRError via errors.As.
  • takeAction() filters successes before pickHighestPriorityPR and records an exclusion on unmergeable failure; pickBatch filters candidates, and excludeUnmergablePRsFromBatch records per-PR exclusions after a failed batch merge.
  • Entries age via ageMergeExclusions() once per Sync() (mergeExclusionSyncs = 3). The SHA-scoped key means a new push auto-clears the exclusion without waiting for it to age out.

Should fix

should fixpkg/tide/tide.go:1741

Serial-trigger gate still tests unfiltered successes, so an excluded PR keeps blocking other PRs' tests. The direct-merge branch filters into eligible, but the fall-through condition still reads len(successes) == 0 using the original slice — so a PR excluded from merging still counts as a "success" that suppresses serial test triggers. Concretely: the pool holds PR #1 (green, permanently rejected by branch protection) and PR #2 (missing required presubmits). #1 is excluded, eligible is empty, so we fall through — but len(successes) == 1, so #2's presubmits are never triggered, and pickBatch can't rescue it since #2 isn't retest-eligible. This is the same class of head-of-line blocking the PR set out to fix. Gate on eligible instead.

should fixpkg/tide/tide.go:1695, doc comment at 615-621

Pre-existing batch merges bypass the exclusion set entirely. takeAction merges batchMerges unconditionally — only pickBatch (new batch selection) and the single-merge path run through filterExcludedFromMerge. batchMerges comes from accumulateBatch, which returns any still-valid successful batch ProwJob, so a batch containing an excluded PR is retried whole every cycle. The practical exposure is narrower than it first looks: if the excluded PR's batch-mates merge successfully they leave the pool, invalidating the batch refs, so sustained retry requires every other batch member to also fail transiently on the same cycle. What is unambiguously wrong either way is the doc comment on excludeUnmergablePRsFromBatch, which asserts this case is handled ("whether the batch is retried whole or the PR resurfaces in a later batch"). Either filter batchMerges (skipping the batch if any member is excluded) or correct the comment.

// Merge the batch!

Nits

nitpkg/tide/tide.go:670

ageMergeExclusions() ages on syncs that never attempt a merge. It is the first statement of Sync(), before provider.Query(), blockers() and dividePool(), and it also ages during syncs where the subpool is PoolBlocked and takeAction is never reached. Three consecutive syncs failing on failed getting blockers will expire an exclusion having granted Tide zero actual opportunities to advance. Aging after the subpools are synced — or only counting cycles in which takeAction ran — would match the documented intent. Low impact: worst case the PR is retried one cycle early.

pickBatch log message misattributes an exclusion to failing tests. The filter is applied to candidates immediately before the empty check, but the message still says the PRs weren't passing tests — when in fact they did pass and were merge-excluded. An operator debugging "why is no batch being created" gets pointed at CI instead of at the exclusion. Distinguish the two causes, or move the filter after the check.

nitpkg/tide/tide.go:588 vs 1673

Per-cycle skip is logged at Debug while the original exclusion is Warning. No history record is written for the skips either, and the PR's Tide status context still reports it as in the merge pool — so the author sees a green, "in merge pool" PR that Tide silently declines to touch, and an operator investigating days later (after the Warning aged out of retention, with Debug off in production) has nothing to go on. Questions

questionpkg/tide/tide.go:519

Should mergeExclusionSyncs (3 cycles, hardcoded) be configurable? For large multi-tenant installations, a branch-protection misconfiguration can take a human longer than three sync cycles to notice and fix, causing the PR to flap in and out of the queue with repeated Warning logs. A Tide config knob and/or a tide_merge_exclusions_active metric would give operators visibility without a code change. The switch from wall-clock TTL to cycle count also makes the window's real-world duration depend on the configured sync period — worth documenting if not made configurable.

Things I checked and was fine with

  • go test ./pkg/tide/... and go vet ./pkg/tide/ both pass (the previous pass had no Go toolchain and relied on static tracing only).
  • Traced the full error-unwrap chain end-to-end: tryMerge() wraps github.UnmergablePRError as fmt.Errorf("PR is unmergable...: %w", err) → GitHubProvider.mergePRs() wraps into &mergeFailure{errs: []mergeErr{...}} → isUnmergableError() type-asserts *mergeFailure, recurses into me.err, falls back to errors.As. Matches the real runtime error shape.
  • errors.As works against github.UnmergablePRError (value receiver on Error()), and correctly does not match the distinct UnmergablePRBaseChangedError, UnauthorizedToPushError or MergeCommitsForbiddenError types — the predicate isn't overly broad.
  • Key scheme is collision-safe: o/r#1@ cannot prefix-match o/r#12@, so the prior-SHA cleanup loop in excludeFromMerge won't delete unrelated PRs' entries.
  • Aging arithmetic matches the constant: a PR excluded during sync N is skipped for N+1..N+3 and retried at N+4. The remaining > 0 check in isExcludedFromMerge is dead (zero-valued entries are deleted) but harmless.
  • SHA-keyed invalidation genuinely works: filterExcludedFromMerge checks the current HeadRefOID, so a force-push clears the exclusion immediately.
  • mergeExclusionsMu is the correct primitive and correctly scoped: syncSubpool runs concurrently across org/repo/branch subpools, locking is flat (no nested acquisition between filterExcludedFromMerge and isExcludedFromMerge), and syncController is only used through a pointer, so the added mutex introduces no copylock issue.
  • takeAction only calls mergePRs with a single-element slice on the non-batch path, so mergeFailure.errs has exactly one entry there — no ambiguity about which PR triggered the exclusion.
  • New tests (TestTakeActionSkipsExcludedPRs, TestIsUnmergableError, TestMergeExclusionAging, TestExcludeFromMergeReplacesPriorSHA, TestTakeActionExcludesPRThatFailsInBatch, TestPickBatchExcludesMergeExcludedPR) are structurally consistent with existing helpers; the two takeAction ones are genuine end-to-end regression tests, not unit tests of map internals.
  • Feature is GitHub-only (Gerrit provider untouched), consistent with the PR's stated scope. No config/API/schema changes; all state is in-memory and lost on restart, so the change is drop-in and safely revertible.

  • Should batchMerges be filtered through filterExcludedFromMerge as well, or is the "batch retried whole" case considered unreachable in practice? If the latter, the doc comment on excludeUnmergablePRsFromBatch should be narrowed, since it currently claims that case is covered.
