Verdict: Approve (with suggestions)

Reviewed via three independent maintainer perspectives (code quality, maintainability, deployment risk) plus an advisor synthesis. No critical issues surfaced from any angle. The strongest signal is convergent: all three reviewers independently flagged that pickLowestPriorityPR doesn't actually consider configured Tide priority tiers despite its name suggesting otherwise. This and the other findings below are worth addressing as fast-follows but don't block merging a small, low-risk, easily-revertible fix for a real reported bug (#474).

What this PR does

  • Adds a third return value, failedBatch, to accumulateBatch, populated from ProwJobs in failureState (previously silently dropped).
  • Adds pickLowestPriorityPR: picks the highest-numbered (newest) PR from a list, and withoutPR: returns a copy of a PR list excluding one PR by number.
  • takeAction now takes a batchFailed parameter; when non-empty, it excludes the lowest-priority PR from the pool before re-picking a batch, bisecting instead of repeating the identical failing combination.
  • Reuses all existing batch-selection code paths (pickBatch/pickNewBatch) rather than adding a parallel mechanism — keeps the change small and additive.
  • Test suite updated for the new signatures, plus two new test cases.

should-fixpickLowestPriorityPR name/semantics conflict with pickHighestPriorityPRflagged by all 3 reviewers
pkg/tide/tide.go:934-947

This is the strongest-confidence finding in the review — independently raised by code quality, maintainability, and deployment risk. pickHighestPriorityPR honors config.Tide.Priority label-tier configuration. pickLowestPriorityPR only ever compares pr.Number, ignoring configured priority tiers entirely. Operators relying on priority labels for hotfix/release-blocking PRs could see one excluded from a batch for reasons unrelated to its configured priority. Rename (e.g. pickNewestPR) and/or document explicitly that it's PR-number-only.

func pickLowestPriorityPR(prs []CodeReviewCommon) (bool, CodeReviewCommon) {
	if len(prs) == 0 {
		return false, CodeReviewCommon{}
	}
	result := prs[0]
	for _, pr := range prs[1:] {
		if pr.Number > result.Number {
			result = pr
		}
	}
	return true, result
}
should-fixNondeterministic failedBatch selection with multiple failed refsflagged by 2 reviewers
pkg/tide/tide.go:1059-1067

Flagged by code quality and deployment risk. The assignment loop iterates a Go map (states), randomized order, and overwrites failedBatch on every matching ref. This PR's own bisection behavior makes multiple simultaneously-failed batch ProwJobs more likely (an older full-size failing batch can persist for hours until GC while a newly-triggered smaller batch also fails) — so a different PR could be excluded on different sync cycles purely due to map iteration order. This now drives real bisection behavior, not just logging.

questionBehavioral shift for operators relying on manual /hold recovery
deployment risk

Tide now auto-retries a smaller batch on every batch CI failure with no opt-out/feature-gate, whereas previously a failed batch fell through to MergeBatch regardless of error and some operators may have built manual /hold-based runbooks around unsticking it. Worth a release-note mention; not a merge blocker since the new behavior is strictly better and safely revertible.

Things I checked and was fine with

  • withoutPR allocates a new slice and does not mutate its input.
  • batchSP := sp is a struct copy; reassigning batchSP.prs does not affect sp.prs (safe today, though a shallow copy could become a hazard if subpool gains pointer/map fields later).
  • pickLowestPriorityPR's "highest number = lowest priority" assumption matches pickHighestPriorityPR's convention and pickBatch's own oldest-first ordering.
  • The if len(batch) > 1 guard downstream correctly prevents triggering a degenerate single-PR "batch" if bisection reduces the pool below 2 candidates.
  • No security-relevant changes; purely internal control-flow/data structure changes, no config/API/CRD/RBAC changes.
  • Behavior is unchanged when no batch has failed — backward compatible, zero upgrade friction; rollback is safe.
  • Bisection is self-terminating (monotonically shrinks the batch), with defensive empty-input handling in both new helpers.

Open questions for the author

  • Should pickLowestPriorityPR respect config.Tide.Priority labels like pickHighestPriorityPR does, or is ignoring them intentional for bisection? If intentional, a comment explaining why would help future readers.
  • Can multiple failed-batch ProwJobs coexist in practice given this PR's own behavior, and if so, should selection be made deterministic (e.g. most recent StartTime, or largest) instead of relying on map iteration order?
  • Does the exclusion of PR N eventually get "forgotten" once the smaller batch succeeds, or can a stale failed ProwJob keep PR N excluded indefinitely?
