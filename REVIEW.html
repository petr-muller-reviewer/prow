Review: kubernetes-sigs/prow#530

github: enable dry-run mode when using apps auth
Head: 37d005f2 Base: main Reviewed: 2026-06-15T12:16:44Z (refreshed; no code changes)

Verdict

APPROVE
The code is correct and safe: the allowlist enforcement is sound, testing is thorough, and mutations remain blocked in dry-run mode. One issue should be addressed before or just after merge: the PR title and description misrepresent scope — the change lives in the shared GitHub client, affecting every Prow component using GitHub Apps auth with --dry-run, not only Peribolos. The remaining findings are nits.

What this PR does

  • Adds an allowInDryRun bool field to the internal request struct in pkg/github/client.go; when set, the dry-run gate is bypassed for that specific request.
  • Sets allowInDryRun: true on exactly one call site: the GitHub Apps token acquisition POST (/app/installations/{id}/access_tokens).
  • Adds a hardcoded allowlist check: if allowInDryRun is set but the URL does not match the expected Apps token endpoint, a SECURITY: error is logged and the flag is ignored.
  • Before this change, any Prow component using --dry-run with GitHub Apps auth failed at token acquisition; now acquisition succeeds and all downstream mutations remain blocked.
  • Adds 409 test lines, including TestAllowInDryRunEnforcesAllowlist covering the security boundary.

Findings

resolved Title and description misstate scope of change
pkg/github/client.go — shared infrastructure, not Peribolos code
The change lives in the shared GitHub client used by every Prow component. Any component running --dry-run with GitHub Apps auth is affected — not just Peribolos. The PR title ("Peribolos: enable dry-run mode…") and description do not disclose this. The description should explicitly state that this is a client-layer change with system-wide effect.
Resolved: PR title updated to "github: enable dry-run mode when using apps auth" reflecting the pkg/github scope.
question Behavioral change for non-Peribolos components in dry-run + GH Apps
pkg/github/client.go:932–950 — request execution path
Before this PR, any Prow component using --dry-run + GH Apps failed immediately at token acquisition. After, they acquire a token and proceed until the first blocked mutation. The code path between successful auth and the first mutation call is untested for components other than Peribolos. Have Tide, Sinker, Crier, etc. been considered? Are there observable side effects (API reads, non-POST mutations, metrics, logging) in that window?
nit Allowlist violation does not fail loudly in test/dev builds
pkg/github/client.go:950
Misuse of allowInDryRun: true on a non-allowed endpoint logs a SECURITY: error and silently falls back to blocked. Correct for production; in test or dev builds a panic would surface accidental misuse earlier.
nit URL pattern matching is fragile and lacks boundary-case tests
pkg/github/client.go — allowlist check
The allowlist uses strings.Contains("/app/installations/") and strings.HasSuffix("/access_tokens") inline, not as a named constant. No test verifies that a near-miss URL (e.g. /apps/installations/{id}/tokens) is correctly rejected. If GitHub changes the endpoint path, the allowlist silently stops working.
nit Dry-run condition readability
pkg/github/client.go:932–934
The compound boolean involving allowInDryRun and c.dry lacks explicit parentheses. Intent requires careful reading to disambiguate operator precedence.

Things I checked and was fine with

  • Defense in depth: both the allowInDryRun flag AND the hardcoded allowlist check must pass for the carve-out to apply.
  • TestAllowInDryRunEnforcesAllowlist correctly exercises the allowlist enforcement at the security boundary.
  • Backward compatibility: PAT users see no behavioral change; all mutation endpoints remain blocked in dry-run regardless of this change.
  • Only one call site sets allowInDryRun: true; the ~96 other request creation sites are unaffected.
  • No API, configuration schema, or CLI flag changes — zero deployment friction.

Open questions for the author

  • Can the PR description be updated to explicitly state that this is a pkg/github client-layer change affecting all Prow components, not just Peribolos? Other component owners may want to know their component's behavior changed. (Title now updated to reflect pkg/github scope; description update less critical.)
  • Have components other than Peribolos been considered or tested when running --dry-run with GH Apps auth? What happens in Tide, Sinker, Crier, etc. between successful token acquisition and the first blocked mutation — any reads or side effects that were previously short-circuited by the auth failure?
