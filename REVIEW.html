Approve — small, well-tested fix. All three maintainer-review perspectives (code quality, maintainability, deployment risk) independently confirmed the security-critical CSRF state-cookie path stays fail-closed and is explicitly regression-tested. Remaining feedback is minor polish, not blocking.

What this PR does

  • Changes four cookie-decode failure paths in pkg/githuboauth/githuboauth.go (HandleLogin, GetLogin, HandleLogout, HandleRedirect) from hard-erroring (500 response) to logging a Warning and continuing with the empty/fresh session gorilla/sessions returns.
  • Rationale: an undecodable cookie is expected to happen benignly whenever the CookieStore's signing keys are rotated — previously this broke login/logout for every affected user until their stale cookie expired.
  • Leaves the oauthSessionCookie state-validation decode in HandleRedirect (line 242) as a hard error, since that cookie is short-lived (10 min) and CSRF-relevant — losing it mid-flow is a genuine failure, not routine rotation.
  • Adds three new tests exercising the stale-cookie fallback behavior for HandleLogin and both HandleRedirect cookie paths, including one that locks in the still-fail-closed state-cookie behavior.
  • No config/schema/CLI/RBAC changes; no overlap with the concurrently open PR #843 (gorilla/csrf removal in Deck), which touches unrelated files and explicitly retains gorilla/sessions.

Findings

Should fix

Should fixDecode-failure fallback conflates benign key rotation with persistent misconfiguration

pkg/githuboauth/githuboauth.go:159, 181, 200, 287

All four sites now log a Warning and silently continue on any decode error, whether the cause is a benign stale/rotated-key client cookie or a persistent server-side CookieStore misconfiguration — gorilla/sessions returns the same error for both. Previously these were Error-level + HTTP 500 via serverErrorAndPrint. If the store is ever broken store-wide, this now degrades silently instead of tripping error-rate/500 alerting. Confirmed independently by two of the three maintainer-review passes as a real (non-blocking) tradeoff.

if err != nil {

Nits

NitFallback pattern duplicated across 4 call sites

pkg/githuboauth/githuboauth.go:159, 181, 200, 287

The "log warning, fall through to already-returned empty session" pattern repeats near-verbatim at all four sites with only the message text varying. The file already centralizes the analogous log+respond pattern in serverErrorAndPrint/serverError; a future policy change here needs 4 lockstep edits.

NitLog message wording inconsistent across the four sites

pkg/githuboauth/githuboauth.go:159, 181, 200, 287

HandleLogin/HandleRedirect say "using new session" (accurate — they call New); GetLogin/HandleLogout omit that qualifier despite the same fallback behavior via Get. Cosmetic, flagged independently by two reviewers.

NitUndocumented reliance on gorilla/sessions non-nil-session invariant

pkg/githuboauth/githuboauth.go:159, 181, 200, 287

The fix depends on CookieStore.New/Get always returning a usable, non-nil *Session even on decode failure (verified against vendored gorilla/sessions v1.2.0). Not documented in a comment; a future library upgrade or internal change could silently reintroduce a nil-session panic risk. A one-line comment near the first changed site would future-proof this.

NitTest-fixture duplication across 3 new tests

pkg/githuboauth/githuboauth_test.go:373

TestHandleRedirectWithStaleCookie, TestHandleLoginWithStaleCookie, and TestHandleRedirectWithStaleOAuthSessionCookie each hand-roll ~15 identical lines building a stale-cookie fixture (old/new CookieStore, save with old key, extract Set-Cookie) instead of sharing one helper.

NitGetLogin's differing observable behavior is untested

pkg/githuboauth/githuboauth.go:178-186

Unlike the other three sites, an undecodable cookie in GetLogin falls through to a failed type-assertion, returning the generic "Could not find GitHub token" instead of the original decode error. None of the three new tests exercise GetLogin directly with an undecodable cookie.

Things I checked and was fine with

  • Nil-deref / wrong-session-reuse risk: refuted — gorilla/sessions v1.2.0 guarantees Get/New always return a valid, non-nil *Session even on decode error.
  • HandleRedirect's oauthSessionCookie state-validation decode (line 242-246) intentionally still hard-errors (CSRF-relevant, short-lived 10 min cookie) and is exercised by TestHandleRedirectWithStaleOAuthSessionCookie; correctly left unchanged, independently confirmed by all three maintainer-review perspectives.
  • No config/schema/CLI/RBAC changes; deployment risk assessed LOW, no breaking changes, safe to roll forward/back.
  • No overlap or conflict with PR #843 (cblecker, open, "replace gorilla/csrf with net/http.CrossOriginProtection") — unrelated CSRF middleware, explicitly retains gorilla/sessions/securecookie, touches no files in pkg/githuboauth/.
  • Adjacent pre-existing bug noted but out of scope: HandleLogin's client.WithFinalRedirectURL error path logs but doesn't return, leaving newClient nil for the next line — a latent panic, not introduced by this PR.
  • No project CLAUDE.md guidance applies to this path. No efficiency concerns found.
