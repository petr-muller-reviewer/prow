Verdict

Approve.

The fix is correct, well-scoped, and directly addresses the known limitation noted in #748. The new host-aware prefix lookup is strictly more robust than the old suffix-matching approach. The test exercises the exact failure scenario. Theoretical edge cases (port normalization, same-host-different-path bases) are practically impossible and are not regressions from this PR.

What this PR does

  • Replaces the pagination prefix computation in readPaginatedResultsWithValuesWithContext: instead of suffix-matching resp.Request.URL.Path against the Link header path (fragile when redirects change the path), it matches the Link URL's host against c.bases and extracts the path component from the matching base entry.
  • This makes GHE pagination immune to redirects (e.g. repo renames) because the prefix is derived from the host, not from path arithmetic that breaks when the response path differs from the request path.
  • Removes 9 lines (the old pathOnly/TrimSuffix logic and outdated comments) and adds 15 lines (the host-matching loop and updated comments).
  • Adds TestReadPaginatedResultsWithGHEAndRedirect: a 63-line test that sets up a TLS server simulating a GHE instance with /api/v3 prefix, a 301 redirect (repo rename), and two-page pagination. Verifies all three requests fire and both pages are collected.

Findings

No findings. All candidates from the review were refuted during verification.

Things I checked and was fine with

  • Correctness of host matching: url.Parse on c.bases entries produces the expected Host and Path fields. For github.com (https://api.github.com), Path is empty, so TrimPrefix is a no-op. For GHE (https://ghe.com/api/v3), Path is /api/v3, correctly stripped.
  • Fallback behavior: If no base matches (prefix stays empty), TrimPrefix(requestURI, "") returns the full URI. The safety check on line 2050 preserves it if it starts with /. For github.com this is correct; for GHE it would re-duplicate, but only under a configuration error (Link host doesn't match any base). This is not a regression — the old code had the same failure mode.
  • Error handling: url.Parse failures on bases are silently skipped (err == nil guard). This is appropriate — invalid bases would already fail on the request construction side.
  • First-match semantics: The loop breaks on first host match. Multiple c.bases entries exist for failover/load-balancing across distinct hosts, not same-host-different-path, so first-match is correct.
  • Test coverage: The existing TestReadPaginatedResultsWithRedirect covers non-GHE redirect. The existing TestReadPaginatedResultsWithGHE covers GHE without redirect. The new test covers GHE + redirect. The matrix is complete.
  • No callers affected: The function signature and return type are unchanged. The change is internal to the pagination loop.
  • Port normalization: Theoretically api.github.com vs api.github.com:443 would not match, but GitHub never emits explicit default ports in Link headers and c.bases entries don't include them. Not a practical concern.
