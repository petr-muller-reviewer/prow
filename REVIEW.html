Verdict

Request changes

Docs-only PR (already merged, LGTM'd). A 3-perspective maintainer review (code quality, maintainability, deployment risk) independently converged on the same core defects: a fabricated CLI flag and a self-contradictory rate-limit claim, plus incorrect/overgeneralized throttling defaults that don't hold for several of the very components the PR documents. Recommend a fast follow-up PR to correct these before operators rely on the page.

What this PR does

  • Adds site/content/en/docs/github-api-access.md: central operator doc covering GitHub auth (PAT vs GitHub App), rate-limit management (client-side throttling, ghproxy), and endpoint configuration (REST/GraphQL/Search).
  • Adds short "GitHub API Access" sections to hook, crier, deck, tide, branchprotector, status-reconciler docs, each linking back to the central page.
  • Docs-only change, +115/-3 across 7 files.

Findings

Blocking

BlockingSelf-contradictory rate-limit comparison

site/content/en/docs/github-api-access.md — GitHub App Authentication section

States "GitHub Apps receive higher API rate limits (5,000 requests/hour per installation vs 5,000/hour for personal tokens)" — the same number on both sides of a claimed contrast. GitHub App installation limits actually scale with the number of repos/users covered (baseline higher than 5,000, commonly 12,500–15,000+).

- **Higher rate limits:** GitHub Apps receive higher API rate limits (5,000 requests/hour per installation vs 5,000/hour for personal tokens)
Convergence: flagged independently by all three maintainer-review perspectives (code quality, maintainability, deployment risk).

BlockingFabricated flag --github-search-endpoint

site/content/en/docs/github-api-access.md — Configuring Components to Use ghproxy section

--github-search-endpoint does not exist anywhere in the codebase (checked pkg/flagutil/github.go and grepped all .go files). Search requests use the same REST base configured by --github-endpoint. If an operator copy-pastes the example into a component's args, Go's flag package rejects the unrecognized flag and the rollout fails to start.

- `--github-search-endpoint`: Search API endpoint (often the same as REST)
Convergence: flagged by all three maintainer-review perspectives; deployment-risk review calls this the one item with real blast radius.

Should fix

Should fixInaccurate, non-per-component throttling flag defaults

site/content/en/docs/github-api-access.md — Client-side Throttling section

Claims --github-hourly-tokens defaults to "matches GitHub's limit" and --github-allowed-burst defaults to "100" as if universal. Per pkg/flagutil/github.go (ThrottlerDefaults), both actually default to 0 (disabled) unless a component opts in. hook, deck, crier — three of the six components this PR documents — never opt in, so throttling is off by default for them. branchprotector/status-reconciler/peribolos use 300/100, invitations-accepter uses 300/300, needs-rebase uses 360/360.

- `--github-hourly-tokens`: Maximum GitHub tokens to consume per hour (default: matches GitHub's limit)
- `--github-allowed-burst`: Maximum burst of tokens that can be consumed at once (default: 100)
Convergence: flagged by all three maintainer-review perspectives.

Should fixTide doesn't expose the documented throttling flags at all

site/content/en/docs/components/core/tide/_index.md — GitHub API Access section

cmd/tide/main.go calls AddCustomizedFlags(fs, prowflagutil.DisableThrottlerOptions()), so --github-hourly-tokens/--github-allowed-burst aren't registered on tide at all. Tide instead has its own --sync-hourly-tokens (default 800) and --status-hourly-tokens (default 400). The tide doc section links to the central page's generic throttling guidance with no callout of this divergence.

Convergence: flagged by maintainability and deployment-risk reviews.

Questions

QuestionSearch API rate-limit claim unverifiable from this repo

site/content/en/docs/github-api-access.md — Managing API Rate Limits section

"Search API: 30 requests/minute (shared across v3 and v4)" is a claim about GitHub's own API, not something prow implements/asserts in code — worth double-checking against current GitHub docs.

Things I checked and was fine with

  • "Cached responses don't count against the token budget" claim — confirmed correct. pkg/github/client.go:447-461 explicitly refunds the throttling token when ghcache.CacheModeIsFree(cacheMode) is true, matching existing wording in site/content/en/docs/ghproxy/_index.md.
  • ETag/conditional-request handling claim — confirmed against pkg/ghcache/ghcache.go.
  • Flag names --github-token-path, --github-app-id, --github-app-private-key-path, --github-hourly-tokens, --github-allowed-burst, --github-endpoint, --github-graphql-endpoint all exist verbatim in pkg/flagutil/github.go:133-141.
  • Component-doc additions are consistent in structure/tone, correctly link back to the central page rather than duplicating detail, and match an existing established pattern (same style already used for ghproxy links). weight: 104 slots cleanly into nav ordering with no collision.
  • No doc-linter or doc-gen mechanism ties these prose numbers to pkg/flagutil/github.go — noted as a maintainability/drift risk rather than a current defect beyond what's listed above.

Open questions for the author

  • Where does the "5,000 requests/hour per installation" figure for GitHub Apps come from — was this meant to be a different (higher) number?
  • Is --github-search-endpoint intended for a future flag that doesn't exist yet, or was it just an assumption that should be removed?
  • Can the throttling defaults section be reworded to reflect that flags default to disabled (0) and defaults are set per-component, rather than implying a single universal default?
  • Should the tide doc section explicitly mention --sync-hourly-tokens/--status-hourly-tokens instead of pointing at the generic throttling flags?
