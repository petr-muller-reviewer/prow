Verdict

Approve — with two robustness suggestions and two design questions to settle explicitly.

This review combines an 8-angle line-by-line finder pass with a 3-perspective maintainer panel (code quality, maintainability, deployment risk) synthesized by an advisor agent — all four independent assessments converge on approve. The change is internally consistent, well-tested, and handles backward compatibility carefully (deprecated private: translation, null handling, both-set rejection, parse-time typo validation). Nothing blocking on supported GitHub deployments. The should-fix items share one root cause — an API that returns an empty visibility string — with a security-flavored failure mode on repo creation, and the ungated private→internal transition plus the pkg/github.RepoRequest API break for downstream vendors are deliberate choices that deserve an explicit maintainer sign-off.

What this PR does

  • Replaces Private *bool with Visibility *RepoVisibility (public/private/internal) on org.Repo, validated at parse time via UnmarshalText.
  • Adds a custom Repo.UnmarshalJSON that translates the deprecated private: true/false to the equivalent visibility (with a throttled deprecation warning), errors when both fields are set, and treats JSON null as absent.
  • Swaps github.RepoRequest.Private for Visibility *string; adds a Visibility string field to github.Repo (keeping Private bool).
  • Narrows the sanitizeRepoDelta guard: only transitions to public require --allow-repo-publish; private↔internal is free.
  • Dump path reads Visibility from the API response and prunes "public" as the default in PruneRepoDefaults.

Old code always had full.Private/current.Private populated. New code parses Visibility and, on an empty/unrecognized string, the dump only warns and omits the field (a private repo dumped from such an API loses its privacy marking; recreating from that dump yields a public repo), while the update path treats empty current.Visibility as unequal to any configured value — generating a delta every run, including a perpetual publish-gated error for legacy private: false configs. Flagged independently by the finder review and by both the code-quality and deployment-risk maintainer-panel reviewers.

Maintainer panel (code quality + deployment risk): suggest falling back to Private bool when Visibility string is empty, in both the dump and the update-delta comparison.

should fixRepo-creation wire format change is a confidentiality hazard on older GHE

cmd/peribolos/main.go:1030-1044 (newRepoCreateRequest)

var visibility *string
if definition.Visibility != nil {
    s := string(*definition.Visibility)
    visibility = &s  // sent as "visibility", not "private: true"
}

Sends visibility: private where the old code sent private: true. If a GHE version's repo-create endpoint ignores an unrecognized visibility parameter, a repo configured private would be silently created public — no error, a genuine confidentiality failure. Flagged by the deployment-risk maintainer-panel reviewer; a hazard only for peribolos users on older/unverified GHE.

Questions

questionprivate→internal is ungated — intended scope of the safety valve?

cmd/peribolos/main.go:1145-1148 (sanitizeRepoDelta)

if delta.Visibility != nil && *delta.Visibility == string(org.RepoVisibilityPublic) && !opt.allowRepoPublish {

The guard only blocks transitions to public. Private→internal widens exposure from repo collaborators to the entire enterprise with no flag. Not a regression (internal wasn't expressible before) and the PR description plus tests explicitly declare private↔internal free; the deployment-risk maintainer-panel reviewer judged this a reasonable, safe narrowing. Still, an exposure-widening transition is exactly what this flag family exists to guard, so it deserves an explicit "yes, this is fine" from maintainers.

questionpkg/github.RepoRequest API break for downstream vendors

pkg/github/types.go:382-390 (RepoRequest)

Private *bool removed, replaced with Visibility *string. In-tree only peribolos is affected, but Prow is widely vendored — any downstream tool constructing RepoCreateRequest/RepoUpdateRequest directly gets a compile break on the next update. Flagged by the deployment-risk maintainer-panel reviewer; worth a release-note callout rather than a code change.

nitgithub.Repo carries unsynced dual state (Private bool / Visibility string)

RepoRequest.Visibility *string drops type safety exactly at the API boundary, and sanitizeRepoDelta compares a github-layer value against string(org.RepoVisibilityPublic), coupling that layer to the org config enum. Defining RepoVisibility in pkg/github (which pkg/config/org already imports) fixes both the dependency direction and the typing.

Things I checked and was fine with

  • Config loading goes through sigs.k8s.io/yaml (YAML→JSON), so the custom Repo.UnmarshalJSON is honored; no gopkg.in/yaml bypass anywhere; pkg/config/org is imported only by cmd/peribolos.
  • Marshal round-trip for dump is correct (RepoVisibility is a string kind), and PruneRepoDefaults prunes only public, so private and internal survive dumps.
  • No stale references to the removed org.Repo.Private / RepoRequest.Private; branchprotector reads github.Repo.Private from live API responses, which still populate it.
  • RepoRequest.Defined() was updated to include Visibility.
  • No extra GitHub mutations on the happy path: the update request omits visibility when it equals the current value, matching the old setBool omit-when-equal behavior.
  • The hard error on both private and visibility set is stated PR intent and tested — not flagged.
  • ThrottledWarnf firing at most once per 5 minutes is adequate for a single-run CLI: one deprecation warning per run.
  • Peribolos site docs don't document the private/visibility repo fields, so no docs went stale.
  • UnmarshalJSON test coverage is thorough (null handling, both-set conflict, typo rejection, migration paths).
  • sanitizeRepoDelta's policy change (public-only gating, free private↔internal) is behavior-tested, including internal→public gating.
  • No new flags, RBAC, scopes, or endpoints; visibility rides the existing repo GET/PATCH/POST calls.
  • Rollback to an older peribolos after adopting visibility: configs (especially internal) doesn't fail outright — sigs.k8s.io/yaml is non-strict — but silently stops reconciling visibility with zero error signal (deployment-risk maintainer-panel finding).

Open questions for the author

  • Does the minimum GHES version prow supports always populate visibility on the repos API and accept it on create/edit? The old create path sent private: true, which every API version honors.
  • Is the pkg/github.RepoRequest API break (Private → Visibility) called out in release notes for downstream vendors of the Go module?
