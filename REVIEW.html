Needs discussion — design change requested, no code change since 124f7da44

The implementation is clean and follows codebase patterns. The disagreement is entirely about which set of jobs the command selects. This session converged on a definition: ContextRequired() && NeedsExplicitTrigger(), triggered unconditionally — the exact complement of /test all — with no context inspection and no awareness of branch-protection or Tide config. That answers the earlier open questions (the command should not read require_manually_triggered_jobs), works for the #729 requester with no config change on their side, and results in less code than is currently on the branch. It needs a rename. A design comment to this effect was posted on the PR on 2026-08-08; the author has not yet pushed the different version they described on 2026-08-04, so steering is time-sensitive.

What this PR does

  • Adds /test-required, which triggers non-optional presubmits whose context has not yet been reported, including jobs that need an explicit trigger (passed as forcedToRun = true).
  • Introduces TestRequiredFilter in pkg/pjutil/filter.go, wired into commentMatchesTrigger and PresubmitFilter.
  • Unlike /retest-required, it does not re-run failed jobs — it only fills in missing ones.
  • Adds a help provider entry and extends the plugin description. +161/-0 across 4 files.
  • Motivated by #729: metal3 maintainers manually trigger a few required-but-not-automatic e2e jobs by copying job names, and want one command for it.

Findings

Should fix

should fixFilter predicate should be ContextRequired() && NeedsExplicitTrigger(), forced unconditionally

pkg/pjutil/filter.go:269-287, pkg/pjutil/filter.go:317-323

The current predicate is a /retest-shaped context check under a /test name, and its NeedsExplicitTrigger() term only feeds the forced return value. Moving that term into the match predicate makes the command the exact complement of TestAllFilter (!p.NeedsExplicitTrigger(), filter.go:150): two disjoint sets whose union is every non-optional job. The set is then small by construction, so unconditional triggering costs nothing and the context check becomes unnecessary rather than merely inconsistent. No config plumbing is needed, so the require_manually_triggered_jobs question disappears entirely.

// current
func (trf *TestRequiredFilter) ShouldRun(ps config.Presubmit) (bool, bool, bool) {
    if ps.Optional {
        return false, false, false
    }
    return !trf.allContexts.Has(ps.Context), ps.NeedsExplicitTrigger(), false
}

// target
func (trf *TestRequiredFilter) ShouldRun(ps config.Presubmit) (bool, bool, bool) {
    return ps.ContextRequired() && ps.NeedsExplicitTrigger(), true, false
}

Not merely "drop the context check." Dropping it alone yields "trigger every non-optional job unconditionally", including always_run: true jobs that already ran — the wasteful variant, and exactly what the author described implementing on 2026-08-04.

Side effects, all subtractive: the allContexts field and constructor argument are deleted; the contextGetter() call in PresubmitFilter (filter.go:317-323) goes away, so the command stops issuing a GetCombinedStatus call and the block collapses to match the NewTestAllFilter() line below it.

Works for #729 unchanged: the requester's jobs are always_run: false, optional: false with no conditional matcher, so they satisfy the predicate with no config change on their side.

Nits

pkg/pjutil/filter.go:281

ContextRequired() is !ps.Optional && !ps.SkipReport (pkg/config/jobs.go:550-552). A skip_report: true job posts no context and cannot be required in any meaningful sense. RetestRequiredFilter (filter.go:254) uses bare ps.Optional, so precedent is mixed.

nitTests need inverting, not extending

Under the target predicate the "skips jobs with already-reported contexts" expectations invert, and a new case should assert that always_run: true required jobs are not triggered. The previously-noted missing coverage for already-reported contexts becomes moot.

Things I checked and was fine with

The requester's actual configuration (metal3-io/project-infra)

  • prow/config/config.yaml: tide.context_options.from-branch-protection: true; branch-protection: is only protect: true for orgs Nordix and metal3-io. No require_manually_triggered_jobs anywhere.
  • Target jobs (cluster-api-provider-metal3.yaml:170-185, ip-address-manager.yaml:149-164, ironic-image.yaml:52-67): always_run: false, optional: false, no conditional matcher.
  • baremetal-operator.yaml:124-205 carries ~10 always_run: false, optional: true e2e jobs — the concrete reason /test all is unacceptable to them.
  • No branchprotector deployment found in the repo (only a doc-comment mention). The GitHub Required badge in the #729 screenshot is therefore likely hand-managed outside Prow, since BranchRequirements would place these contexts in requiredIfPresent, and branchprotector replaces rather than unions the context list (cmd/branchprotector/protect.go:542).

Existing commands genuinely do not cover the use case

  • /retest-required → RetestRequiredFilter (filter.go:254) → RetestFilter (filter.go:236): failed || (!p.NeedsExplicitTrigger() && !allContexts.Has(p.Context)). For a never-run manual job, failed is false and the second clause is short-circuited → not triggered.
  • /test all → TestAllFilter (filter.go:150) excludes NeedsExplicitTrigger() by construction.

Config-level workarounds that exist today

  • A shared trigger: regex across jobs is legal — only job names are checked for uniqueness (config.go:2306-2336), and CommandFilter (filter.go:127) returns forced = true, so matched jobs run despite always_run: false.
  • rerun_command is mandatory when trigger is set (config.go:3134; defaulting only fires when both are empty, config.go:3245) and must itself match the trigger regex (config.go:3274-3275). It is copied into the ProwJob (pjutil.go:177) and printed in the failure report (report/report.go:313), so a shared rerun_command makes a single failure advertise a rerun of the whole set. Widen trigger, keep rerun_command per-job.
  • run_before_merge: true (jobs.go:216-220) is the per-job equivalent of require_manually_triggered_jobs — same forceRun expression, but it does not feed BranchRequirements, so it does not change what GitHub requires.

Tide's treatment of manually-triggered required jobs, without the flag: enforced but unmanaged

  • jobIsRequiredByTide (tide/github.go:443-445) = ContextRequired() || RunBeforeMerge → passes.
  • forceRun (tide.go:1708) is false → ps.ShouldRun(branch, changes, false, false) returns false (jobs.go:518-530, with RegexpChangeMatcher.ShouldRun returning determined=false, jobs.go:449-456) → the job is absent from sp.presubmits[pr.Number].
  • Consequence: accumulate (tide.go:1108-1122) never sees it → never in missingTests → Tide never triggers or retests it.
  • But IsOptional is false for RequiredIfPresentContexts (config/tide.go:1015-1016), so unsuccessfulContexts (tide.go:865-877) still gates on it: failure → PR filtered from the pool (tide.go:781) with no possible retrigger; pending → filtered as "not Prow-controlled" (tide.go:785-788); success → accepted forever, never revalidated when the base moves, because the base-SHA staleness check in accumulate only covers jobs in the required set.
  • With require_manually_triggered_jobs + from-branch-protection (tide.go:2395-2405): forceRun is true → Tide triggers the job itself once the PR is in the pool. Introduced by c13d06d6c (2024-01-21, "tide: Fix require_manually_triggered_jobs tide handling", "resulted in missing protection for this kind of jobs"). The auto-trigger machinery itself is old (75b0d3a36, 2019-08-03).
  • Batches already use union semantics: presubmitsForBatch (tide.go:1731-1776) recomputes from batchChanges(prs) (union of changed files) and is the single chokepoint for both pickBatch (:1242) and accumulateBatch (:1005), so pick-time and validate-time cannot drift.

Unchanged from earlier reviews

  • Filter ordering (test-required after retest-required, before test-all) is correct in AggregateFilter.
  • commentMatchesTrigger wiring is correct; help pruning works (/test-required matches anyTestRe, help.go:33).
  • Purely additive; no config/API/behavioral change to existing commands; cleanly revertible; no security concerns.

Open questions for the author

  • Naming: /test-manual-required (precise, long), /test-required plus prominent documentation of the exclusion, or the argument form /test manual-required matching the /test all precedent?
  • For the #729 reporters: do you hand-manage GitHub branch protection for these contexts? Prow classifies them as required-if-present, so Tide would consider a PR mergeable without them — the answer determines whether require_manually_triggered_jobs: true or run_before_merge: true is the config fix you actually want, independent of this PR.
  • Follow-up issue candidate against Tide, independent of this PR: make a present context imply managed — add "context already present on this PR" as a forceRun disjunct in presubmitsByPull (tide.go:1708), so a maintainer's manual trigger produces a genuinely first-class required check (retriggered on base drift, self-healing on failure) without the org-wide flag. Same defect class as c13d06d6c, adjacent axis. Open risks: batch composition (union over per-PR context presence) and headContexts fetch cost, possibly already cached (tide.go:1211-1212).
