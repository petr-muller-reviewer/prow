What this PR does

  • Adds a --git-signing-key-path flag to GitHubOptions accepting a path to an SSH private key.
  • Threads the path through ClientFactoryOpts into the clientFactory struct.
  • In ClientForWithRepoOpts, after each secondary clone, configures gpg.format=ssh, user.signingkey, and commit.gpgsign=true on the repo.
  • Extends NewLocalClientFactory with variadic ...ClientFactoryOpt for testability (backwards-compatible change).
  • Adds an integration test that generates an ed25519 key, creates a local repo, applies a patch via git am, and verifies the commit contains an SSH signature.

Findings

Should fix

Should fix ClientFromDir does not apply signing configuration
pkg/git/v2/client_factory.go:435-438

ClientFromDir is part of the public ClientFactory interface but returns a client without applying signing config, unlike ClientForWithRepoOpts. There are no production callers today, so this is a latent gap rather than an active bug. A future caller expecting signed commits would silently get unsigned ones. 

func (c *clientFactory) ClientFromDir(org, repo, dir string) (RepoClient, error) {
    return c.bootstrapClients(org, repo, dir)
}
Should fix Generic error message for three distinct git config calls
pkg/git/v2/client_factory.go:497-506

Converging concern: flagged independently by code quality and maintainability reviewers.

All three config calls (gpg.format, user.signingkey, commit.gpgsign) wrap errors with the same message "failed to configure commit signing". When the error fires, the operator cannot tell which config key failed without examining the inner error text. Include the config key: 

fmt.Errorf("failed to configure commit signing (%s): %w", args[0], err)

Nits

Nit No early validation of signing key path
pkg/flagutil/github.go:151

Converging concern: flagged independently by all three reviewers.

SigningKeyPath is not checked in Validate(). A typo like --git-signing-key-path=/ect/keys/bot lets the component start successfully. The failure surfaces only at commit time with a cryptic git/ssh error. An os.Stat check would surface misconfiguration at startup. Consistent with how AppPrivateKeyPath is handled (also no stat check), so not blocking. 

fs.StringVar(&o.SigningKeyPath, "git-signing-key-path", "",
    "Path to an SSH private key for signing git commits.")
Nit No log line when signing is enabled
pkg/git/v2/client_factory.go:494

Other factory-level configurations produce log output. A debug-level log when signingKeyPath is non-empty would help operators confirm signing is active without inspecting individual repo configs.

Nit Signing support deepens existing GitClientFactory placement debt
pkg/flagutil/github.go:51, pkg/flagutil/github.go:338-339

There is an existing TODO(chaodaiG) acknowledging GitClientFactory belongs outside github.go. The Gerrit adapter already instantiates an empty GitHubOptions{} just to get a git client factory. Adding SigningKeyPath here is pragmatic given current architecture but further entangles git concerns with GitHub-specific types. Not blocking — noting for the eventual refactor. 

// TODO(chaodaiG): move this logic to somewhere more appropriate instead of in
// github.go.

Questions

Question Should ClientFromDir also apply signing config?
pkg/git/v2/client_factory.go:435

Is ClientFromDir intentionally a "raw" client that skips factory-level config, or should it apply signing for interface completeness?

Question Key format validation
pkg/git/v2/client_factory.go:499

Passing a GPG key path while gpg.format=ssh is hardcoded would fail at commit time with a confusing error. Worth a doc note or comment?

Things I checked and found fine

  • NewLocalClientFactory signature change is backwards-compatible (variadic opts; existing callers unaffected).
  • ClientFor delegates to ClientForWithRepoOpts, so signing config applies for both entry points.
  • Apply method handles SigningKeyPath consistently with other string fields (Host, CookieFilePath).
  • Flag naming (--git-signing-key-path) is appropriate — distinguished from --github-* flags since this is a git concern, not a GitHub API concern.
  • Test correctly exercises git am path matching cherrypicker's production usage.
  • Signing config applied to secondary clone only (correct; cache is bare/mirror for fetching).
  • No interface breakage from the NewLocalClientFactory signature change.
  • Feature is entirely opt-in; zero behavioral change without the flag.
  • Per-clone config — no global git config side effects.

Open questions for the author

  • Should ClientFromDir also apply signing config for interface completeness, or is it intentionally a "raw" client?
  • Would an os.Stat check on the key path at Validate() time be welcome, or is deferred validation preferred here?
  • Is a GPG-vs-SSH key format mismatch worth guarding against or documenting?
