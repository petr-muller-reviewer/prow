# kubernetes-sigs/prow#583

Full-source re-review at `af38ab180`. Supersedes the earlier summary-derived pass, which contained four factual errors (recorded under Corrections).

## What this PR does

- Adds a `fork:` block to the peribolos org-config `repos:` surface (`ForkConfig{From, DefaultBranchOnly}`), reconciled by a new `configureForks` that runs before `configureRepos`.
- Adds `CreateForkInOrg` to the GitHub client, passing the config key as GitHub's fork `name` parameter so fork naming is explicit rather than GitHub-selected.
- Adds `--fix-forks`, defaulting to whatever `--fix-repos` is unless explicitly passed.
- Extracts the GitHub-API-shaped fields of `org.Repo` into an embedded `RepoMetadata` struct (serialization-transparent, Go-source breaking).
- Teaches `--dump` to emit `fork:` for any repo whose GitHub parent is set.

## Findings

### [should-fix] `--dump` auto-populates `fork:`, silently widening what `--fix-repos` reconciles
- where: `cmd/peribolos/main.go:402-406`
- concern: This is the mechanism by which fork reconciliation reaches operators who never opted in. Combined with `--fix-forks` inheriting from `--fix-repos`, a config regenerated by `--dump` after upgrading starts reconciling every fork in the org — one extra `GetRepos` plus one `GetRepo` per fork, and the new hard-failure paths below become reachable. Behaviourally a no-op for a faithful dump, but it means "opt-in via the new config key" holds only until the next re-dump. Worth a release note.
- excerpt: |
    // If repo is a fork, record the upstream
    if full.Fork && full.Parent.FullName != "" {
        repoConfig.Fork = &org.ForkConfig{From: full.Parent.FullName}

### [should-fix] Upstream rename or transfer turns a previously-working config into a non-zero exit
- where: `cmd/peribolos/main.go:1342`, `cmd/peribolos/main.go:1465-1468`
- concern: A dumped `from:` pins the upstream's `FullName` at dump time. If that upstream is later renamed or transferred, `expectedUpstream` stops matching `Parent.FullName`, `checkExistingRepoConflict` produces a conflict error, and the whole run exits non-zero. Pre-PR there was no fork tracking to disagree with reality. The error is accurate and actionable, so this is acceptable — but it is a new way for an untouched config to start failing, and it deserves a mention in docs.
- excerpt: |
    return fmt.Errorf("repo %s exists as fork of %s, but config specifies %s", repoName, cachedResult.fullName, expectedUpstream)

### [should-fix] Duplicate-upstream validation hard-returns, making dump→apply non-idempotent
- where: `cmd/peribolos/main.go:1369-1371`
- concern: Unlike the format errors just below it (which accumulate into an aggregate), this is a bare `return nil, err` that aborts all fork handling. An org holding two repos with the same GitHub parent — reachable by transferring a fork in, even if the fork API refuses a second fork — dumps to a config that peribolos then rejects outright. Fails loudly rather than corrupting anything, but `peribolos --dump | peribolos --fix-repos` should not be able to produce a config peribolos won't accept.
- excerpt: |
    if existing, ok := upstreamToConfig[upstream]; ok {
        return nil, fmt.Errorf("multiple config entries (%s, %s) fork from the same upstream %s, only one fork per upstream is allowed per org", existing, repoName, repoCfg.Fork.From)
    }

### [should-fix] Fork error is dropped from the message when another subsystem fails first
- where: `cmd/peribolos/main.go:1009-1013`, `cmd/peribolos/main.go:1054-1056`
- concern: `forkErr` is deliberately deferred so other subsystems still run, then returned at the end. But `configureRepos`, `configureCollaborators` and `configureTeams` all `return` directly on failure, discarding `forkErr`. Exit status is still non-zero so the stated guarantee holds, but the fork failure becomes invisible in the output — the operator sees only the repos/teams error. Wrapping into an aggregate at each return would preserve both.
- excerpt: |
    } else if err := configureRepos(opt, client, orgName, orgConfig, forkNames); err != nil {
        return fmt.Errorf("failed to configure %s repos: %w", orgName, err)
    }

### [should-fix] New user-facing config surface and flag ship with no documentation
- where: `site/content/en/docs/components/cli-tools/peribolos.md`
- concern: The PR touches zero docs. `--fix-forks`'s inheritance from `--fix-repos` is non-obvious behaviour documented only in the flag help string and the PR body. Mitigating: that page does not document the `repos:` surface at all today, so this matches an existing gap rather than creating a regression — but the inheritance semantics in particular are the kind of thing operators will be surprised by.

### [nit] Unreachable fallback in `checkExistingRepoConflict`
- where: `cmd/peribolos/main.go:1344-1348`
- concern: Dead code. The only call site is `main.go:1465`, reached only when `byName[repoNameLower]` exists. If that repo is not a fork the function already returned at `:1335-1337`; if it is a fork, `configNameResult` was necessarily set in the candidate loop at `:1436-1442`; and if it matched the expected upstream the loop already `continue`d at `:1459-1461`. So `cachedResult` is never nil here and this `GetRepo` never runs.
- excerpt: |
    fullRepo, err := client.GetRepo(orgName, existingRepo.Name)
    if err != nil {
        return fmt.Errorf("failed to get full repo info for %s: %w", repoName, err)
    }

### [nit] Empty-string return conflates dry-run with a nameless 202
- where: `cmd/peribolos/main.go:1480-1486`, `pkg/github/client.go:4598-4600`
- concern: `createdName == ""` is the sentinel for "dry run, nothing created". A real non-dry 202 whose body lacks `name` would take the same branch, log `dry-run: fork creation skipped`, record a fork name that does not exist, and skip `waitForFork`. GitHub does return the repo object, so this is theoretical — but a bool return or an explicit dry check in the caller would remove the ambiguity.
- excerpt: |
    if createdName == "" {
        repoLogger.Info("dry-run: fork creation skipped")
        forkNames[repoName] = repoName
        continue
    }

### [nit] Hardcoded fork-wait timeout and interval
- where: `cmd/peribolos/main.go:1490`
- concern: `5*time.Minute` / `10*time.Second` inline at the call site. Named constants would document intent and make the worst case — serial waits across N forks in one run — easier to reason about.
- excerpt: |
    if err := waitForFork(client, orgName, createdName, 5*time.Minute, 10*time.Second); err != nil {

### [question] Is the `org` package's Go API considered stable for external importers?
- where: `pkg/config/org/org.go:88-99`
- concern: Open thread from petr-muller (2026-05-11), answered with a question by hoxhaeris (2026-07-13), still unanswered. The `RepoMetadata` extraction is a compile-time break for out-of-tree code building `org.Repo{Description: ...}` literals. No code change rides on the answer — the extraction is an independently-revertible commit — but the answer determines whether this warrants a release note.

### [question] Can one org actually hold two forks of the same upstream?
- where: `cmd/peribolos/main.go:1369-1371`
- concern: The PR body asserts "GitHub only allows one fork per upstream per org", which is what justifies the hard `return`. Fork *creation* is restricted, but repo *transfer* appears able to produce the state. If reachable, the duplicate-upstream finding above is real; if genuinely impossible, the validation is belt-and-braces and the finding drops to a nit. I could not confirm either way from the code.

## Checked

- `configureForks` early return at `main.go:1377-1379` genuinely precedes the `GetRepos` call at `:1382` — no API cost for configs without `fork:` entries. Confirmed.
- `RepoMetadata` embedding is serialization-transparent. Verified empirically, not by reasoning: a pre-PR config with flat `description`/`private`/`default_branch`/`previously`/`on_create`/`collaborators` parses through `sigs.k8s.io/yaml`, all fields promote correctly, and re-marshals flat with no `repometadata` nesting key.
- `cmd/peribolos` is the only in-tree importer of `pkg/config/org` (`main.go`, `main_test.go` only).
- `parts[1]` indexing in the second `configureForks` loop (`main.go:1408-1410`) is safe — the validation loop hard-returns on any malformed `from` before it is reached.
- `parentResult` caching correctly avoids double-reporting: a failed `GetRepo` on the config-named repo is recorded once in the candidate loop, and `checkExistingRepoConflict` returns nil for that case (`main.go:1338-1341`).
- `append([]string{wantName}, wantRepo.Previously...)` at `main.go:1207` and `:1209` allocate fresh backing arrays — no slice aliasing into config state.
- Fork/rename mapping is threaded correctly: `configureRepos` uses `actualName` for the update to avoid spurious renames (`main.go:1266-1269`), and `configureCollaborators` remaps via `forkNames` (`main.go:1522`).
- `--fix-repos --fix-forks=false` leaves fork-configured repos unmanaged rather than creating them as empty repos (`main.go:1238-1241`). Consistent with opting out.
- `waitForFork` distinguishes 404 from other errors and surfaces the latter immediately (`main.go:1320-1322`) — ivankatliarchuk's March review point, confirmed fixed.
- Fork detection is not O(repos): one `GetRepos` plus at most two `GetRepo` per configured fork (`main.go:1421-1424`) — ivankatliarchuk's other point, confirmed fixed.
- `go build ./...` succeeds; `cmd/peribolos` and `pkg/config/org` test suites pass.
- No PR template or release-note requirement exists in this repo.

## Corrections

Four claims in the previous (summary-derived) pass were wrong and have been corrected:

- "New fields `fork_from`, `default_branch_only` are `omitempty` pointers" — describes the pre-`2479e7c74` shape. Current surface is nested `fork: {from, default_branch_only}`; `ForkConfig.From` is a plain `string`, not a pointer and not `omitempty`.
- "Config key as fork name … not visible in the current PR diff — may be in unpushed commits" — it is in the diff: `main.go:1473` passes `repoName` to `CreateForkInOrg`, serialized as `name` at `client.go:4602-4610`.
- Release-note framing was presented as a missed repo convention; no such convention exists here.
- The independent risk scan did not examine the `--dump` path, which is where this feature actually reaches existing operators.

## Open questions

- Is `pkg/config/org` a supported Go API for out-of-tree importers, or effectively internal to peribolos? Determines whether the `RepoMetadata` extraction needs a release note.
- Should the duplicate-upstream check accumulate into the aggregate like the format errors beside it, rather than aborting all fork handling?
- Should `--dump` emit `fork:` at all, given it activates reconciliation on the next `--fix-repos` for operators who never asked for fork management? An opt-in dump flag would keep the round-trip inert.
- Is losing the fork error message (when repos/teams fail first) acceptable, or should those returns aggregate `forkErr`?
