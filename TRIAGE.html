#400 — tide merge queue stalls when unresolved comments exist Reported by aevyrie · accepted area/tide kind/bug lifecycle/stale

State: open Triaged: 2026-06-03T11:33:36Z Main SHA: 53a81071b

Verdict

accepted — legitimate bug with a well-defined fix path

The issue is real and reproducible: Tide's pre-merge filter isAllowedToMerge() does not check GitHub branch protection requirements, so PRs blocked by "require resolved conversations" or "require approving reviews" pass the filter, enter the sync pool, and trigger an infinite 405-retry loop that stalls all other PRs in the subpool. Two separate users (aevyrie, bonsairobo) have kept the issue alive through three stale cycles. The fix is well-scoped: add mergeStateStatus to the existing GraphQL query and check for BLOCKED in isAllowedToMerge(). One open question (timing of Tide's own context write) needs verification before implementation.

What the Issue Reports

  • A PR that passes all required CI checks but has unresolved review comments gets stuck in Tide's merge queue indefinitely.
  • GitHub's branch protection rule "require conversations to be resolved" causes GitHub to reject the merge with HTTP 405; Tide logs this at debug level and retries next cycle.
  • The stalled PR blocks all other successful PRs in the same subpool from merging.
  • There is no user-visible signal: the PR's Tide status shows "success" and no error is surfaced to the author.
  • The issue has a confirmed shared root cause with #269 ("Changes Requested" causing the same loop).

Analysis

Probable Cause

isAllowedToMerge() does not check branch protection state

pkg/tide/github.go:605-636 — isAllowedToMerge() checks:

  • Merge conflicts (Mergeable == Conflicting)
  • Valid merge method labels
  • Rebase capability / repo merge method settings

It does not check mergeStateStatus or query branch protection rules. A PR with mergeStateStatus == BLOCKED passes all existing checks and lands in the merge attempt path.

The Stalling Mechanism

1
PR passes all CI → lands in Tide's "success" pool
2
pickHighestPriorityPR() selects it deterministically each cycle (no per-PR failure state)
3
GitHub rejects merge with 405 (UnmergablePRError)
4
Tide logs failure at debug level; no user-visible status update
5
Next sync cycle: same PR selected again → infinite loop
6
All other successful PRs in the subpool are blocked

Recommended Fix

Use GitHub's mergeStateStatus GraphQL field

mergeStateStatus aggregates all branch protection rules into a single value: BLOCKED, CLEAN, BEHIND, DIRTY, DRAFT, HAS_HOOKS, UNKNOWN, UNSTABLE. Adding a check for BLOCKED in isAllowedToMerge() covers both this issue and #269 without enumerating individual branch protection rules.

~100-200 lines including tests. Follows the same pattern as the existing Mergeable == Conflicting check. Fully backwards compatible (only prevents merges that would fail anyway).

Pros
  • Single field covers all current and future branch protection rules
  • Minimal API overhead (extra field in existing GraphQL query)
  • Follows existing Mergeable check pattern
  • Fixes #269 as a side effect

This is closely related to #269 (PR with "Changes Requested" repeatedly failing to merge). Both stem from the same root cause: Tide does not pre-validate GitHub branch protection requirements before attempting to merge a PR. Tide's pre-merge filtering (`isAllowedToMerge` in `pkg/tide/github.go:605`) currently only checks for merge conflicts, invalid merge method labels, and rebase capability. It does not check whether the PR meets branch protection requirements like "require conversations to be resolved" or "require approving reviews". When a PR passes all required CI checks but fails these branch protection rules, Tide categorizes it as a "success" and repeatedly attempts to merge it. GitHub rejects the merge with a 405 error (`UnmergablePRError`), Tide logs the failure at debug level, and on the next sync cycle the same PR is picked again — creating an invisible infinite retry loop. The stalling is particularly impactful in the single-PR merge path: `pickHighestPriorityPR` selects the same PR every cycle, effectively blocking all other successful PRs in that subpool from merging. A potential fix would be to use GitHub's `mergeStateStatus` GraphQL field on the PullRequest object. This field aggregates all branch protection checks into a single state (`BLOCKED`, `CLEAN`, `BEHIND`, etc.) — so checking for `BLOCKED` in `isAllowedToMerge` would filter out PRs that can't pass branch protection, covering both this issue and #269 without needing to understand each individual branch protection rule. This follows the same pattern as the existing `Mergeable == Conflicting` check in that function. /remove-lifecycle stale /help-wanted
