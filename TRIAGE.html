Verdictaccepted
Accepted. Legitimate bug in Tide's merge loop. A PR that GitHub refuses to merge (branch protection) blocks the entire merge queue indefinitely because Tide has no cross-cycle memory of merge failures. PR #674 proposes a well-scoped fix.

What the issue reports

  • When enforce_admins: true and required_approving_review_count: N are set in branch protection, a PR with lgtm+approved labels but fewer than N GitHub reviews fails to merge with HTTP 405 (UnmergablePRError).
  • Tide retries the same PR every sync cycle because accumulate() only looks at CI status (which is green) and has no awareness of prior merge failures.
  • pickHighestPriorityPR() is deterministic (lowest PR number), so the same stuck PR wins every cycle, starving all other ready-to-merge PRs.
  • The error is logged at Debug level only — operators may not notice the queue is stalled.
  • A member comment confirms the same loop occurs when a PR has a "changes requested" review verdict alongside lgtm/approve labels.

Since previous triage: @kaovilai removed the lifecycle/stale label via /remove-lifecycle stale on 2026-07-01. No other activity; PR #674 remains open and unmerged.

Analysis

Probable cause

The sync cycle (Sync() → syncSubpool() → accumulate() → takeAction()) has no state that persists across cycles. Three factors combine:

  1. accumulate() (pkg/tide/tide.go:1077) classifies PRs purely by ProwJob/CI status. A PR with passing CI always lands in successes, regardless of merge history.
  2. tryMerge() (pkg/tide/tide.go:1474) returns keepTrying=true for UnmergablePRError, meaning "continue to next PR in batch." For single-PR merges, the cycle just ends. Nothing records the failure.
  3. pickHighestPriorityPR() (pkg/tide/tide.go:912) always picks the lowest-numbered PR from successes, so the same PR is selected again.

Existing partial mitigation

isAllowedToMerge() (pkg/tide/github.go:630-638) checks MergeStateStatus == "BLOCKED" with a configurable github_merge_blocks_policy. Setting it to "block" would filter these PRs at the filterSubpool level. However, the default is "permit" (pkg/config/tide.go:412), so most deployments are unprotected. There may also be edge cases where GitHub hasn't updated MergeStateStatus yet.

What I checked

  • All code references from the issue body verified against HEAD ae8e2d87.
  • syncController struct (pkg/tide/tide.go:79-98) has no merge failure tracking fields.
  • accumulate() has no merge history awareness — purely ProwJob status.
  • MergeStateStatusBlocked / github_merge_blocks_policy examined as partial mitigation — default "permit" does not prevent the issue.
  • Gerrit provider (pkg/tide/gerrit.go) treats all merge errors as immediate failures — not affected.
  • No existing tests verify cross-cycle advancement past stuck PRs.
