Verdict: ACCEPTED — legitimate feature/architecture proposal, keep open.

The issue's own cross-link (to #477, a branchprotector bug) is loose, but it accurately captures a real, maintainer-endorsed direction: the maintainer (petr-muller) explicitly stated on 2026-08-13, the same day #846 was filed, that branchprotector is legacy with a poor configuration surface, and that future effort should go toward GitHub Rulesets support rather than deeper into branchprotector. Repository code confirms a genuine, verified gap — no Rulesets API support exists anywhere in Prow.

What the issue reports

  • Tide (and Prow's branch-protection tooling generally) should support GitHub's newer Repository Rulesets API, not just "classic" branch protection rules.
  • The author (kaovilai) links kubernetes-sigs/prow#477 as related, saying #846 "should include fixes for" it.
  • #477 is actually about a different bug: branchprotector not removing protection from branches added to an exclude pattern.
  • The two issues are connected through the maintainer's own 2026-08-13 comment on #477, not through any shared code path described in #846's body.

Analysis

Reproducibility / observed behavior

  • Not a bug report — no reproduction steps needed. This is an architecture/feature gap: any repo relying on GitHub-side rulesets (rather than Prow-managed classic branch protection) for required checks has those requirements invisible to Tide.

Probable cause

Prow has zero representation of GitHub's Repository Rulesets API. Two distinct code paths are affected differently:

  • Merge-blocking decision (pkg/tide/github.go:600-641, isAllowedToMerge) already delegates to GitHub's own computed mergeStateStatus field via GitHubMergeBlocksPolicyMap (pkg/config/tide.go:250-256, added Dec 2025 in commit 2c14b702b, merged as PR #579). Since GitHub computes mergeStateStatus server-side accounting for rulesets, this path is likely already functionally ruleset-compatible — untested for that specific scenario, but not a code gap.
  • Required-status-context resolution is genuinely ruleset-blind (and live-branch-protection-blind too): the chain config.Config.GetTideContextPolicy (pkg/config/tide.go:944-995) → Config.GetBranchProtection/GetPolicy (pkg/config/branch_protection.go:456-524) is fed exclusively from Prow's own declarative branch-protection: config tree, never from a live GitHub call.

  • Confirmed Prow does not vendor go-github; its GitHub client is hand-rolled, so there is no upstream library ruleset support to fall back on.
  • Confirmed cmd/branchprotector/pkg/config/branch_protection.go operate purely on Prow's declarative config, not live GitHub branch-protection/ruleset state (aside from the reconciler's own push/diff calls).
  • Read kubernetes-sigs/prow#477 in full, including the maintainer's 2026-08-13 comment.

Recommended next steps

  • Ask the author (kaovilai) to clarify intended scope: full ruleset management (branchprotector-equivalent) vs. narrower "Tide should recognize ruleset-driven required checks."
  • Split into (a) a small verification/test task confirming GitHubMergeBlocksPolicyMap correctly handles ruleset-only blocks, and (b) a larger design proposal for ruleset-aware config before any new client/schema work begins.
  • Apply labels: kind/feature, area/tide (and area/branchprotector for cross-reference).
  • Require a short design note before any new Rulesets API client/config work starts, to avoid repeating branchprotector's configuration-surface problems.
