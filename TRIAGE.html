Stale queued presubmits run after the base advances

kubernetes-sigs/prow#1078 · main_sha 9c8eff7c98cc · state open · labels · triaged_at 2026-11-20T00:36:57Z
verdict: needs-discussion

Verdict

Needs discussion: Prow works as designed here; the only defect is that a queued job spends a run that cannot count, because the base moved before it started.

A presubmit captures its base SHA when the PR event fires and never re-evaluates it. A job held behind max_concurrency therefore runs pre-move base + current PR head. That is the same outcome as a base advance during a run, and Tide's base-SHA validity rule means the result is not evidence for the new base, so Tide re-triggers the job for pooled PRs. The maintainer's reading (2026-11-20) is that this is intended behavior and a mild inefficiency rather than a bug; queueing differs from a running base advance only by the pre-flight window, where something smarter could be done. Disposition (keep as a backlog enhancement vs. close wontfix with documentation) is open.

What the issue reports

  • A presubmit that waits in Prow's queue starts with the base SHA from its creation, so it tests stale base + current PR head; the reporter's example ran 4h41m after creation and ~3h40m after another PR merged to main.
  • The reporter argues the run "can't vote, nor present the fresh state", so the PR needs at least one more run before it can merge.
  • Requested remedy: stale queued jobs "should be cancelled or superseded / auto rebased".
  • Scope is presubmits only ("non tide batch jobs"); Tide batch staleness is tracked separately.
  • The run was created by the trigger plugin, not Tide: labels show created-by-prow and event-GUID, and no created-by-tide.

causebase SHA is captured once, at event time

  • detail: the trigger plugin resolves heads/<base ref> on the PR event and freezes it into refs.base_sha; nothing re-reads the branch while the ProwJob waits.
  • evidence: pkg/plugins/trigger/pull-request.go:52-59, pkg/pjutil/pjutil.go:130-150

causesupersede requires a newer run to already exist

  • detail: terminateDupes aborts older pending/triggered runs of the same job and PR set; the digest excludes commit SHAs, so a base advance alone supersedes nothing. Replacements come from Tide (pool PRs only), a new PR event, or /test.
  • evidence: pkg/plank/reconciler.go:438-450, pkg/pjutil/abort.go:61-118

causeTide retests only PRs that are in its pool

  • detail: subpools contain only PRs matching tide.queries with required labels. kubevirt runs Tide (sync_period: 2m), but PR #18626 was not merge-eligible, so no fresh run was created and terminateDupes had no newer run to prefer.
  • evidence: pkg/tide/tide.go:642-662

causequeueing differs from a running base advance only by the pre-flight window

  • detail: both leave a run pinned to an old base with that base recorded; queueing adds an arbitrarily long wait plus the option to decide before spending the run.
  • evidence: pkg/pod-utils/clone/clone.go:266-300, pkg/config/config.go:3533-3552

causea stale green keeps the PR pooled, so Tide re-triggers and the PR is not stuck

  • detail: filterPR judges required contexts by state only, so green keeps the PR in the pool; prowJobsFromContexts drops it as evidence on the base mismatch, accumulate records the job as missing, and takeAction triggers a fresh run. Open questions

  • Is the pre-flight window worth acting on at all, given that a base advance during a running job produces the same stale result and is not treated as a bug?
  • If it is: cancel or re-base? Cancelling needs coverage for PRs outside Tide's pool; re-basing needs a guarantee that the job definition still matches the new base.
  • Should pinned runs (mkpj --base-sha, Deck's original-spec rerun) be excluded explicitly if a refresh is ever implemented?
  • Should the pinning behavior be documented in user-facing docs, independent of the disposition?
