Verdict

Accept as a branchprotector feature/bug gap.

GitHub can require a named status check from a specific App, but branchprotector can neither declare that identity nor notice when it differs. The report provides a concrete failure, diagnostics, and a compatible direction; it is not a deployment-only configuration issue.

What the issue reports

  • A legacy required context can become bound to the App that recently set it.
  • A same-named successful check from another App is then rejected by GitHub.
  • Branchprotector configures only legacy string contexts and cannot express the expected App.
  • It also considers matching context names converged despite an App-identity mismatch.

Since previous triage: @weshayutin added “@myprc fyi” on 2026-09-07T18:25:16Z. It provides no technical information and does not change the assessment.

Analysis

Reproducibility / observed behavior

The reporter identifies a concrete PR where a successful Run CI check was rejected because it came from the wrong App. GitHub's branch-protection API documents checks[].app_id, including -1 to explicitly accept any App.

Probable cause

RequiredStatusChecks contains only Strict and Contexts; the desired-state renderer emits only legacy contexts, and equality compares only strictness and those names. Therefore Prow cannot serialize, read, compare, or repair identity.

Related code

  • pkg/config/branch_protection.go:75-83,148-162,472-489 — string-only policy, inheritance, and auto-added presubmit contexts.
  • cmd/branchprotector/request.go:63-70 — emits deduplicated contexts.
  • pkg/github/types.go:686-690 — lacks a check/App wire type.
  • cmd/branchprotector/protect.go:575-584 — ignores App identity while comparing state.
  • pkg/github/client.go:2906-2917 — current full branch-protection PUT can already carry required_status_checks.checks; no separate call is necessary.
return state.Strict == request.Strict &&
    equalStringSlices(&state.Contexts, &request.Contexts)

Related issues

  • kubernetes-sigs/prow#841 — a different required-context reconciliation failure, not App identity.
  • kubernetes/test-infra#24530 — reportedly App support for branch restrictions, a different subresource.

What I checked

  • The issue is open with no labels or comments, and its stated SHA is the worktree HEAD.
  • No existing branchprotector config/documentation supports required-check app_id.
  • GitHub officially supports required_status_checks.checks[].app_id and -1.
  • An equality-only change cannot fix the gap because the desired state has no identity information.
  • Legacy merging, rendering, and equality tests exist; App-identity coverage does not.

Recommended next steps

  1. Apply kind/feature and area/branchprotector; consider help-wanted after agreeing on the schema.
  2. Add additive explicit checks such as checks: [{context: Run CI, app_id: -1}], retaining legacy contexts when absent.
  3. Define conflict/precedence rules for legacy contexts and automatic presubmit contexts.
  4. Extend types, rendering, normalization/equality, tests, and documentation together.

Open questions

  • Should overlapping contexts and checks be rejected or have documented precedence?
  • Should an omitted app_id be passed through for GitHub to choose, or should Prow require an explicit ID or -1?
  • May operators override the identity of automatically managed presubmit contexts?
