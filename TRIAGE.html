Verdict

Duplicate — the reported bug was already fixed by PR #764 before/shortly after this issue was filed; no residual action needed.

The reporter hit a panic-induced CLA-label sync failure caused by a bug in the cla plugin that had already been fixed in #764 (merged 2026-06-20), likely before the fix had fully rolled out to all affected deployments. The reporter closed the issue themselves once the fix took effect, and a follow-up commenter confirmed the root cause. This triage exists purely as a record linking the symptom to its fix.

What the issue reports

  • PRs across several repos (kubernetes/test-infra, kubernetes-sigs/agent-sandbox, kubernetes/kubernetes) weren't getting CLA labels applied automatically.
  • Reporter (janetkuo) observed this on 2026-06-22 and gave three example PRs exhibiting the symptom.
  • Workaround at the time: manually commenting /check-cla to force a recheck.
  • Reporter closed the issue the next day (2026-06-23) with "Fixed now".
  • A commenter (Prucek) asked for confirmation and janetkuo confirmed the fix was #764, linking an internal Slack thread for more context.

Analysis

Probable cause

The cla plugin's status-event handler called gc.FindIssues(query, sort, asc) without an org argument. When the target installation used GitHub Apps auth, this panicked inside the apps-auth round-tripper:

BUG apps auth requested but empty org, please report this to the test-infra repo

The panic aborted CLA-label sync for that webhook event, so PRs were left without an up-to-date cncf-cla-yes/cncf-cla-no label until someone manually forced a recheck.
