Verdict

wontfix — already correctly closed, no action needed.

The issue is a legitimate, well-specified feature request (a /depend #NNN command for stacked-PR merge gating) that was already fully triaged and closed by the community: maintainer Prucek wrote up a complete design and concluded the reliability cost — new cross-PR reconciliation machinery needed to survive missed merge webhooks — outweighs the benefit over the existing manual /hold + comment workaround, and author tallclair agreed to close in favor of waiting on GitHub-native stacked PRs. Independent code research confirms this rationale holds.

What the issue reports

  • Requests first-class support for stacked PRs: a /depend #1111 command on PR #2222 would block #2222 from merging until #1111 merges.
  • Proposes a companion /undepend (or /depend cancel) to remove the link manually.
  • Motivated by a common Kubernetes workflow: opening PR B that builds on PR A, currently handled manually via /hold plus a comment noting the dependency.
  • Maintainer Prucek proposed a concrete design in comments: new label-based plugin, do-not-merge/has-unmerged-dependency label, a merge-event handler to release dependents — but flagged reliability/complexity concerns as reasons not to build it.
  • Author tallclair agreed to close, pointing to GitHub-native stacked PRs as a likely-sufficient alternative.

Analysis

Probable outcome if built (feasibility)

The "block" half of the proposal is trivial: a new do-not-merge/* label plus Tide's already-generic missingLabels filter (pkg/tide/status.go:209-216, config field pkg/config/tide.go:550,583) — no Tide code changes required.

The "auto-unblock when the dependency merges" half is the hard part. It requires a PullRequestHandler that, on a merge event, looks up and mutates other PRs' labels — a pattern that does not exist anywhere in the current plugin codebase. Grepping for GetPullRequests/Search( across pkg/plugins/* returned nothing. Checked every plugin registering PullRequestHandler (branchcleaner, bugzilla, releasenote, milestoneapplier, lgtm, reward-owners, updateconfig) — none of them search or mutate other PRs on an event. The closest analog is Tide's own sync loop (pkg/tide), a large, purpose-built subsystem, not a lightweight pattern other plugins reuse.

This means reliably auto-releasing dependents would also need a periodic reconciliation pass to cover missed merge webhooks — exactly the concern Prucek raised in the issue thread.

Related code

  • pkg/plugins/hold/hold.go:41-108 — the /hold plugin, precedent for the "block" half only: 
    RegisterGenericCommentHandler(pluginName, handleGenericComment, helpProvider)
// matches /hold and /hold cancel via regex, then AddLabel/RemoveLabel(labels.Hold)
    Purely comment-driven; no PullRequestHandler, no merge-event reaction, no reconciliation loop at all.
  • pkg/tide/status.go:209-216 and pkg/config/tide.go:550,583 — Tide's missingLabels filter is a generic string list; confirms a new blocking label needs zero Tide changes.
  • pkg/labels/labels.go:22-54 — established do-not-merge/* naming convention (BlockedPaths, CpUnapproved, Hold, InvalidOwners, MergeCommits, WorkInProgress) a new label would fit cleanly.
