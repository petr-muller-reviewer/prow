Verdict

Accepted — as a real bug, but not the one the issue title/body describe. This is a full re-triage: the originally-proposed Deck-side fix (hide stale GitHub-only contexts client-side) was rejected on the issue itself, and independently by prior art (PR #615, rejected in review). The actionable bug that survived scrutiny is in pkg/statusreconciler: two confirmed, code-verified gaps in its one-shot context-retirement pass — an in-flight job at retirement time, and a closed-then-reopened PR. Both were independently re-verified against the source, not taken on the issue thread's word.

What the issue reports

  • Originally filed as: Deck's PR status page can show a context for a presubmit job that no longer exists (renamed/removed from config), because getFullPRContext never evicts a GitHub-only entry.
  • A maintainer challenged the value of that fix on the issue: hiding a context that genuinely exists on the commit has unclear value, may interfere with Tide, and any implementation needs a fragile heuristic — plus it duplicates work status-reconciler is already meant to do.
  • The issue author then investigated pkg/statusreconciler directly and, through discussion, converged on two real, specific gaps in its retirement logic (see Analysis).
  • A third hypothesis — a stale context "spreading" to an unrelated new PR/commit — was raised, investigated, and correctly retracted; no such mechanism exists.

Analysis

Probable cause

pkg/statusreconciler's retirement pass is one-shot and point-in-time: it retires a removed/renamed presubmit's GitHub context once, synchronously, when the config delta that removed it is processed. Nothing persists which contexts/PRs were actually retired — only the whole config snapshot persists — so there's no way to detect or catch up on missed work later. This produces two independent blind spots.

causeIn-flight job at retirement time is not aborted or rechecked

pkg/statusreconciler/controller.go:294-322, pkg/statusreconciler/migrator/migrator.go:232-249

retireRemovedContexts retires a context immediately with no check against ProwJob state. processPR has no ProwJob lookup, and there is no abort/cancellation logic anywhere in pkg/statusreconciler (confirmed via code search, zero hits). A ProwJob still running when its job is removed from config can finish afterward and re-report its own (now stale) status via crier, silently overwriting the retirement.

causeClosed-then-reopened PR is permanently missed

pkg/github/client.go:2144-2169, pkg/statusreconciler/migrator/migrator.go:252-268, pkg/statusreconciler/controller.go:228, controller.go:409-437

// GetPullRequests get all open pull requests for a repo.
func (c *client) GetPullRequests(org, repo string) ([]PullRequest, error) {
  ...
  path := fmt.Sprintf("/repos/%s/%s/pulls", org, repo)
  ...
}

No state parameter is passed, so GitHub defaults this endpoint to state=open. migrator.Migrate() and controller.go's triggerNewPresubmits both consume it this way. A PR closed at the moment a config delta is processed is invisible to that retirement pass; since each delta's diff (removedPresubmits) only reports jobs that transitioned out of config in that specific delta, a later reopen of the PR is never revisited and its stale context is permanently missed.

reproducibilityThird hypothesis investigated and retracted

pkg/prstatus/prstatus.go

An initially suspected gap — a stale context "spreading" to a brand-new PR/commit after retirement — was checked and ruled out. getHeadContexts only ever queries the current HEAD SHA via GetCombinedStatus/ListCheckRuns; there is no mechanism for an old commit's status to appear on an unrelated new commit.

Related code

related-codeSequential controller loop constrains any in-flight-job fix

pkg/statusreconciler/controller.go:161-183

func (c *Controller) Run(ctx context.Context) {
  changes, err := c.statusClient.Load()
  if err != nil {
    logrus.WithError(err).Error("Error loading saved status.")
    return
  }

  for {
    select {
    case change := <-changes:
      start := time.Now()
      log := logrus.WithField(...)
      if err := c.reconcile(change, log); err != nil {
        log.WithError(err).Error("Error reconciling statuses.")
      }
      log.WithField("duration", ...).Info("Statuses reconciled")
      c.statusClient.Save()
    case <-ctx.Done():
      logrus.Info("status-reconciler is shutting down...")
      return
    }
  }
}

Relevance: Run() is single-goroutine and fully sequential — one delta's reconcile (trigger/retire/migrate) completes, then statusClient.Save() is called unconditionally, even if reconcile returned an error, before the next delta is read. Any fix that blocks mid-retirement (e.g. waiting for a job to finish) would stall every subsequent delta across every repo, not just the affected one.

related-codeExisting abort + crier-skip pattern a fix could reuse

pkg/plugins/trigger/pull-request.go:170-199, pkg/crier/reporters/github/reporter.go:72-87

// abortAllJobs (pull-request.go): sets Status.State/Status.Description only
job.Status.State = prowapi.AbortedState
job.Status.Description = abortedDescription

// ShouldReport (github reporter.go): checks Spec.Report first
func (c *Client) ShouldReport(_ context.Context, _ *logrus.Entry, pj *v1.ProwJob) bool {
  if !pj.Spec.Report {
    return false
  }
  ...
}

Relevance: abortAllJobs does not touch Spec.Report. Crier's github reporter ShouldReport checks Spec.Report first and skips entirely if false. A status-reconciler abort that additionally sets Spec.Report = false in the same update would prevent a report race with crier without needing direct coordination — verified both sides of this claim in code.

related-codeProwJobClient reaches the controller but not the migrator

pkg/statusreconciler/controller.go:41-70

func NewController(..., prowJobClient prowv1.ProwJobInterface, githubClient github.Client, ...) *Controller {

      prowJobClient: prowJobClient,

      ...

    githubClient: githubClient,

Relevance: prowJobClient is passed into NewController and used only to build kubeProwJobTriggerer (the presubmit-triggering path); gitHubMigrator (the retirement/migration path) is constructed with only githubClient, no ProwJob awareness at all. A fix needs to thread prowJobClient into gitHubMigrator as well. ProwJobSpec.Context is a plain string field (pkg/apis/prowjobs/v1/types.go:171), directly usable for matching without any annotation scheme.

Recommended next steps

  • Retitle the issue (or add a clarifying top comment) to reflect the actual scope: status-reconciler retirement gaps, not a Deck display bug.
  • Consider removing the area/deck label — the Deck-side proposal was explicitly rejected on the issue, and research confirms the real gaps are entirely within status-reconciler.
  • Split into two independently-shippable pieces given very different risk profiles: (1) closed-then-reopened-PR revisit cursor, (2) in-flight-job abort.
  • Before any implementation on the in-flight-job piece, get explicit maintainer sign-off on the abort-vs-block trade-off (sunk CI compute vs. a residual report-race window) — this is a product decision, not an implementation detail.
  • Once cursor-persistence semantics (per-repo scoping, only-advance-on-full-success) are agreed, the closed-PR piece could be scoped as a standalone, lower-effort follow-up issue.
