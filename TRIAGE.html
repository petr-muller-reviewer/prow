Verdict

Accepted. This is a legitimate, reproducible bug in tide's pool-building and batch-trigger logic: stale GitHub search results for just-merged PRs are trusted with no independent merged-state check anywhere in the pipeline, and a merge's base-SHA bump invalidates the whole subpool's job-match state at once, causing the stale PR to be swept into a freshly picked batch. Confirmed independently by two reporters and by a maintainer's own investigation. A small, additive fix (post-query merged-state filter) is well-defined and ready for a contributor to pick up; effort assessed at Level 2 (help-wanted).

What the issue reports

  • Tide fired a TRIGGER_BATCH ProwJob that included PR #4297 on Azure/ARO-HCP just 3 minutes after that PR was manually merged.
  • Reporter expected a merged PR to never be included in a batch.
  • A second maintainer (raelga) independently observed the same pattern recur consistently on the same repo (PR #4488).
  • Maintainer petr-muller confirmed, after his own investigation, that this happens more often than the team realized, and traces back to around November 2025.
  • A prior AI-assisted investigation (referenced but not directly available here) proposed adding a merged field as a post-query filter, and floated merge-attempt backoff via the existing history package as a possible complementary fix.

Analysis

Reproducibility / observed behavior

reproducibility

Confirmed independently by two reporters with concrete tide-history timeline evidence (9:50 merge → 9:53 TRIGGER_BATCH including the merged PR), and by the maintainer's own follow-up investigation, which found the issue is more frequent than initially assumed and dates back to roughly November 2025.

Probable cause

cause

No merged/closed-state check anywhere in tide's pool pipeline

The PullRequest GraphQL struct tide uses (pkg/tide/tide.go:1990-2026) has no Merged/MergedAt/State/Closed field — only Mergeable, MergeStateStatus, CanBeRebased, contexts, commits, labels. filterPR() (pkg/tide/tide.go:755-793) and mergeChecker.isAllowedToMerge() (pkg/tide/github.go:600-627) never check merge/closed state either. The only "Merged" occurrence in pkg/tide/*.go is a post-merge log line at pkg/tide/github.go:289 — not derived from any query result. So a stale GitHub search result that still reports state:open for an already-merged PR is trusted at face value and enters the pool unfiltered.

cause

Batch-trigger branch evaluated before single-retest branch

dividePool() (pkg/tide/tide.go:1938-1967) recomputes each subpool's base SHA fresh every sync via c.provider.GetRef(...). ProwJobs are matched into the subpool only by exact (org, repo, branch, sha) (pkg/tide/tide.go:1974). A merge bumps this SHA, invalidating job-match state for every PR in the subpool simultaneously — not just the merged one — so several PRs look "missing" at once (accumulate(), pkg/tide/tide.go:1080-1136; accumulateBatch(), pkg/tide/tide.go:946-1038). takeAction() (pkg/tide/tide.go:1545-1588) checks the batch condition len(sp.prs) > 1 && len(batchPending) == 0 before the single-PR retrigger condition, so the batch path wins and sweeps in the stale merged PR. This matches the maintainer's own observation that a just-merged PR shows up in TRIGGER_BATCH but essentially never in a plain TRIGGER.

Related code

related-code

pkg/tide/history/history.go — no per-PR merge-attempt tracking

type Record struct {
    Time      time.Time
    Action    string // e.g. "TRIGGER", "TRIGGER_BATCH", "MERGE", "MERGE_BATCH"
    BaseSHA   string
    Target    []prowapi.Pull
    Err       string
    TenantIDs []string
}

Floated in the issue thread as a possible basis for merge-attempt/backoff tracking. It is a pure append-only audit log keyed per subpool (org/repo:branch), written once per sync from syncSubpool() (pkg/tide/tide.go:1809-1818). No per-PR lookup capability exists today — reusing it for backoff would need new indexing, not just consumption.

related-code

Natural insertion point for a fix — pkg/tide/github.go:102-151

GitHubProvider.Query() converts every raw GraphQL search node into the pool unconditionally. This is the cheapest place to add a Merged-state guard, before the PR ever reaches filterPR() or subpool division.
