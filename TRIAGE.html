What the Issue Reports

  • During the k8s 1.33.0 release, multiple release managers independently clicked “Rerun” on the same failed Conformance-GCE-1.33-kubetest2 job, producing 3 simultaneous runs and wasting CI resources.
  • There is no mechanism in Deck to detect or prevent a duplicate rerun when another user has already triggered one moments before.
  • BenTheElder noted that the existing job_queue_name / JobQueueCapacities feature can enforce n=1 concurrency, but it is opt-in and not configured for most jobs.
  • The request is for automatic deduplication so that a second “Rerun” click returns the already-queued job rather than creating a new one.

Analysis

Root Cause

Race condition + no deduplication at Deck level

  1. Deck creates jobs unconditionally: handleRerun() at cmd/deck/rerun.go:326 creates a new ProwJob with a unique UID on every call, with no check for recently-created pending reruns.
  2. Plank’s concurrency check is timing-dependent: Plank counts “pending or older triggered” jobs (pkg/plank/reconciler.go:1117-1139). If two reruns arrive before the first transitions TriggeredState → PendingState, both pass and execute simultaneously.
  3. Queue feature not universally applied: job_queue_name + JobQueueCapacities solve the problem but are opt-in; the Conformance-GCE job had no queue configured.

Contributing Factors

  • Multiple users with rerun permissions active simultaneously during a release
  • No UI feedback indicating a pending rerun already triggered by another user
  • Serialization locks prevent same-thread races within Plank’s reconciler but not cross-request races via the API server
  • Brief TriggeredState → PendingState window (seconds) is wide enough for duplicates to slip through

Solution Approaches

Recommended: Deduplication check in Deck (handleRerun())

Before creating a new ProwJob at line 326, query for existing ProwJobs with the same name in SchedulingState, TriggeredState, or PendingState within a recent time window (5–10 min). If found, return the existing job with informative UI feedback (“A rerun was already triggered 3 min ago by user X”).

  1. Add findRecentPendingRerun(ctx, jobName, within) (*ProwJob, error) helper
  2. Call before line 326 in handleRerun()
  3. Return informative HTTP response when duplicate detected
  4. Optional: configurable time window, per-job opt-out, metrics for blocked reruns

Effort: ~200–300 LOC across 2–4 files. Suitable for contributors with Go + client-go experience. Not a good-first-issue.

Alternative: Automatic queue assignment with default capacity 1

Auto-assign all jobs to implicit queues by job name, default capacity 1. Zero config; uses existing infrastructure. Risk: changes default behavior for legitimately parallel jobs; requires opt-out mechanism. Complexity: Medium.

Alternative: Global default MaxConcurrency config

Add default_max_concurrency_per_job_name: 1 config field. Minimal code change. Does not prevent duplicate ProwJob creation; delayed feedback; jobs still sit in SchedulingState. Good as defense-in-depth alongside the recommended approach. Complexity: Low.
