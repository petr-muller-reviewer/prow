ACCEPTED

Legitimate feature request. Tide's includedBranches/excludedBranches only support exact string matching while branchprotector supports regex — the inconsistency is real and the use case (covering release-* or feature/* patterns) is valid. However, the implementation is significantly more complex than the issue implies because the GitHub Search API's base: qualifier does not support regex, requiring a deliberate workaround. A design discussion should precede any implementation PR.

What the issue reports

  • Tide's TideQuery.includedBranches and excludedBranches fields accept only exact branch name strings — no wildcards or patterns.
  • Users with patterned branch names (release branches, feature branches) must enumerate every branch explicitly in their Tide config.
  • Branchprotector already supports regex for its include/exclude fields (cmd/branchprotector/protect.go:312-346).
  • The request is to add the same capability to Tide for consistency and flexibility.
  • The issue has been repeatedly marked stale and revived by the author, indicating real ongoing need.

Analysis

Probable cause / why this is hard

The branchprotector analogy is architecturally misleading. Branchprotector enumerates all branches via the GitHub Branches API, then filters locally using compiled *regexp.Regexp. Tide works entirely differently: constructQuery() translates each branch name into a base:"X" or -base:"X" qualifier in a GitHub Search API query, and GitHub executes the filter server-side. The GitHub Search API's base: qualifier is exact-match only — it does not support regex patterns. Any regex implementation in Tide requires a workaround.

Additionally, the branch matching in requirementDiff() (pkg/tide/status.go:149-155) only scores query-to-PR affinity for status display purposes — it does not drive merge decisions. A regex fix applied only there would be incomplete.

Implementation approaches

Three workarounds exist; none is cost-free:

  1. Enumerate-and-expand: Call the GitHub Branches API before query construction, expand regex matches to explicit branch names, pass those as base: qualifiers. Correct semantics; adds one Branches API call per org/repo per sync cycle.
  2. Local post-filter: Omit base: qualifier when patterns are configured, fetch all open PRs, filter locally. No extra API calls; potentially much larger result sets.
  3. New config fields (includedBranchPatterns/excludedBranchPatterns): Add separate fields for patterns alongside the existing exact-match fields. Fully backwards compatible, cleaner API surface; uses either approach 1 or 2 as the backend.

Recommended: Approach 3 (new fields) + Approach 1 (enumerate-and-expand). Requires a design discussion before implementation begins.

  • requirementDiff() confirmed to be status scoring only, not merge gating — a partial fix there would be insufficient.
