Verdict

Accepted — legitimate correctness bug in the approve plugin.

The reporter (a Kubernetes approver) demonstrated, with an exact reproduction on an external PR, that the approve plugin's "manually added approval" bypass keeps the approved label in place even after a PR's file set changes to one the original approver has no OWNERS authority over. This is a real gap in ManuallyApproved()'s logic, not a misconfiguration or misunderstanding — it's actionable without further reproduction work, though the exact failure mode (bot misidentification vs. under-scoped override) needs one more piece of evidence before a fix is written.

What the issue reports

  • A KEP PR (kubernetes/enhancements#5923) was opened under keps/sig-network/; the author is a sig-network approver, so self-approval correctly satisfied requirements and the bot added approved.
  • The PR was later repushed with the KEP moved to keps/sig-architecture/, where the author is not an approver.
  • The bot's re-evaluation should have removed the approved label, but instead the notifier comment read "Approval requirements bypassed by manually added approval" and the label stayed.
  • The reporter correctly identifies this as wrong: their sig-network approval authority has no bearing on a PR now scoped to sig-architecture.

Analysis

Reproducibility / observed behavior

Not independently reproduced in this repo (the bug manifests against kubernetes/enhancements, a downstream consumer of this plugin), but the linked PR comment is unambiguous evidence: kubernetes/enhancements#5923#issuecomment-5453924514 shows both "Author self-approved" attribution and the "bypassed by manually added approval" branch of the notifier template rendering simultaneously — meaning RequirementsMet() was false (correctly, post file-set change) while ManuallyApproved() was true (incorrectly, or at least unexpectedly to the reporter).

Probable cause

Approvers.IsApproved() is defined as:

func (ap Approvers) IsApproved() bool {
	return ap.RequirementsMet() || ap.ManuallyApproved()
}

RequirementsMet() / AreFilesApproved() correctly recompute against the PR's current file set on every handle() run — self-approval is properly OWNERS-scoped (verified by reading UnapprovedFiles), so it did flip to false once the KEP moved directories. The problem is ManuallyApproved(): it's computed once and cached per handle() call, and its only signal is "was the actor of the most recent labeled GitHub event for the approved label non-bot?" That check has no correlation to which file set was active when that event fired, and no expiry when later pushes change the file set entirely — so once true, it silently masks correct, freshly-computed false results indefinitely.

Two candidate explanations, not yet disambiguated:

  • (a) Bot-identity misdetection — WasLabelAddedByHuman/BotUserChecker may not correctly recognize the actual bot/GitHub App identity acting on kubernetes/enhancements, making a genuinely-automated label add look human. Narrow fix if true.
  • (b) Under-scoped intentional override — a human really did force the label once (a documented, intentional design feature — see doc comment below), but the override has no bound tied to the file set it was granted for. Broader design fix if true.

Disambiguating requires the actual GitHub issue-events timeline for kubernetes/enhancements#5923, not available during this triage pass.

func (c *client) WasLabelAddedByHuman(org, repo string, number int, label string) (bool, error) {
	isBot, err := c.BotUserChecker()
	...
	events, err := c.ListIssueEvents(org, repo, number)
	var lastAdded ListedIssueEvent
	for _, event := range events {
		if event.Event != IssueActionLabeled || event.Label.Name != label {
			continue
		}
		lastAdded = event
	}
	if lastAdded.Actor.Login == "" || isBot(lastAdded.Actor.Login) {
		return false, nil
	}
	return true, nil
}

Open questions

What GitHub identity performs Prow's bot actions against kubernetes/enhancements, and does BotUserChecker correctly recognize it there?
Should any change to the set of OWNERS-protected files touched by a PR force a fresh RequirementsMet re-evaluation and label removal, with ManuallyApproved only ever acting as a one-time, non-persistent override?
