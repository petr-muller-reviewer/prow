Verdict

Keep open as needs-discussion. The disclosure gap is reproducible and affects Prow-owned shared code, but maintainers need to define the supported structured-format/value-extraction policy before accepting an implementation. Automatically making JSON and INI special raises the same question for YAML, TOML, XML, and other structured secrets.

What the issue reports

  • A complete JSON or INI secret file is censored when emitted verbatim.
  • A job can extract and log one child value, which is not currently registered for replacement.
  • The reporter supplied dummy AWS INI and JSON examples plus an external reproduction.
  • The report correctly notes that sidecar-only work would not protect in-process logs.

Analysis

Reproducibility / observed behavior

Refresh registers the payload, its trimmed representation, and base64 encodings. A child value from a valid JSON/INI document is none of those strings, so it remains visible when logged alone. Evidence: reporter reproduction and pkg/secretutil/censor.go:101-126.

Probable cause

The shared raw-payload registration has no structure awareness:

for _, secret := range secrets {
    toEncode := []string{secret}
    ...
    addReplacement(secret)
    for _, item := range toEncode {
        encoded := base64.StdEncoding.EncodeToString([]byte(item))
        addReplacement(encoded)
    }
}
c.Replacer = bytereplacer.New(replacements...)

This is pkg/secretutil/censor.go:101-131; no JSON, INI, or other child-value extraction occurs before replacements are built.

Related code

Process logging shares the affected censorer (pkg/config/secret/agent.go:155-172):

for _, value := range a.secretsMap {
    secrets = append(secrets, value.getRaw())
}
...
a.ReloadingCensorer.RefreshBytes(secrets...)

Therefore a sidecar-only change leaves process formatter/output censoring with the same limitation.

The sidecar has narrow duplicate extraction (pkg/sidecar/censor.go:507-545,567-619):

secrets = append(secrets, raw)
if info.Name() == ".dockercfg" { parser = loadDockercfgAuths }
if info.Name() == ".dockerconfigjson" { parser = loadDockerconfigJsonAuths }
if slices.Contains(iniFilenames, info.Name()) { parser = loadIniData }
extra, parseErr := parser(raw)

Docker auth fields and explicitly configured INI filenames receive special treatment; generic JSON does not. loadIniData already recursively collects INI key values.

Policy boundary

Extracting all JSON/INI values centrally fixes the supplied cases but creates an arbitrary format boundary and can redact harmless configuration values. YAML, TOML, XML, and other structured formats have the same child-value property. Current INI extraction is explicit filename opt-in in pkg/sidecar/options.go:125-132; the generic JSON fixture pkg/sidecar/testdata/secrets/a/service-account.json is not individually extracted.

Related issues / PRs

GitHub searches for censor secret JSON INI and secret censor found no related issue or open PR beyond #939.

What I checked

  • Checked upstream-main revision d91e0f84e0f2050b41390b28b69a05f5284ba4a2.
  • pkg/secretutil/censor_test.go:25-218 covers raw, trimmed, base64, boolean, and minimum-length behavior but no generic structured payload.
  • pkg/sidecar/censor_test.go:151-166,309-367 covers opt-in INI and Docker extraction only.
  • The boolean exception and minimum_secret_length are intentional shared-censorer protections; gopkg.in/ini.v1 and encoding/json are already available.

Recommended next steps

  1. Decide the contract: whole-blob-only, a bounded built-in format set, or explicit opt-in format/value extraction.
  2. If extraction is chosen, apply it at shared secret registration so sidecar and process logging have identical coverage; retain raw registration on parse failures.
  3. Define whether all string leaves or only explicit sensitive paths are registered; do not register JSON keys or numeric scalar values by default.
  4. Add regressions for nested JSON/arrays, INI sections, invalid documents, short/boolean values, base64, and both shared-censorer callers.
  5. Apply kind/bug, area/pod-utilities, area/podutils/sidecar, and sig/security; defer help wanted until policy is settled.

Open questions

  • Should the contract state that all values of a supported structured secret are sensitive, or require explicit value/path selection?
  • Which formats are in scope, and why should unsupported formats be excluded?
  • Should existing IniFilenames remain as compatibility configuration if extraction becomes centrally configurable?
