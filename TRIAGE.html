kubernetes-sigs/prow#693
Integrate with Netlify for /retest Prow command

State: open Labels: kind/featurearea/plugins Triaged: 2026-05-30T13:22:53Z Main SHA: 53a81071b Original: test-infra#35103 Author: Caesarsage (Destiny Erhabor)

Verdict

needs-discussion

The feature is legitimate and architecturally feasible within Prow, but the Netlify API situation is unresolved. No documented API endpoint exists for triggering deploy preview rebuilds. Caesarsage's spike (2026-04-30) claims an undocumented POST /api/v1/deploys/{deploy_id}/retry endpoint works, but this is unverified and absent from the official Netlify OpenAPI spec. If confirmed, the Prow change is straightforward (Level 2, following the TriggerGitHubWorkflows pattern). If not, the feature is blocked at Level 4. Security concern also open: Netlify PATs have no granular scoping. Both questions need resolution before implementation proceeds.

What the Issue Reports

  • When an org member uses /retest on a PR in k/website or k/contributor-site, Netlify should rebuild the deploy preview.
  • Currently the only self-service option is the PR author pushing an amended/empty commit — high friction for a simple flake retry.
  • Originally filed at test-infra#35103 by lmktfy (Tim Bannister, SIG Docs chair); copied here by Caesarsage because GitHub does not allow cross-org issue transfers.
  • BenTheElder noted Netlify exposes deploy triggers "but that's not quite it" and raised security concerns about handing Netlify credentials to presubmits that run arbitrary user code.
  • Caesarsage self-assigned and posted a spike result on 2026-04-30 claiming an undocumented retry endpoint exists.

Analysis

Netlify API — documented endpoints

MethodTriggers build?True deploy preview?Updates PR status?
Build hook + trigger_branchYesNo — branch deployNo
POST /sites/{id}/buildsYesNo — prod onlyNo
POST /sites/{id}/deploys with branchPartialNoNo
Push empty commit to PR branchYesYesYes
Re-deliver GitHub webhook (repo admin)YesYesYes
POST /deploys/{id}/retry (undocumented)YesClaimed yesUnverified

Key distinction: a deploy preview is tied to a PR number, gets the URL deploy-preview-N--site.netlify.app, and posts status back to the GitHub PR. A branch deploy has none of those properties.

Caesarsage's spike (2026-04-30) — unverified

Caesarsage confirmed build hooks and POST /sites/{id}/builds produce only branch deploys (consistent with our analysis), then claimed POST /api/v1/deploys/{deploy_id}/retry reruns the same deploy preview for forked PRs and preserves PR preview identity.

This endpoint is absent from Netlify's official OpenAPI spec (v2.53.0). The only supporting evidence is a Nov 2023 community thread where even the original poster could not find it in official docs. No curl transcript or API response was provided.

If the endpoint works as claimed, feasibility shifts from Level 4 (blocked) to Level 2-3 (moderate). Security concern remains active: Netlify PATs have no granular scoping — a token grants full account access.

Existing Prow pattern for external CI

TriggerGitHubWorkflows at pkg/plugins/trigger/generic-comment.go:168-196 is the exact template. On /retest it fetches failed GitHub Action runs and re-triggers them via the GitHub API, in parallel with ProwJob re-creation. A Netlify integration would add an analogous config option (e.g. TriggerNetlifyDeployPreviews) to the Trigger struct and follow the same goroutine pattern.

Recommended Next Steps

  1. Ask Caesarsage to share a curl transcript or minimal test demonstrating that POST /api/v1/deploys/{deploy_id}/retry produces a deploy preview (not a branch deploy) and updates the GitHub PR status check.
  2. If endpoint is confirmed: open design discussion on credential handling — how a Netlify PAT would be stored (Kubernetes Secret?) and referenced from trigger plugin config. Precedent needed.
  3. If endpoint is confirmed and security model agreed: implement following TriggerGitHubWorkflows pattern — new bool in Trigger struct, config for site ID + PAT secret ref, goroutine calling GET /sites/{site_id}/deploys to find deploy_id then POST /deploys/{id}/retry.
  4. If endpoint is unreliable or undocumented risk is unacceptable: post a comment documenting workarounds (empty commit, webhook re-delivery) and note this is blocked pending Netlify API improvements.

Open Questions

  • Does POST /api/v1/deploys/{deploy_id}/retry actually preserve the deploy-preview-N URL and update the GitHub PR status check? Can Caesarsage share a test transcript showing the before/after status?
  • How does Prow look up the deploy_id for a PR's latest deploy preview? Likely GET /sites/{site_id}/deploys?branch=deploy-preview-{pr_number} — needs verification that this query works and returns the right deploy.
  • Is relying on an undocumented Netlify endpoint acceptable for upstream Prow? What's the policy on undocumented external APIs?
  • How should Netlify credentials be stored and referenced? Kubernetes Secret + config field pointing to it? Is there precedent in Prow for other external API credentials?
