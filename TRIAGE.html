What the issue reports

  • Blunderbuss currently selects reviewers randomly from OWNERS files via PopRandom(), ignoring who actually wrote or maintains the changed code.
  • Proposes a blame-based scoring formula: score = (line_count × 10) + (recency_score × 5) + owner_bonus, using GitHub's GraphQL blame API to rank OWNERS-listed candidates.
  • Only OWNERS-listed reviewers are eligible — blame data ranks existing candidates, does not discover new ones.
  • Proposes smarter fallback when ReviewerCount cannot be met: look at reviewers/approvers elsewhere in the repo, rank by blame data, fall back to random if no blame scores available.
  • Motivated by reviewer fatigue, slow review cycles, and reviewers ignoring assignments when they have no context on the changed code. Author has built similar tooling in OpenShift's internal ai-helpers.

Analysis

Current implementation

The blunderbuss plugin (pkg/plugins/blunderbuss/blunderbuss.go, 477 lines) assigns reviewers on PR open, /auto-cc comment, or status event. The selection pipeline:

  1. handle() (line 319) loads OWNERS via LoadRepoOwners(), fetches changed files via GetPullRequestChanges().
  2. getReviewers() (line 380) iterates changed files, finds OWNERS files for each, collects leaf reviewers into a layeredsets.String with three priority layers.
  3. findReviewer() (line 433) calls PopRandom() from the first non-empty layer. Optionally checks GitHub availability status via GraphQL.
  4. If not enough reviewers, falls back to approvers (unless ExcludeApprovers is set).

PR #787 — the rifle plugin

The author chose approach B (separate plugin) from the triage options. The PR:

  • Adds a new pkg/plugins/rifle/ package with rifle.go, blame.go, and tests.
  • Adds GetBlame to the GitHub client (pkg/github/client.go) using GraphQL with Apps auth support.
  • Extracts shared reviewer logic into pkg/reviewer/reviewer.go.
  • Still uses the original scoring formula: (lines × 10) + (recency × 5) + owner_bonus with +3 approver / +2 reviewer — which the maintainer flagged as backwards.
  • 17 files changed total.

Maintainer concerns (from issue comments)

  • Concentration of review load: Blame-based ranking assigns more reviews to prolific authors, making busy people busier instead of spreading opportunities.
  • Contributor ladder conflict: Kubernetes reviewers are expected to review areas they may not be deeply familiar with — that's how they grow. Approvers serve as the safety net. Weighting by blame history works against this.
  • Formula inversion: The proposed owner_bonus (+3 approver, +2 reviewer) is backwards — reviewers should be primary assignees, not approvers.
  • Must be opt-in: Not a unilateral change to the default algorithm. The separate plugin approach satisfies this concern.
