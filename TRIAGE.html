Verdict: ACCEPTED — keep open, legitimate bug

Tide's merge decision never checks GitHub branch protection's required_approving_review_count; it merges based purely on its own lgtm/approved labels and CI status. Because Tide's bot account typically holds admin/bypass-branch-protection permission, GitHub itself doesn't stop it. This is a confirmed code-level gap, not a misconfiguration, already correctly labeled `kind/bug`, `area/tide`. No further author info is needed; the fix requires new implementation work sized as a Level 3 effort.

What the issue reports

  • With org-level Tide config requiring approved + lgtm labels, and a repo branch-protection rule requiring 2 approving reviews, Tide merged a PR with only one review.
  • The reporter verified GitHub's own UI correctly blocks the manual merge button with only one approval (screenshot in original report) — so branch protection is genuinely configured and would work for a human.
  • Reporter asked whether an undocumented tide.queries.reviewApprovedRequired setting was the missing piece — it isn't a review-count feature.
  • Follow-up discussion (dhaiducek, kaovilai, petr-muller) converged on: Tide's bot account is a repo admin, and GitHub branch protection doesn't apply to admins unless enforce_admins is explicitly enabled.
  • A later comment (2026-04-01) notes that enabling enforce_admins as a workaround triggers a different bug (issue #673): Tide gets stuck retrying the same now-unmergeable PR indefinitely.

Analysis

Reproducibility / observed behavior

Reproducible by configuration, not a transient failure: any org/repo with required_approving_review_count >= 1 and no enforce_admins, combined with a Tide bot holding admin/bypass permission (the common default), exhibits this. Confirmed independently by two reporters (dhaiducek, kaovilai) across multiple repos/orgs from 2024-04-25 through 2026-04-01.

Probable cause

Tide's merge gate (mergeChecker.isAllowedToMerge) only checks GraphQL Mergeable (conflict state) and merge-method labels — never branch protection's review-count requirement. Pool membership (filterPR/filterSubpool) is decided purely by tide.queries labels/missingLabels and CI status. The final merge call is unconditional aside from that gate. RequiredApprovingReviewCount exists in the codebase, but only for branchprotector to configure GitHub — never consumed by Tide itself.

Open questions

Should the fix be a hard pre-merge gate, or opt-in config — some deployments may rely on today's bypass semantics (e.g. override-command workflows)?
Should scope include CODEOWNERS-based required reviewers, or just a plain approving-review-count check for a first PR?
Should the check live inside mergeChecker.isAllowedToMerge directly, or as a separate cacheable pre-check, given the added GitHub API cost per sync loop across large pools?
