Accepted. This is a real bug in the cherrypicker external plugin. The plugin uses git am --3way exclusively; git am strips CR from CRLF lines by default during mail processing, causing the patch context to mismatch when files in the repository use CRLF endings. git am --keep-cr --3way, git apply --3way, and git cherry-pick all succeed on the same patch.

What the issue reports

  • The cherrypicker plugin fails to cherry-pick a merged PR onto a release branch, claiming a conflict exists.
  • The same patch applies cleanly using git apply --3way and git cherry-pick — there is no real conflict.
  • The error message is "patch does not apply" / "does not apply to blobs recorded in its index", which is a git am-specific failure mode.
  • Fully reproducible with a public PR (karmada-io/website#1022) and target branch release-1.18.
  • Reporter provides exact reproduction commands and identifies the root cause as a git am limitation.

Since previous triage (2026-06-09):

  • valen-mascarenhas14 commented on 2026-06-14 with a more precise root cause: the 6 compatibility.md files were stored with CRLF line endings. git am strips CR by default during mail processing, causing the patch context to no longer match the working tree. git am --keep-cr --3way succeeds.
  • valen-mascarenhas14 volunteered to implement a retry with git am --keep-cr --3way when plain git am --3way fails.

Analysis

Probable cause (refined)

The cherrypicker downloads the PR patch from GitHub (in git format-patch / mbox format) and applies it using git am --3way. git am strips carriage returns from CRLF lines by default during mail processing. When files in the repository use CRLF line endings, the patch contains CRLF context lines, but git am normalizes them to LF. This causes the patch context to no longer match the actual file content, and the apply fails.

git am --keep-cr disables this behavior, preserving the original CRLF endings. The git am documentation describes this option. git apply --3way and git cherry-pick do not perform this CR stripping, which is why they succeed.

The original hypothesis (missing base blobs on divergent branches) may still independently cause failures in other scenarios, but the confirmed trigger for this report is CRLF stripping.

Reproducibility

Fully reproducible using the reporter's steps. Independently confirmed by valen-mascarenhas14 on 2026-06-14. The comment log shows the exact cherrypicker output. Both git am --keep-cr --3way and git apply --3way succeed on the same patch.

What I checked

  • No existing issues or PRs in kubernetes-sigs/prow address this problem.
  • No configuration option exists to select alternative cherry-pick strategies.
  • The Interactor interface has no Apply() or CherryPick() method — only Am().
  • cherrypickapproved and cherrypickunapproved in pkg/plugins/ are separate label-management plugins, not involved in the actual cherry-pick operation.
  • CRLF root cause confirmed by valen-mascarenhas14's local reproduction (2026-06-14).

Recommended next steps

  • Label as kind/bug, area/cherrypicker, help-wanted.
  • Recommended fix: retry with git am --keep-cr --3way when plain git am --3way fails. Simpler than the original "fallback to git apply" proposal — stays within the git am family, preserves commit metadata automatically. Alternatively, use --keep-cr by default (harmless on non-CRLF repos).
  • Broader fallback to git apply --3way could still be considered for cases where --keep-cr doesn't help (e.g. genuine blob-missing scenarios on divergent branches).
  • valen-mascarenhas14 has volunteered to implement. Respond to their comment with guidance on approach.

Open questions

  • Is retrying with --keep-cr sufficient, or should the fix also include a git apply --3way fallback for non-CRLF failure cases?
  • Should --keep-cr be the default instead of a retry? It's harmless on non-CRLF repos (no effect when there are no CRs to keep).
