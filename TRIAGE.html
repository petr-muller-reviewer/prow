This is a legitimate, well-motivated feature request for Prow components that live in this repo. The problem is real and reproducible: /override results are silently lost whenever the target branch advances, forcing maintainers to repeatedly re-override the same broken job. The author provides two concrete implementation approaches and links the prior discussion (#238). Accepting for labeling and design engagement; effort level 3 — requires an experienced Prow contributor and design discussion before coding.

What the issue reports

  • When a job is overridden via /override, Tide re-triggers it every time the base branch HEAD moves (another PR merges or a commit is pushed to the target branch).
  • This is fine for "reviewed and accepted" overrides, but painful for "job is simply broken / irrelevant" overrides — maintainers must keep re-overriding the same job repeatedly.
  • Proposed: an /override-sticky command that persists the override across retests.
  • Two approaches offered: (1) a plugin that re-applies overrides when cleared, or (2) a Tide modification that skips triggering sticky-overridden jobs entirely.
  • Prior discussion in #238 (2024) was closed by the original reporter without a fix.

Analysis

Probable cause — why overrides are re-triggered

Prow's status reporter embeds the current baseSHA into status context descriptions using ContextDescriptionWithBaseSha(). When the base branch advances, Tide's prowJobsFromContexts() (pkg/tide/tide.go:1043–1073) synthesizes ProwJob records only from statuses whose embedded baseSHA matches the new subpool SHA. This allows Tide to recognize valid results even after sinker GCs the original ProwJobs.

The /override plugin does not use ContextDescriptionWithBaseSha(). It sets the description to the plain string "Overridden by <user>", which contains no baseSHA. As a result:

  • BaseSHAFromContextDescription("Overridden by X") returns "" — override status is never promoted to a synthetic ProwJob.
  • The real override ProwJob was created with the old baseSHA; when the subpool's sp.sha changes, it falls out of scope.
  • accumulate() finds no ProwJob for the context at the new baseSHA+headSHA combination → context is "missing" → Tide triggers the job.

Proposed solution — Approach 1 (recommended): plugin-based re-apply

Introduce /override-sticky <job> which applies a normal override AND records sticky intent as a GitHub PR label (e.g. prow-sticky-override/<encoded-context>). A new event handler watches for status changes on that context; when Tide clears the override by triggering the job, the plugin automatically re-applies /override <context>. /override-sticky cancel <job> removes the label.

Pros: Self-contained, no Tide changes, follows the established Prow pattern (labels for persistent state like approved/lgtm), override intent is visible in the GitHub UI.

Cons: Job still gets triggered once before being re-overridden (wasted CI resources + latency); race window between Tide triggering and re-override firing; label naming is awkward when context names contain spaces or slashes.

Alternative — Approach 2: Tide modification

Modify Tide's accumulate() to read sticky-override labels from PRs and skip triggering those contexts. More efficient (job never runs) but couples Tide's core safety logic to the override plugin's label scheme and requires changes to Tide's subpool sync to fetch PR labels.

What I checked

  • description() in override plugin has no call to ContextDescriptionWithBaseSha — confirmed no baseSHA is embedded.
  • Checkrun-based override path (GitHub Apps auth, override.go:530–554) follows the same pattern — override checkrun output has no baseSHA.
  • No existing sticky-override or label-based override persistence anywhere in the codebase.
  • #238 was closed by the original reporter (/close comment), not resolved with a code fix.
  • Override ProwJob creation at override.go:494–496 uses baseSHA from baseSHAGetter() at override time — correct baseSHA for the override moment, wrong for later subpool evaluations.

Open questions

  • Should sticky overrides auto-cancel when the PR head SHA changes (new push to the PR branch)? The issue doesn't address this — canceling on head-change seems safer but reduces utility.
  • What happens to sticky labels if the overridden job is later removed from the required list? Need a cleanup mechanism or orphan handling to avoid a label that silently does nothing.
  • Is GitHub PR label storage sufficient for encoding arbitrary context names (containing spaces, slashes, colons), or does this suggest a different state mechanism (e.g., a structured bot comment marker)?
  • Is Approach 2 (Tide modification) acceptable to maintainers, given the efficiency benefit of not triggering the job at all vs. the coupling concern?
