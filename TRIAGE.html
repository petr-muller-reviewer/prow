Verdict

Accepted as a valid bug in the Tide component.

Two independent bugs compound: (1) a hypothesized context list collision when from-branch-protection: true causes the same context to appear in both RequiredContexts and RequiredIfPresentContexts, and (2) a confirmed silent subpool drop in filterSubpools that swallows the resulting error and leaves affected PRs with no tide status context. The specific collision trigger is a strong hypothesis but not yet confirmed; the silent-drop behavior is confirmed from logs.

What the issue reports

  • TideContextPolicy.Validate() errors when a context appears in both RequiredContexts and RequiredIfPresentContexts.
  • This can happen implicitly when from-branch-protection: true pulls BP-required contexts that are also conditionally-triggered presubmit jobs.
  • filterSubpools catches the error, logs it, and silently drops the entire subpool — no tide status is set on any affected PR.
  • PR authors see no signal: no "error" status, no "pending" status, nothing. Tide appears to ignore the PR entirely.
  • Maintainer has observed the behavior in production with a concrete config: BP-required context + always_run: false + skip_if_only_changed + from-branch-protection: true.

Analysis

Probable cause (hypothesized trigger)

GetTideContextPolicy at pkg/config/tide.go:944-995 builds the context policy from two independent sources:

  1. Branch protection (line 968): when from-branch-protection: true, contexts from bp.RequiredStatusChecks.Contexts are inserted into required.
  2. Job properties (lines 974-976): BranchRequirements() partitions presubmit jobs by trigger behavior. A conditionally-triggered, non-optional job (TriggersConditionally() == true) lands in requiredIfPresent.

When the same context appears in both, Validate() at line 868 rejects the overlap. This is a hypothesis — confirmed that the error fires, but the exact config path producing the collision needs reproduction.

// pkg/config/tide.go:968 — BP contexts go into required
required.Insert(bp.RequiredStatusChecks.Contexts...)

// pkg/config/tide.go:974-976 — job properties may put same context into requiredIfPresent
prowRequired, prowRequiredIfPresent, prowOptional := BranchRequirements(branch, presubmits, requireManuallyTriggeredJobs)
required.Insert(prowRequired...)
requiredIfPresent.Insert(prowRequiredIfPresent...)

Silent subpool drop (confirmed)

filterSubpools at pkg/tide/tide.go:673-676 catches the initSubpoolData error and silently drops the subpool:

if err := c.initSubpoolData(sp); err != nil {
    sp.log.WithError(err).Error("Error initializing subpool.")
    return  // subpool silently excluded from filtered map
}

The status controller runs independently and can only report on PRs it knows about from the pool map. Dropped subpool PRs may get misleading status or none at all.

What I checked

  • Confirmed the error message in the issue matches pkg/config/tide.go:869.
  • Confirmed checkconfig validates context policies at config-load time but cannot catch runtime collisions from from-branch-protection: true.
  • Verified the status controller already uses github.StatusError for merge conflicts and blockers — same pattern could report initSubpoolData errors.
  • Checked that filterSubpools has no error-propagation mechanism.
  • The specific config trigger (BP + conditional job collision) is a hypothesis; the symptom (silent drop, no status) is confirmed.

Recommended next steps

  • Confirm the hypothesis: reproduce with the exact config from the maintainer's comment and verify the Validate error is the one firing.
  • Fix A (higher priority): deduplicate contexts in GetTideContextPolicy after merging BP and job sources, before calling Validate(). Keep Validate() strict so checkconfig still catches explicit misconfigurations.
  • Fix B (hardening): propagate initSubpoolData errors to the tide status context as github.StatusError. Prevents any future init error from being silent.
