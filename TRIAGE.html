Verdict

ACCEPTED — legitimate, scoped feature request

The request to add an advisory_approvers OWNERS field is a legitimate, well-specified feature request that maps cleanly onto pkg/repoowners's existing leaf-vs-full accessor split. It has a directly analogous precedent already in the codebase (RequiredReviewers), is already self-assigned by the author, and carries no architectural risk — recommend keeping it open, labeling it, and letting the author proceed after confirming the field name.

What the issue reports

  • Wants a new advisory_approvers OWNERS field for people (e.g. senior/emeritus maintainers) who should keep /approve authority.
  • These people should never be auto-suggested as reviewers/approvers by blunderbuss (excluded from LeafApprovers()).
  • If also listed under reviewers, they should remain normally selectable as a reviewer.
  • Currently the only workarounds are full approvers membership (gets auto-assigned) or removal/emeritus status (loses approve power) — neither satisfies the need.
  • Split out from #780 (same author, smg247) which proposes smarter blunderbuss reviewer selection.

Analysis

Current model

Config holds Approvers, Reviewers, RequiredReviewers, Labels. Each is copied by applyConfigToPath into its own map[path]map[*regexp.Regexp]sets.Set[string] field on RepoOwners.

Why a single new field isn't enough

entriesForFile(path, people, leafOnly) is the shared walk: with leafOnly=true it stops at the first directory with a match (backing LeafApprovers/LeafReviewers, consumed by blunderbuss auto-assignment); with leafOnly=false it accumulates the whole path (backing Approvers/AllApprovers, consumed by /approve authorization). Crucially, LeafApprovers and Approvers both read the same o.approvers map — so today a user can't be in the "full" set without also being in the "leaf" set. A naive addition of advisory approvers to that map would make them show up in LeafApprovers too, breaking the "never auto-assigned" requirement.

Recommended approach

  • Add AdvisoryApprovers []string to Config, parsed like Approvers.
  • Populate a new, separate o.advisoryApprovers map in applyConfigToPath (same shape as o.approvers).
  • Approvers()/AllApprovers() union o.approvers and o.advisoryApprovers — so /approve recognizes them.
  • LeafApprovers() stays scoped to o.approvers only — advisory approvers are structurally excluded from auto-assignment, no extra filtering needed.
  • Reviewers/LeafReviewers untouched — an advisory approver also listed under reviewers is unaffected.

This is directly precedented by how RequiredReviewers was added (fully separate field/map/accessor triple), so the implementation shape is well understood, not novel.
