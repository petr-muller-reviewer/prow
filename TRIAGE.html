Verdict

Accept as a bug; fix before or together with #955.

The trigger plugin treats every residual GitHub 403 from workflow approval as proof that rerunning is appropriate, even though rerun changes the triggering actor and authorization failures can have other causes.

What the issue reports

  • #798 added a rerun fallback when approval returns 403, intended for bot-created PRs in the same repository.
  • Rate-limit, abuse-limit, and obvious OAuth-scope 403s get special handling, but other 403s reach the generic fallback.
  • Such 403s can represent missing permissions or organization policy restrictions rather than the approve endpoint being inapplicable.
  • #955 repairs an invalid pending-run query and makes this currently dormant path execute in configured deployments.

Analysis

Reproducibility / observed behavior

The condition is deterministic. The current unit test passes github.NewForbidden() and expects a rerun; no cause-specific discriminator is required.

pkg/plugins/trigger/generic-comment.go:336-344

if github.IsNotFound(err) {
    ...
} else if github.IsForbidden(err) {
    if rerunErr := c.GitHubClient.TriggerGitHubWorkflow(org, repo, runID); rerunErr != nil {
        ...
    }
}

Probable cause

github.IsForbidden identifies the type forbiddenError, not why GitHub emitted a 403. The client retries rate/abuse responses and reports scope mismatch differently, but residual permission, SSO/IP policy, installation-state, and non-fork responses all become forbiddenError. The response body is retained but not exposed as a typed cause.

Approve and rerun are separate Actions endpoints (pkg/github/client.go:2241-2254 and 2304-2320). The latter changes triggering actor; treating a generic authorization failure as a rerun request is therefore too broad.

Related code

The caller already loads the pull request before invoking the helper:

pr, err := refGetter.PullRequest()
...
approveGitHubActionsWorkflowRuns(c, org, repo, pr.Head.Ref, headSHA)

pkg/plugins/trigger/generic-comment.go:137-154. It can pass same-repository/fork topology from pr.Head.Repo, avoiding an opaque response-body match.

Open questions
