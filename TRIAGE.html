Verdict

Accepted — legitimate, well-motivated feature request; effort level 3 (large), gated on an open maintainer design decision rather than code complexity.

The label plugin has no mechanism to enforce that only one label from a conceptual prefix set (priority/, lifecycle/, tracked/) exists at a time, forcing manual cleanup by the Release and Enhancements teams. A working analog already exists — hardcoded since 2018 in the standalone lifecycle plugin — and is the natural template to generalize into the label plugin via new configuration. The remaining blocker isn't code; it's an unresolved config-scope question awaiting input from @MadhavJivrajani/@cblecker.

What the issue reports

  • Users/bots can currently attach multiple labels from the same conceptual set simultaneously — e.g. two different priority/* labels on one issue — which doesn't make semantic sense.
  • The Release Team and Enhancements team spend recurring effort manually cleaning up these duplicates.
  • Requested fix: "exclusive sets" of label prefixes (priority/, lifecycle/, tracked/) where adding a label from a set auto-removes any other label already in that set.
  • Originally filed as kubernetes/test-infra#6095 before the repo split; the reporter notes this has been a known TODO for five years because it requires touching the label handler.
  • A contributor is actively engaging on implementation design, but a scope decision is still pending from maintainers.

Analysis

Reproducibility / observed behavior

Trivially reproducible: comment /priority important-soon on an issue that already has priority/backlog. Both labels end up applied — nothing removes the prior one. Root cause is structural, not a regression.

Probable cause

handleComment (pkg/plugins/label/label.go:147-312) computes labelsToAdd/labelsToRemove independently from regex matches and applies them in two separate loops (label.go:223-259 and label.go:261-286) with no cross-checking. The only prefix-grouping concept that exists — needs-* category handling at label.go:206-221, helper labelsWithCategory at label.go:374-383 — only decides whether to add a needs-kind/needs-priority label; it doesn't enforce exclusivity between labels of the same category.

Related code

pkg/plugins/lifecycle/lifecycle.go:32-34, 102-146

lifecycleLabels = []string{labels.LifecycleActive, labels.LifecycleFrozen, labels.LifecycleStale, labels.LifecycleRotten}

This is exactly the behavior the issue requests, but fixed to one hardcoded slice and one fixed regex (/lifecycle <x>), living in a separate plugin from label.go — not configurable, not reusable for priority/ or tracked/. Introduced in commit 83bd40f13 ("prow: allow only one lifecycle label to persist", 2018) — very likely the origin of the "5-year-old TODO" the issue references.

related-codeLabel plugin configuration model

pkg/plugins/config.go:447-495

type Label struct {
    AdditionalLabels []string
    RestrictedLabels map[string][]RestrictedLabel
}

RestrictedLabels is keyed by "*" (global) / org / org/repo, resolved via RestrictedLabelsFor — the established idiom for global/org/repo config scoping in this plugin. It governs write permission, not exclusivity, but its merge machinery (Label.mergeFrom, config.go:2378-2398) is the likely template for a new exclusivity config. Maintainer jberkus stated the new config should be "per Prow installation rather than per repo" — suggesting a simpler global-only shape may be preferred.

related-codeComparable prefix/regex + scoping pattern

pkg/plugins/config.go:921-957, plugin at pkg/plugins/require-matching-label/require-matching-label.go

RequireMatchingLabel uses a flat, org/repo/branch-scoped list with a compiled Regexp field — the "require at least one matching label" analog (opposite requirement, same regexp-prefix idea). Useful structural reference.

What I checked

  • No partial exclusivity implementation exists anywhere in the codebase beyond the hardcoded lifecycle plugin.
  • blunderbuss and sigmention have no prefix-based label logic at all.
  • tracked/* is not currently a recognized label command prefix in Prow (no regex, no constant) — only reachable via the generic /label path with AdditionalLabels configured.
  • lifecycle is not among the built-in prefixes in label.go; it's handled entirely by the separate plugin.
  • Broader codebase search for "exclusive"/"restricted label set" concepts turned up nothing relevant beyond unrelated config-validation comments (branch protection Include/Exclude, decoration config).
