Bottom line: accepted — legitimate, large (Level 3) architectural gap in Tide.

Tide has no concept of a GitHub "stacked PR" as a unit: its search-based discovery, its per-branch subpool partitioning, and its one-call-per-PR synchronous merge logic all independently break when applied to stacked PRs. The maintainer's own comment already scopes the three root causes correctly. This needs a design doc before implementation — not a quick patch.

What the issue reports

  • Tide fails to merge a PR that is part of GitHub's newer "stacked PR" feature.
  • GitHub returns: "Merging stacked PRs via this endpoint is not supported. Use the asynchronous merge endpoint instead."
  • A maintainer (Prucek) commented that this isn't a simple API swap: Tide's PR discovery, subpool grouping, and merge call all assume non-stacked, independent PRs.
  • No design work has started; the maintainer stated a design doc is needed before implementation.

Since previous triage:

  • On 2026-08-31T19:37:47Z, reporter dobesv confirmed that GitHub does not permit merging an individual stacked PR; it merges the stack. This confirms the reported async whole-stack behavior.

Analysis

Reproducibility / observed behavior

Any attempt by Tide to merge a PR belonging to a GitHub stacked-PR chain hits the classic merge endpoint's new rejection. No special repro steps beyond having a stacked PR in a Tide-managed repo and letting Tide reach merge time for it.

Probable cause

Tide's data model assumes every PR is independent, identified by a single (org, repo, base-branch) tuple, and mergeable via one synchronous API call. GitHub's stacked-PR feature breaks all three assumptions simultaneously:

  • Discovery: the GitHub search query is built from IncludedBranches/ExcludedBranches, emitted as base:"<branch>" qualifiers. Only the bottom PR of a stack has base == main/master; PRs above it target synthetic intermediate branches the query never matches — they are invisible to Tide, not just mis-pooled.
  • Pooling: PRs are grouped into subpools keyed by org/repo:branch. Even if discovered, each stack member would land in a different subpool (different base branch), so status/blocker/merge logic — which runs independently per subpool — can never treat a stack as one unit.
  • Merge semantics: Tide's merge loop assumes one API call resolves exactly one PR, synchronously. GitHub's async merge endpoint for stacked PRs merges the whole stack up to the given PR in one call and requires polling a job UUID — a different call/response shape Tide has no support for.

Recommended next steps

  • Confirm ownership of a design doc covering discovery, pooling, and async-merge semantics before any implementation starts — the maintainer explicitly requested this.
  • Verify stability/maturity of GitHub's stacked-PR async merge API before committing to a design.
  • If incremental progress is wanted, scope a narrower stopgap separately (swap in the async merge endpoint only for detected stack members, without fixing discovery/pooling) and label it explicitly as partial.
  • Apply labels area/tide, kind/feature; hold off on good-first-issue/help-wanted until a design exists.

Open questions
