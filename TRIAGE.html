Verdict: needs-discussion

The reported behavior is real, but whether it is a bug depends on the intended semantics of exclude. The current behavior (“don’t manage,” like unmanaged) has been stable for years. The issue author wants exclude to actively remove protection (like protect: false). This is a design ambiguity, not a clear-cut bug. A PR exists but changes long-standing behavior with backwards compatibility and API consumption implications.

What the issue reports

  • Adding a branch pattern to exclude in branchprotector config stops new protection from being applied, but does not remove existing protection from branches that were previously protected.
  • Branches matching exclusion patterns (e.g. ^konflux-, ^dependabot/) remain protected on GitHub, causing GH006: Protected branch update failed push errors.
  • Branchprotector logs show the branch as excluded, but takes no action to remove existing protection.
  • The author identifies the root cause at protect.go:341-343 and provides a workaround (temporarily remove from exclude list, let branchprotector run, re-add).
  • PR #478 by the same author implements a fix. Has lgtm, all CI green, waiting for approve.

Analysis

The design ambiguity

Branchprotector has three distinct branch-level behaviors with overlapping semantics:

  • protect: false — actively removes protection. Sends Request: nil through the updates channel, triggering RemoveBranchProtection.
  • unmanaged: true — don’t touch the branch. Branch enters UpdateBranch but returns early at line 456.
  • exclude (pattern) — branch is skipped via continue during enumeration (line 341-343). Never enters UpdateBranch. Functionally identical to unmanaged, but specified as a regex pattern rather than per-branch boolean.

If exclude is meant to mean “branchprotector doesn’t manage this branch,” the current behavior is correct. If it means “this branch should not be protected,” then the bug is real. The documentation (“branches that should be excluded from the protection policy”) doesn’t resolve the ambiguity. There is historical tension between the boolean config (protect/unmanaged) and the pattern config (include/exclude).

Probable cause (if it is a bug)

In UpdateRepo, the branch iteration loop at lines 328–347 builds a branches map. Excluded branches are filtered out via continue and never added to the map:

} else if !ok && branchExclusions != nil && branchExclusions.MatchString(b.Name) {
    logrus.Infof("%s/%s=%s: excluded", orgName, repoName, b.Name)
    continue
}

The processing loop at lines 370–377 iterates the map and calls UpdateBranch for each entry. Since excluded branches aren’t in the map, they never reach UpdateBranch, and no removal request is queued.

Related PRs

  • PR #478 — fix by kaovilai (same author as the issue). Adds a second pass after branch enumeration to detect excluded-but-protected branches and queue removal requests (Request: nil). Has lgtm, all CI green, waiting for approve.

Concerns with PR #478

  • Backwards compatibility: Changes exclude semantics from “don’t manage” to “actively remove.” Existing deployments using exclude to leave manually-managed branches alone would see their protection removed.
  • API consumption: Removal requests bypass the equalBranchProtections dedup (sent directly to the channel, not through UpdateBranch). For repos with many excluded protected branches, the first run produces a burst of RemoveBranchProtection API calls. Subsequent runs are fine (branches are no longer Protected after removal).

What I checked

  • Exclude field docs say “branches that should be excluded from the protection policy” — ambiguous.
  • Unmanaged flag takes a different code path (per-branch policy, not enumeration filter) but has the same “don’t touch” effect.
  • Include filtering has the same gap: branches that stop matching an include pattern keep existing protection.
  • Existing tests only verify excluded branches don’t receive protection, not that existing protection is removed.
  • Fake test client’s GetBranches correctly simulates Protected=true for the onlyProtected=true call.
  • Current exclude behavior has been stable for years.
