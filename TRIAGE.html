Verdict: needs-discussion

The reported behavior is real and root-caused: exclude is a pure enumeration-time skip that never queues protection removal, which the maintainer (petr-muller) confirmed 2026-08-13 is intentional — exclude is meant as a pattern variant of unmanaged: true, not of protect: false, and he initially moved to close this issue and the linked PR #478 on that basis. A subsequent live exchange with the reporter (kaovilai) surfaced a narrower, concrete gap — bot/automation-created branches get protected before any pattern can cover them, with no pattern-based way to retroactively unprotect them — which left the maintainer explicitly “softening” toward accepting a new, additive, pattern-based protect: false field instead. That decision is unresolved as of the last comment.

What the issue reports

  • Adding a branch pattern to exclude in branchprotector config stops new protection from being applied, but does not remove existing protection from branches that were previously protected.
  • Branches matching exclusion patterns (e.g. ^konflux-) remain protected on GitHub, causing GH006: Protected branch update failed push errors.
  • Branchprotector logs show the branch as excluded, but takes no action to remove existing protection.
  • The author identifies the root cause at protect.go:341-343 and provides a workaround (temporarily remove from exclude list, let branchprotector run, re-add).
  • PR #478 by the same author implements a fix by repurposing exclude itself; has lgtm, all CI green, but the maintainer has ruled out this specific approach.

Analysis

Reproducibility / observed behavior

Confirmed and root-caused by the reporter, independently verified in code. Add a branch to exclude, run branchprotector against a branch that was already Protected=true on GitHub — protection is never removed; the log line reads excluded and no further action is taken. Subsequent pushes to that branch fail with GH006.

Probable cause

In UpdateRepo, the branch iteration loop at lines 328–347 builds a branches map. Excluded branches are filtered out via continue and never added to the map:

} else if !ok && branchExclusions != nil && branchExclusions.MatchString(b.Name) {
    logrus.Infof("%s/%s=%s: excluded", orgName, repoName, b.Name)
    continue
}

Since excluded branches never reach UpdateBranch, no removal request is ever queued. The maintainer confirmed (2026-08-13T12:12:31Z) this is intentional: exclude is a pattern variant of unmanaged: true (don’t touch), not of protect: false (actively remove), and this semantics will not be changed.

The deeper gap surfaced during discussion

Unmanaged (pkg/config/branch_protection.go:32-34) is a per-branch-name boolean, not a regex list. Exclude/Include are the only regex mechanisms in Policy, and both are pure “don’t touch” filters. For branches whose names aren’t knowable in advance — bot/automation-created branches, e.g. Copilot-assigned branches — there is no pattern-based way to pre-empt protection, and once branchprotector’s default policy protects them, no pattern-based way to remove that protection afterward. Only a manual, exact-name protect: false or a manual GitHub UI/API action works, which for some organizations requires a change-ticket process. This reframing (surfaced 2026-08-13T12:45:09Z–13:18:08Z between kaovilai and petr-muller) is materially different from “what should exclude mean” and is what shifted the maintainer’s stance.
