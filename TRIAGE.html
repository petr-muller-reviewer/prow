#541 was auto-closed on 2026-07-04 by the stale-issue bot purely on inactivity, never judged on the merits. A prior full triage (2026-02-04) concluded Tide's accumulate() trusts unverified passing statuses and proposed a two-part fix. Re-checking against current main, the baseSHA-verification gate the fix would have added already exists in prowJobsFromContexts() and traces back to 2022 — three years before this issue and its motivating incident (#540) were filed. Applying that gate to #540's actual reproduction (a status description with no baseSHA) shows it would already force a retest rather than merge on the false status. Separately, the one real gap the prior triage found — the override plugin not encoding baseSHA — was fixed incidentally by unrelated work (PR #778) after #541 was closed. Recommend reopening and landing one regression test to confirm this by execution rather than by inspection, then closing with a citation-backed explanation (or re-scoping, if the test surprises us).

What the issue reports

  • Companion to #540, where a haywire status-reconciler falsely marked required job contexts as passing on in-flight PRs.
  • Requests that Tide force a retest of a required job whose passing status is "suspiciously" green — not backed by an actual passing ProwJob or a legitimate /override.
  • Author (a project maintainer) explicitly flagged uncertainty: they hadn't verified how Tide actually behaves today, and heard Tide did not retest the falsely-retired jobs during the #540 incident.
  • Filed with area/tide and kind/feature, well-scoped to a real component in this repository.

Analysis

Reproducibility / observed behavior

Not independently reproduced by running a test in this pass. #540's log shows the actual status description used by the buggy reconciler: "Context retired without replacement." — no baseSHA encoding at all. By inspection, feeding that description through current prowJobsFromContexts() logic, it fails the baseSHA/skip-retest gate and would not be treated as a verified passing context.

Probable cause (of the confusion, not a code bug)

The prior 2026-02-04 triage asserted accumulate() doesn't validate already-passing required contexts before trusting them. That claim doesn't hold up: prowJobsFromContexts() (pkg/tide/tide.go:1044-1076) only synthesizes a ProwJob for a passing context when its description carries a matching baseSHA (via config.BaseSHAFromContextDescription) or an explicit skip-retest sentinel (config.IsSkipRetest). accumulate() (pkg/tide/tide.go:1080-1138) builds its state map purely from real and synthesized ProwJobs — anything that doesn't clear that bar lands in missingTests and forces a retest.

Git blame traces this exact gate back to commit a1e8b25f4 ("Tide Controller interacts with GitHub by interfaces", 2022-06-02) — over three years before the issue (2025-10-31) and #540 (2025-10-14) were filed.

Related code

pkg/tide/tide.go:1050-1059 — the verification gate in prowJobsFromContexts:

desc := string(headContext.Description)
baseSHAForContext := config.BaseSHAFromContextDescription(desc)
if config.IsSkipRetest(desc) || (baseSHAForContext != "" && baseSHAForContext == baseSHA) {
    passingCurrentContexts = append(passingCurrentContexts, string(headContext.Context))
}

pkg/tide/tide.go:1112-1115 — unverified/missing contexts force a retest:

if s, ok := psStates[ps.Context]; !ok {
    // No PJ with correct baseSHA+headSHA exists
    missingTests[pr.Number] = append(missingTests[pr.Number], ps)
    log.WithFields(pr.logFields()).Debugf("missing presubmit %s", ps.Context)
}

pkg/tide/tide.go:845-889 (isPassingTests / unsuccessfulContexts) — the raw, unverified GitHub-status check. Used only by filterPR to decide pool membership, never to decide a merge.

pkg/tide/tide.go:1545,1561-1562,1783 (takeAction) — merges are only picked from the successes bucket returned by the baseSHA-verified accumulate(), confirming the unverified path never gates a merge.

pkg/plugins/override/override.go:564 — the override plugin now also encodes baseSHA (this was the one real gap the prior triage found):

status.Description = config.ContextDescriptionWithBaseSha(descFn(user), baseSHA)
