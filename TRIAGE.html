Verdict: accepted — Confirmed bug in Tide's batch merge logic. A fix exists in PR #538 and needs review to get merge-ready.

What the issue reports

  • When two PRs in the merge pool are semantically incompatible (each passes alone, they fail when batched), Tide gets stuck in an infinite loop re-triggering the same failing batch.
  • Tide should break the tie by falling back to merging one PR individually and retesting the other, but it never does.
  • Observed in production in Azure/ARO_HCP and openshift/dpu-operator repos.
  • The individual retest fallback in takeAction is starved because batch triggering has higher priority and fires first every sync cycle.
  • The root cause was identified by maintainers: accumulateBatch() silently discards failed batches, so takeAction() never learns a batch failed.

Analysis

Probable cause

accumulateBatch() in pkg/tide/tide.go:946-1038 evaluates batch ProwJob results and returns (successBatch, pendingBatch). The switch statement at lines 1028-1035 handles pendingState and successState but has no case for failureState. Failed batches are silently discarded.

switch overallState {
// Currently we only consider 1 pending batch and 1 success batch at a time.
// If more are somehow present they will be ignored.
case pendingState:
    pendingBatch = state.prs
case successState:
    successBatch = state.prs
}
// NO CASE FOR failureState
return successBatch, pendingBatch

This causes the following loop:

  1. syncSubpool() (line 1781) calls accumulateBatch(sp) and receives only success/pending — failed batch dropped.
  2. takeAction() (line 1798) receives batchPending but has no information about batch failure.
  3. At line 1569, takeAction checks len(batchPending) == 0 — true because the failed batch was discarded — and triggers a new batch via pickBatch().
  4. pickBatch() selects the same PRs (still eligible candidates), re-triggering the identical failing batch.

Why individual retests don't break the cycle

takeAction returns a single action per sync cycle. Step 4 (trigger batch, line 1569) has higher priority than step 5 (trigger individual retest, line 1579). Each time a failed batch clears batchPending, step 4 fires first and returns before step 5 is reached. Step 5 also requires len(successes) == 0 && len(pendings) == 0, further restricting when it can fire.

Related PRs

Reproducibility

Observed in production in Azure/ARO_HCP repo (PRs 3957, 3962, 3964 stuck in batch loop) and openshift/dpu-operator. Requires:

  • Two or more PRs eligible for batching with stale individual test results (base moved after a prior merge).
  • The PRs are semantically incompatible (pass alone, fail together).
  • Batch jobs fail quickly relative to the Tide sync period.
