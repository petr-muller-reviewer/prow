Verdict: Accepted

Legitimate, well-scoped feature request. The assign plugin has no configuration surface today (helpProvider in pkg/plugins/assign/assign.go explicitly says so), and the requested per-repo "only org members can /assign" gate closely mirrors two existing, established patterns — Trigger.OnlyOrgMembers and Approve's per-repo config/getter — and can reuse trigger.TrustedUser rather than reimplementing trust logic. A later follow-up idea in the thread (bot warning-comment for unvetted good-first-issue self-assigns) is materially larger and should be split into its own issue rather than bundled here.

What the issue reports

  • During GSoC-style contributor drives, newcomers drive-by /assign themselves (or others) to issues that were never vetted as beginner-friendly, citing a concrete kubevirt example.
  • Author asks for a per-repo config on the assign plugin restricting who may run /assign to org members only, referencing the exact config struct and enforcement code location.
  • A maintainer raised whether this should default to on (behavior change) vs. be opt-in — never resolved in-thread.
  • A separate commenter asked about also blocking non-owners from *re*-assigning an already-assigned issue.
  • A later (2026-04-14) comment adds a second, distinct idea: have the bot post an informational reply (not a hard block) when a non-org-member self-assigns an issue lacking a good-first-issue label.

Analysis

Probable cause / architectural gap

The plugin was never built with a config surface. handle() (pkg/plugins/assign/assign.go:113-152) unconditionally calls h.add/h.remove for any commenter; the only existing restriction is GitHub's own assignee-eligibility rule (must be an org member, collaborator, or prior commenter), which constrains who can be assigned, not who is allowed to issue the command.
