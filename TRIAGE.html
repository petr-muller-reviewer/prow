What the issue reports

  • Pushing a merge commit to a PR causes owners-label to add a flood of unrelated sig/*/area/* labels, based on every file touched by the merged branch.
  • mergecommitblocker separately flags the offending commit and the user force-pushes to remove it — but the spurious labels from owners-label never go away, because it only adds labels and never removes them.
  • Reporter (danwinship) and maintainer (BenTheElder) converged, across 6 comments, on skipping labeling unconditionally for merge commits — there is no workflow where labeling off a merge's aggregate diff makes sense.
  • Reporter proposed a per-commit approach; ruled out during research because per-commit file lists require additional GetCommit/GetSingleCommit API calls that the coarser DCO-style check avoids.

Discussion Summary (original issue thread)

6 comments between danwinship (reporter) and BenTheElder (maintainer). Key points:

Consensus reached: Merge commits should always be skipped for labeling, regardless of whether mergecommitblocker is enabled. There is no workflow where labeling from merge commits makes sense.
  • BenTheElder: +1, initially suggested opt-in tied to mergecommitblocker
  • danwinship: Argued the fix should be unconditional — labeling from merges only produces noise
  • danwinship proposed per-commit pseudocode: skip commits with len(Parents) > 1
  • Key insight: Merging master into a PR would label every file changed upstream since branch point — never useful
Tension with PR #782: the PR implements this as an opt-in per-repo config flag (ignore_merge_commits), reviving BenTheElder's earlier framing rather than the unconditional behavior the thread settled on. Worth raising explicitly in review.

Analysis

Reproducibility / observed behavior

Unchanged since the original report, confirmed still true against current main: push a merge commit onto a PR → owners-label fires on synchronize, labels every file in the merge's diff → force-pushing the merge commit away does not remove the labels.

Probable cause

owners-label calls GetPullRequestChanges which hits GitHub's GET /pulls/{n}/files endpoint. This returns the full diff between PR head and base branch — no per-commit breakdown. When a merge commit is present, all files from the merged branch appear in the diff.

Since owners-label's githubClient interface has no RemoveLabel method at all, the erroneous labels persist even after the user force-pushes to remove the merge commit.
