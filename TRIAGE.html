Overview

The issue requests OPA/Gatekeeper compatibility for Prow. The good news: Prow doesn't actually need privileges. No hardcoded privileged mode, no docker.sock mounts, no root requirements. The gap is missing SecurityContext boilerplate—Prow predates Pod Security Standards and never added it.

Proposed retitle: "Support Pod Security Standards (restricted profile) for ProwJob pods and control plane"

The Two Gaps

Gap 1: ProwJob Pods — No Container-Level SecurityContext

Utility containers (clonerefs, initupload, entrypoint, sidecar) are injected by pkg/pod-utils/decorate/podspec.go without container-level SecurityContext. PSS "restricted" requires each container to set:

  • allowPrivilegeEscalation: false
  • capabilities.drop: [ALL]
  • seccompProfile.type: RuntimeDefault

DecorationConfig (pkg/apis/prowjobs/v1/types.go:564-576) only exposes RunAsUser, RunAsGroup, FsGroup—none of the container-level fields.

Gap 2: Control Plane Pods — Bare Starter Manifests

All starter and integration deployment manifests ship with zero SecurityContext:

  • config/prow/cluster/starter/starter-gcs.yaml
  • test/integration/config/prow/cluster/{deck,hook,crier,horologium,tide}_deployment.yaml

Missing: runAsNonRoot, allowPrivilegeEscalation, capabilities.drop, seccompProfile.

Key Findings

Core Code Is Clean
  • No privileged: true in Go code
  • No docker.sock mounts
  • No hardcoded root user
  • decorateSpec() is non-overriding
Utility Containers Are FS-Safe
  • All writes go to volume mounts
  • /logs, /tools, /home/prow/go
  • readOnlyRootFilesystem: true should work
  • Needs verification audit
Privileged Only in Tests
  • privileged: true in Maistra test configs only
  • allowPrivilegeEscalation in nginx test only
  • Not in Prow's own deployments
No Policy Integration
  • Admission webhook: spec immutability only
  • No OPA/Gatekeeper integration
  • No PSS enforcement or warnings
  • No e2e tests in restricted namespaces

Recommended Solution

Recommended

Opt-in SecurityContext + Hardened Starter Manifests

Extend DecorationConfig with additional SecurityContext fields (following the existing RunAsUser/RunAsGroup/FsGroup pattern), plumb them through decorateSpec() to container-level contexts on utility containers, and update starter manifests with PSS "restricted" defaults.

+ Zero breaking changes—all new fields are optional pointers
+ Follows established DecorationConfig pattern exactly
+ Starter manifests give new deployments secure defaults
− Not secure by default for ProwJob pods (opt-in)
− Operators must discover and configure

Alternative approaches considered

Approach 1: Hardened Defaults

Make Prow secure-by-default. + Best security posture. − Breaking change for existing ProwJobs running as root.

Approach 3: Combined (Hardened Defaults + Opt-out)

Secure defaults with config relaxation. + Best of both. − Most complex, still breaking, bumps to Level 3.

PR Decomposition

  • (easiest, pure YAML) Harden starter manifests with PSS "restricted" SecurityContext
  • (API) Extend DecorationConfig with RunAsNonRoot, AllowPrivilegeEscalation, ReadOnlyRootFilesystem, SeccompProfile, Capabilities
  • (plumbing) Apply container-level SecurityContext to utility containers in decorateSpec()
  • (docs) "Running Prow in PSS-restricted environments" guide
